# Security Documentation

This page is the map of the security reference and the internal self-assessment of the controls in the current source. It was checked against that source on 2026-09-29.

> [!IMPORTANT]
> The ~99.9% figure below is this repository's own weighted checklist. It is not a penetration test. One item stays on the open list: a dated penetration test by someone outside the project. [Still open →](#still-open)

## Self-assessment

The self-assessment has two parts, both dated 2026-09-29: the weighted checklist, and an inventory of what the source does today. An inventory row leaves the open list when the outstanding work is in the tree and a regression test fails if that control is removed. The penetration-test row leaves the list when a dated third-party report exists. That report is not one of the six weights, so a clean scanner run cannot turn the checklist into an external test.

### How close this is to a penetration test

A penetration test is a dated report by someone outside the project who attacks a running deployment. This repository does not contain that report. The in-repo checks fail when a named control is removed: 343 security regressions, plus the five scanners in `bun run risk:audit`. They do not search for a bug the checklist never named. The [OWASP matrix](./owasp-asvs-compliance.mdx) maps controls to chapters. It is not a passed ASVS audit and not a certificate. The remaining distance is the external engagement itself, which is the open row below and the roadmap item "Third-Party Security Audit".

## How a request is checked

`classifyRequest` in `src/hooks.server.ts` picks the pipeline after setup is complete.

1. **Collection read lane.** A simple collection `GET` or `HEAD` with a warm session can be answered by `tryCollectionReadLane` before the pipeline. The lane scans the path, query, and headers with `wafGuard` before any cache or database read. Heap shedding and the Redis WAF limiter stay on `handleSecurity`.
2. **Collection write lane.** Opt-in with `SVELTY_FAST_LANE_WRITE=1`. It runs the WAF guard, CSRF, and the session-risk step-up, then one persist. A cold session falls through.
3. **API write pipeline.** `handleSecurity`, rate limit, system state, compression, authentication, authorization, audit logging, API dispatch.
4. **API read pipeline.** `handleSecurity`, system state, turbo GET, compression, authentication, authorization, API dispatch, token resolution. Rate limit and audit logging are omitted because those hooks cover mutations.
5. **Page pipeline.** The read pipeline plus the mutation rate limiter, redirects, user preferences, and audit logging.

Security headers are applied to responses, including errors. Fast static paths such as `/favicon.ico` return before the pipeline.

## Deployment checklist

The application ships the controls in the table above. These items are set in the environment that runs it.

- [ ] `JWT_SECRET_KEY` and `ENCRYPTION_KEY` are high-entropy values generated at setup (`ENCRYPTION_KEY` is a 32-byte AES-256-GCM key).
- [ ] The site is served over TLS. HSTS is set when the request is HTTPS.
- [ ] The database listens on a private network.
- [ ] The setup-wizard admin password has been replaced.
- [ ] API tokens use the smallest permission set that caller needs.
- [ ] Backup encryption, key rotation, and log retention match the operator's compliance window. `AUDIT_CHAIN_SYNC` is the switch for synchronous hash chaining.
