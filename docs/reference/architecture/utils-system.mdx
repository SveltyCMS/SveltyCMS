# Utility System Architecture

SveltyCMS utilities are organized by domain into flat files and subdirectories. The `@utils/*` path alias enables direct, tree-shakeable imports. The legacy `src/utils/utils.ts` barrel no longer exists — it was removed in the 2026 lean-out and `tests/unit/utils/circular-imports.test.ts` fails if a util imports `@utils/utils` again.

---

## 1. Directory Structure

```
src/utils/                          (counts verified 2026-11-05)
├── api-playground/   1 file    REST playground URL builder
├── auth/             2 files   Post-auth landing (server + shared)
├── compilation/      4 files   AST compilation for content scanner
├── media/           26 files   DAM engine — storage, processing, search, sharing, MIME, Canvas 2D
├── rate-limit/      13 files   Adaptive limits, L1 flood gate, token bucket, Redis client, tenant plans
├── schema/           3 files   Validation, comparison, tree
├── security/        23 files   Crypto, CSRF, CORS, envelope, field encryption, auth utils
├── server/           9 files   Setup checks, batch loading, layout caches, HMAC tokens
│
├── 126 flat `.ts` modules + `sanitize.svelte` + `iso639-1.json` (most-used listed below)
```

## 4. Import Patterns

```typescript
// ✅ Direct import — tree-shakeable, 1 module loaded
import { cn } from "@utils/string";
import { deepCopy } from "@utils/data-utils";
import { debounce } from "@utils/debounce";
import { lazyModule } from "@utils/lazy-module";
import { formatBytes } from "@utils/file";
import { formatUptimeMs } from "@utils/format-uptime";
import { decodePreferenceValue } from "@utils/preference-value";
import { hashPassword } from "@utils/security/crypto";
import { isSetupComplete } from "@utils/setup-check-fast";
import { advancedSearch } from "@utils/media/advanced-search";
import { createLink, revoke } from "@utils/media/sharing";
```

> ❌ `import { cn } from "@utils/utils"` no longer resolves — the barrel was deleted. Any remaining occurrence is a bug, not a shortcut.

Utilities connected to REST API handlers:

| Endpoint                        | Method | Utility                                           | Handler                    |
| ------------------------------- | ------ | ------------------------------------------------- | -------------------------- |
| `/api/media/share/{id}/{token}` | DELETE | `revoke()` in `sharing.ts`                        | `handleMediaShareRevoke`   |
| `/api/media/share/{id}/{token}` | PATCH  | `extend()` in `sharing.ts`                        | `handleMediaShareExtend`   |

## 6. Design Rules

1. **No barrel files** — `src/utils/utils.ts` and `src/utils/security/index.ts` were removed; every import names its module (enforced by `tests/unit/utils/circular-imports.test.ts`)
2. **New utilities go in domain files**
3. **No duplicate exports across modules** — use `import` instead of redefining
4. **Server-only files must guard** — throw on browser import, or use `.server.ts` suffix
5. **Subdirectories need 3+ related files** — single-file subdirs were flattened
6. **Documented features keep their code** — planned API endpoints need their utilities; only delete truly dead code with 0 consumers and 0 docs
