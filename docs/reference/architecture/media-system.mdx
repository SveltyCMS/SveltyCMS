# Media system

This page is the storage and processing pipeline. Cropping in the admin is the [Image editor](../../guides/content/image-editor.mdx). Upload and download routes are the [Media API](../api/media.mdx).

The SveltyCMS Media system is a decoupled, performance-first engine. Built with Svelte 5 and Sharp.js, it prioritizes native Node/Bun utilities over heavy third-party dependencies to ensure sub-millisecond latency and reduced bundle size.

## JSON Path Media Filter

Gallery filtering supports a small JSON-path expression language (client + server + DB).

| Layer        | Location                               | Behavior                                                       |
| :----------- | :------------------------------------- | :------------------------------------------------------------- |
| **Client**   | `+page.svelte` + `json-path-filter.ts` | Instant filter on loaded items                                 |
| **Server**   | `+page.server.ts` `?jsonPath=`         | Passes `jsonPath` into `getByFolder`; post-filters SSR payload |
| **Database** | `media-json-path.ts` + adapters        | Native pushdown for `metadata.*` on large libraries            |

### Syntax

```
metadata.camera = Canon
metadata.camera ~ canon
metadata.iso >= 400
metadata.tags[0] = nature
metadata.camera = Canon; metadata.iso > 100
```

Operators: `=` / `==`, `!=`, `~` / `*=` (contains), `>`, `<`, `>=`, `<=`. Multi-clause AND via `;` or `&&`.

Shareable URL example: `/mediagallery?folderId=…&jsonPath=metadata.camera%20%3D%20Canon`

### DB-native pushdown (large libraries)

When `options.jsonPath` is set on `media.files.getByFolder`:

| Adapter           | Mechanism                                       |
| :---------------- | :---------------------------------------------- |
| **SQLite**        | JSON1 `json_extract(metadata, '$.…')`           |
| **PostgreSQL**    | jsonb `metadata->>` / `metadata#>>`             |
| **MariaDB/MySQL** | `JSON_UNQUOTE(JSON_EXTRACT(metadata, …))`       |
| **MongoDB**       | Dotted-path filters + case-insensitive `$regex` |

Only simple `metadata.*` paths (no array indices) are pushed to the DB. Array paths (`metadata.tags[0]`) and non-metadata fields stay as in-memory post-filters so pagination remains correct when every clause is native.

Implementation:

- Parser: `src/utils/json-path-filter.ts`
- SQL/Mongo builders: `src/databases/core/media-json-path.ts`
- Unit: `tests/unit/utils/json-path-filter.test.ts`, `tests/unit/databases/media-json-path.test.ts`
- Integration: `tests/integration/api/media-jsonpath.test.ts` (`?jsonPath=` reduces load payload)

## 🛡️ Published-Reference Protection (Media Integrity Gate)

The media system prevents mutation of assets referenced by published content entries. This protects against broken references on live pages.

### How It Works

1. **Service Layer** (`media-service.server.ts`): `getPublishedReferences()` scans all collection schemas for entries with `status: "publish"` that reference a given media ID (by ID, path, URL, or embedded object reference).

2. **Handler Layer** (`handlers/media.ts`): A `checkMediaNotReferencedByPublishedContent()` helper is called in all 6 mutation handlers before performing the operation. Returns **409 Conflict** with details identifying which content entries reference the asset.

3. **UI Layer** (`media-grid.svelte`, `media-table.svelte`, `virtual-media-grid.svelte`): Edit/delete buttons are disabled with contextual tooltip "Referenced by published content". A lock badge appears at the top-left of affected media cards.

4. **Server Load** (`+page.server.ts`): Batched `Promise.allSettled` pre-checks all visible media items for published references before rendering.

### Gated Operations

| Handler         | HTTP Method                       | Response     |
| --------------- | --------------------------------- | ------------ |
| Direct delete   | `DELETE /api/media/:id`           | 409 Conflict |
| POST delete     | `POST /api/media/delete`          | 409 Conflict |
| Manipulate      | `POST /api/media/manipulate`      | 409 Conflict |
| Version create  | `POST /api/media/version`         | 409 Conflict |
| Version upload  | `POST /api/media/version/upload`  | 409 Conflict |
| Version restore | `POST /api/media/version/restore` | 409 Conflict |

### Error Response Format

```json
{
  "error": {
    "message": "Cannot modify asset: referenced by published content - \"Blog Post\" in \"Posts\" (featuredImage) and 2 more",
    "code": "MEDIA_REFERENCED_BY_PUBLISHED_CONTENT"
  }
}
```

## 🚀 The Media Pipeline (4-Stage Workflow)

SveltyCMS employs a high-performance ingestion and delivery pipeline designed for massive scale and resilience.

### Phase I: Ingestion (Client-Side & Hashing)

- **WebGPU/WASM Optimization**: **[Client-Only]** Large images are compressed, focal-cropped, and converted to WebP/AVIF directly in the browser _before_ upload, saving >90% bandwidth (`local-upload.svelte`).
- **Smart Upload Routing** (`upload-client.ts`): The gallery and dedicated upload page route payloads automatically — files or batches under **10 MB** use the SvelteKit form action (`?/upload`); larger payloads stream to `POST /api/media/stream` with the `folder` field preserved. Both paths share one hard ceiling: the dispatcher bounds the request at `API_MAX_BODY_SIZE_BYTES` (**15 MB**, `Content-Length` and chunked alike) and `parseMultipartStream` receives the same cap for `maxFileSize`/`maxTotalSize`, aborting incrementally with `413 PAYLOAD_TOO_LARGE` instead of buffering toward the parser defaults.
- **Hash-First Approach**: Every file is identified by the full 64-character hex **SHA-256** digest of its bytes (`hashFileContent()` in `src/utils/media/media-processing.server.ts`). The hash is both the deduplication key and the storage directory of the file: `{tenantId}/{hash}/original/<name>-<hash>.<ext>`. The lookup happens **before any derivative work** and is scoped to the tenant — see _Storage & Deduplication_ below and [#2 of the media pipeline plan](../../project/media-pipeline-plan.mdx).
- **SlimSniffer + unified allowlist**: `slim-sniffer.server.ts` (~2KB, no `mime-types`/`mrmime`) inspects magic bytes. Uploads use `isAllowedUploadMime()` (from `MIME_MAP`, minus scriptable/office types) and `assertMimeAgreement()` at write time. `/files` resolves Content-Type via extension → stored MIME → 512-byte sniff. Remote imports and `saveRemoteMedia` share `resolveRemoteAssetMime()`. All media responses send `X-Content-Type-Options: nosniff`.

### Phase II: Processing (Deep Metadata & AI)

- **Deep Metadata Extraction (opt-in)**: EXIF/IPTC/XMP, dominant colour and the 32 px WebP placeholder are extracted by `MediaProcessingService.getMetadata()` — called by `POST /api/media/process` and the SDK, not on every serve. The deep pass is more than a header read: `metadata()` **plus** `stats()` and a `resize(32,32).webp()` thumbnail (a full decode). Results are cached 24 h per file hash; `fastPath: true` returns the header-only fields (`format`, `width`, `height`, `space`, `channels`) without the decode.
- **Derivative ladder (SIZES)**: `saveResized()` (`media-storage.server.ts`) writes one primary output plus a WebP sidecar per configured `SIZES` step into `{tenantId}/{size}/<name>-<hash>.<ext>`. Two invariants hold: a step **wider than the decoded source is dropped** (plus `withoutEnlargement` at the encoder), so a 400 px icon produces the 200 px step only, and **each resolved path is written once** — a source that is already WebP no longer encodes its own primary twice. The `thumbnails` map records the encoder's real output dimensions; steps that were clamped away are simply absent, which `mediaUrl`/`mediaDisplayUrl` fall back from. Measured 2026-09-22: a 400 px source went from 8 files / 16,984 B to 2 files / 600 B.
- **Responsive variants (deferred)**: after the record exists, a fire-and-forget job derives `thumbnail`/`card`/`default` presets under `{tenantId}/{hash}/variants/{preset}-{width}.{format}` and stores them in `metadata.imageVariants`. Those paths are hash-keyed, so re-running the job is idempotent. This is the second pipeline that [#1](../../project/media-pipeline-plan.mdx) collapses into the ladder.
- **AI-Native Tagging [WIP]**: A conceptual background task that hooks into local Ollama (`llava`) for privacy-first image analysis.
- **Document Thumbnails**: Automated extraction of PDF first-pages (requires `imagemagick`).

### Phase III: Storage & Deduplication

- **Deduplication Engine**: After the hash is computed (and before any derivative work), the service looks the hash up **scoped to the tenant** (`media.files.getByHash` with `tenantId` — no cross-tenant reuse). On a hit it verifies that the record's original **and** every derivative path it advertises still exist; when they do, the existing record is reused, the deferred variant job is never scheduled, and the upload returns after at most one plain file copy (only when the same bytes arrive under a different filename, so the patched `path` stays truthful). When a file is missing — `remove()` unlinks files rather than directories, and a GC sweep can drop them — the row is **repaired in place** (original rewritten, ladder re-derived, `metadata` merged) instead of being returned with URLs that 404, and never duplicated into a second row.
- **Hybrid Storage**: Supports Local, S3, and R2 storage backends via the `CloudStorage` abstraction.
- **ETag/304 Handling**: Unified ETag strategy ensures high-performance browser caching. Cloud backends answer `/files/**` with a **302** redirect to the CDN public URL (with the object ETag when available, so `If-None-Match` can still 304); local storage streams the bytes itself. Because a dedupe hit writes nothing, the `W/"size-mtime"` ETag of an unchanged asset survives a re-upload — clients are not forced to re-download identical bytes.

### Phase IV: Delivery & Transformation

- **On-Demand Transforms**: `/files/**?w=&h=&q=&fmt=` produces cached raster variants on the delivery route (no separate `/api/media/*` transform endpoint exists). See [On-Demand Image Transforms](#-on-demand-image-transforms) below for the parameter contract, clamps, cache layout and fallback rules.
- **Focal Points**: Visual crosshair coordinates are injected into delivery APIs to support art-directed cropping in the frontend.
- **Lazy Loading**: `virtual-media-grid.svelte` handles 10,000+ files with sub-millisecond scroll performance using Svelte 5 runes.

## 🚀 On-Demand Image Transforms

> Added 2026-09-22 — `/files/**` honours `w`/`h`/`q`/`fmt` again with a real resize. Before this, the route ignored those parameters entirely and transferred the full original under any URL.

Transforms are **cached**: the variant is generated exactly once (single-flight), written next to the original, and every later request streams it from disk with an ETag + `Cache-Control: immutable`. Without `w`/`h` the route streams the original byte-for-byte — the parameters are opt-in and never change a plain asset URL.

### Parameters

| Param    | Aliases  | Accepted values                          | Behaviour                                                                                 |
| :------- | :------- | :--------------------------------------- | :---------------------------------------------------------------------------------------- |
| `w`      | —        | dimension ladder step                    | Target width, snapped **down** to the nearest step                                        |
| `h`      | —        | dimension ladder step                    | Target height; with `w` it becomes a bounding box (`fit: inside`, aspect preserved)       |
| `q`      | —        | quality ladder step                      | Encoder quality, snapped to the nearest step (default `82`)                               |
| `fmt`    | `format` | `webp`, `avif`, `jpeg`/`jpg`, `png`      | Explicit output format; any other value (e.g. `svg`, `gif`) rejects the transform         |
| `Accept` | —        | `image/avif`, `image/webp`, `image/jpeg` | Used (in `q=` order) only when `fmt`/`format` is absent; wildcards mean "keep the source" |

- **Dimension ladder** (`TRANSFORM_DIMENSION_STEPS`): `16, 24, 32, 48, 64, 96, 128, 160, 192, 240, 320, 384, 480, 640, 768, 960, 1280, 1600, 1920, 2560, 3840`, filtered by `MAX_OUTPUT_DIMENSION` (6000 px default). Requests are clamped **down** to a step and never upscaled (`withoutEnlargement`), so a caller cannot allocate an arbitrary resolution or fill the variant cache with one file per pixel width.
- **Quality ladder** (`TRANSFORM_QUALITY_STEPS`): `50, 60, 70, 75, 80, 82, 85, 90`. Encoder settings are shared with the upload-time variants (`applyEncoder()` in `src/services/media/image-processor.ts`), so quality stays consistent.
- Both ladders live in `src/services/media/image-processor.ts`; parsing is the pure `parseTransformParams(searchParams, accept, sourceMime)` helper.

```text
/files/global/<hash>/original/photo-<hash>.jpg?w=300          → 240 px wide, source format
/files/global/<hash>/original/photo-<hash>.jpg?w=640&h=480&q=75
/files/global/<hash>/original/photo-<hash>.jpg?w=1280&fmt=avif
/files/global/<hash>/original/photo-<hash>.jpg?w=320          + Accept: image/webp → WebP variant
```

### Cache layout

Variants reuse the existing variant store (`src/services/media/image-variant-storage.ts`):

```text
{tenantId}/{hash}/variants/t{height}q{quality}-{width}.{format}
# e.g. global/9f2c…/variants/t0q82-320.webp
```

- The key is `(hash, width, height, quality, format)` — `t0` means "height derived from the source aspect ratio". `hash` is the content hash of the original bytes, so a variant can never belong to another asset.
- The key is derived from the **original's tenant-scoped path**, never from a signed URL's signature: authorization stays with the route's tenant gate + signature validation (both run before any transform work), and differently-signed requests for the same tenant safely share one entry.
- Variant responses carry their own weak ETag, `Last-Modified`, `immutable`, `Vary: Accept` (the negotiated format depends on the request header) and `X-Media-Transform: w{width}h{height}q{quality}.{format}` for observability.

### What is never transformed

| Source / request                                                               | Result                                                                                         |
| :----------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| SVG                                                                            | Original (sanitised at upload; `/files` keeps its CSP `script-src 'none'` path)                |
| GIF (animated or still)                                                        | Original — animation must not be flattened                                                     |
| Animated WebP (`VP8X` animation flag / `ANIM` chunk)                           | Original — header sniffed, never re-encoded                                                    |
| Animated AVIF (`avis` brand)                                                   | Original — header sniffed                                                                      |
| TIFF, BMP, HEIC, PDF, video, unknown types                                     | Original                                                                                       |
| Files above `MAX_TRANSFORM_SOURCE_BYTES` (40 MB)                               | Original — bounds the one-shot read + decode                                                   |
| More than `MAX_CONCURRENT_TRANSFORMS` (8) distinct variants generating at once | Original for the excess — bounds aggregate decode memory; the rest generate on a later request |
| Paths that are not `{tenant}/{hash}/original/…`                                | Original — only canonical originals have a variant key                                         |
| Explicit unencodable `fmt`/`format`                                            | Original — a format we cannot encode is never faked                                            |
| No `w`/`h`, or both below the smallest step                                    | Original                                                                                       |

Every skip logs at **debug** level and falls back to streaming the original — a broken or hostile `?w=` can never fail the request (encoder errors, disk errors, oversized sources included).

### Storage backends

- **Local storage**: transforms are generated and cached in Node (Sharp), one generation per variant, single-flight coalesced.
- **`s3` / `r2` / `cloudinary`**: unchanged — the route keeps its **302** redirect to the CDN public URL _before_ any byte work, so transform parameters never pull the object through Node; on Cloudinary/Fastly-style CDNs the equivalent transform is applied CDN-side.

### Where the code lives

| Concern                                               | Location                                                                                                |
| :---------------------------------------------------- | :------------------------------------------------------------------------------------------------------ |
| Query parsing, ladders, encoder settings              | `src/services/media/image-processor.ts`                                                                 |
| Variant cache path + writes                           | `src/services/media/image-variant-storage.ts`                                                           |
| Route (gates → transform → stream), single-flight map | `src/routes/files/[...path]/+server.ts`                                                                 |
| Unit coverage                                         | `tests/unit/media/on-demand-transform-params.test.ts`, `tests/unit/media/files-route-transform.test.ts` |

## 📁 Virtual Folders & Drag-and-Drop Moves

Assets live in **virtual folders**: a logical `folderId` on each media row, not a physical directory tree. Folder definitions are stored as system virtual folders (`/api/system-virtual-folder`). Moving media updates metadata only — blobs and share URLs stay put.

### Data model

| Field on media | Meaning                                             |
| :------------- | :-------------------------------------------------- |
| `folderId`     | Virtual folder ID, or `null` / unset for media root |
| `path` / `url` | Storage-relative / public URL (unchanged by moves)  |

### Move pipeline

```mermaid

    participant Grid as media-grid / media-table
    participant Target as Sidebar folder OR breadcrumb
```

## 🔄 Asynchronous Processing & Job Queue

Heavy processing tasks (AI analysis, bulk variant generation, video transcoding) are decoupled from the main request/response cycle.

1. **Immediate Success**: The API returns a `202 Accepted` status along with an **`OperationID`**.
2. **Background Execution**: The `Job Queue Service` picks up the task and executes it across multiple worker threads.
3. **Polling/SSE**: The client polls the **`/api/media/jobs/:id`** endpoint or listens via SSE for the completion event.
4. **Metadata Update**: Once complete, the `MediaItem` metadata in the database is atomically updated.

## 🔍 Media Reference Reverse-Index

> Added 2026-07-16 — replaces O(n × entries) full-scan with O(1) indexed lookups.

### Problem

`getMediaReferences()` and `getPublishedReferences()` previously scanned **every entry in every collection** for each query — O(n × entries) per call. On a CMS with 50 collections and 10,000 entries, this meant 500,000 field traversals per reference check.

### Solution

`MediaReferenceIndex` (`src/utils/media/media-reference-index.ts`) is an in-memory reverse-index that maps media identifiers to the entries that reference them:

```typescript
// First query triggers a full rebuild (lazy)
// Subsequent queries are O(1) Map lookups
const refs = await mediaService.getMediaReferences(mediaId);
```

| Component                 | Location                                    | Purpose                                             |
| :------------------------ | :------------------------------------------ | :-------------------------------------------------- |
| `MediaReferenceIndex`     | `media-reference-index.ts`                  | In-memory `Map<mediaId, MediaReference[]>`          |
| `rebuildReferenceIndex()` | `media-service.server.ts`                   | Full scan → populates index, status map, name map   |
| `eventBus` invalidation   | Constructor + `SystemEvents.CONTENT_UPDATE` | Auto-clears index on any content mutation           |
| `enrichReferences()`      | `media-service.server.ts`                   | Backfills `fieldName`/`entryName` for API consumers |

### Architecture

```
Content mutation (create/update/delete)
  → eventBus.emit(CONTENT_UPDATE)
    → referenceIndex.clear()  (cache invalidated)

Next getMediaReferences() call
  → lazy rebuildReferenceIndex()  (one full scan)
    → O(1) lookups for all subsequent queries
```

**Design note**: The index is in-memory only. On first query it performs a full scan (rebuild), then subsequent queries are O(1). For production with thousands of entries, consider a periodic rebuild via `setInterval` or stale-while-revalidate. The `eventBus` listener ensures the cache is invalidated on any content update.

## 📤 Streaming Upload Parser

> Added 2026-07-16 — true streaming multipart parser with backpressure, replacing the previous TextDecoder→TextEncoder implementation that corrupted binary uploads.

### Problem {#streaming-upload-problem}

The previous `streaming-upload.ts` had two critical bugs:

1. **Binary corruption**: `TextDecoder`→`TextEncoder` round-trip replaced non-UTF8 bytes with replacement characters
2. **Not streaming**: Read the entire request body into RAM before parsing — OOM on large files

### Solution {#streaming-upload-solution}

A byte-level state machine (`streaming-upload.ts`) that processes `ReadableStream` chunks incrementally:

| Feature                   | Implementation                                                                                                                                                                                                                                                                                                                                      |
| :------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **True streaming parser** | Incremental byte-level parser — the multipart framing is never buffered as a whole                                                                                                                                                                                                                                                                  |
| **Binary-safe**           | Raw `Uint8Array` chunks pass through untouched                                                                                                                                                                                                                                                                                                      |
| **Backpressure**          | Per-file `ReadableStream` is pulled by the route consumer; the media route buffers the _current file_ into `chunks[]` (bounded by `API_MAX_BODY_SIZE_BYTES`) until it is complete, then hands it to the storage adapter — framing stays streaming, the part body does not                                                                           |
| **Size limits**           | `maxFileSize` / `maxTotalSize` are set by the route to `API_MAX_BODY_SIZE_BYTES` (**15 MB**) — the same ceiling the dispatcher enforces for `Content-Length` and chunked bodies. The parser's 1 GiB / 5 GiB defaults are never the effective limit on uploads; an oversize part aborts incrementally (`413 PAYLOAD_TOO_LARGE`) instead of buffering |
| **MIME validation**       | `isAllowedUploadMime()` on part Content-Type (415); magic-byte agreement after the body is available                                                                                                                                                                                                                                                |
| **Filename sanitization** | Path separators, control chars, Windows reserved names stripped                                                                                                                                                                                                                                                                                     |
| **Error cleanup**         | Active push streams errored on parser failure — no hanging readers                                                                                                                                                                                                                                                                                  |
| **Timeout**               | Configurable per-chunk read timeout (default 300s)                                                                                                                                                                                                                                                                                                  |

```typescript
// Real consumer (routes/api/[...path]/handlers/media.ts): the parser surfaces each part's
// ReadableStream; the route accumulates it under the 15 MB cap and writes one buffer —
// the StorageAdapter interface is `upload(data, relativePath)`, there is no uploadStream().
await parseMultipartStream(request, {
  onFile: async ({ filename, stream }) => {
    const chunks: Uint8Array[] = [];
    // …read with a running size check, then:
    await getStorageAdapter().upload(Buffer.concat(chunks), `global/${hash}/original/${filename}`);
  },
});
```

## 🛡️ Type-Safe Media Models

> Refactored 2026-07-16 — discriminated union with type guards, DTO types, and exhaustiveness checking.

### Design

`media-models.ts` uses `as const` maps (not enums) for tree-shakable, JSON-safe value lists. Each map doubles as the runtime valid-value list:

```typescript
// Type guards — narrow discriminated union at runtime
if (isMediaImage(item)) item.width;           // MediaImage
if (isStoredMedia(item)) item.hash;           // StoredMedia (excludes remote video)
if (isMediaOfType(item, MediaType.Video)) item.duration; // MediaVideo

// DTO types — server-assigned fields rejected at compile time
const draft: NewMedia<MediaImage> = { ... };  // no _id, hash, url, createdBy
const patch: MediaPatch = { alt: "photo" };   // PATCH-safe fields only

// Exhaustiveness — add a new media type and every switch fails to compile
switch (item.type) {
  case MediaType.Image:    return item.width;
  case MediaType.RemoteVideo: return item.provider;
  // ...
  default: return assertNever(item);
}
```

| Improvement         | Before                                      | After                                                    |
| :------------------ | :------------------------------------------ | :------------------------------------------------------- |
| Type safety         | `any` everywhere, zero guards               | Discriminated union + 7 type guards                      |
| DTO safety          | Client could PATCH `hash`/`url`/`createdBy` | `NewMedia<T>`, `MediaPatch` block server-assigned fields |
| Exhaustiveness      | Missing type = silent bug                   | `assertNever()` catches at compile time                  |
| Tree-shaking        | `enum` blocks `erasableSyntaxOnly`          | `as const` maps are fully erasable                       |
| Watermark positions | Sharp-rejected `"top"`/`"bottom"`           | `normalizeWatermarkPosition()` maps to compass values    |

## 🚀 Media Caching Layer

The media engine uses **process-local TTL caches** for repeated deterministic operations. These are separate from the global dual-layer cache (L1 LRU + L2 Redis) — media caches are smaller, shorter-lived, and scoped to their module.

| Cache                         | Location                                       | TTL   | Max entries    | Purpose                                                                       |
| ----------------------------- | ---------------------------------------------- | ----- | -------------- | ----------------------------------------------------------------------------- |
| **URL mapping**               | `storage-adapters.ts` → `getUrl()`             | 5 min | 10,000         | Path → URL resolution for every media item, thumbnail, variant on page render |
| **Metadata**                  | `media-processing.server.ts` → `getMetadata()` | 24 h  | 5,000          | Sharp metadata extraction (dimensions, EXIF, stats) by file SHA-256 hash      |
| **File existence (negative)** | `media-storage.server.ts` → `fileExists()`     | 10 s  | unbounded      | Skips adapter lookup for recently checked non-existent paths                  |
| **Watermark list**            | `media-utils.ts` → `fetchWatermarks()`         | 5 min | per-collection | Watermark collection query results                                            |

### Design decisions

- **URL cache**: Deterministic — same path always produces same URL. 10k entries covers all thumbnails + variants in a typical gallery view. LRU eviction via oldest-entry deletion at threshold.
- **Metadata cache**: File hash → metadata map. 24h TTL because image metadata never changes for the same bytes. Callers that already computed the hash (e.g., upload pipeline) pass it via `options.hash` to skip re-hashing.
- **Negative existence cache**: Short 10s TTL — prevents repeated adapter calls during upload validation without stale false negatives. Paths a dedupe hit depends on (the original and every derivative it advertises) are verified with `refresh: true`, so a cached _positive_ can never mask a file that a GC sweep removed.
- **Watermark cache**: Watermarks rarely change. 5min TTL avoids re-fetching on every watermark tool open.

All caches use plain `Map` with timestamp-based expiry — no external dependencies, no serialization overhead, zero allocation on hit.
