### Does it fail closed?

- **Missing tenant at the hook: no.** `src/hooks/handle-authentication.ts:1117` initialises `locals.tenantId = null` and continues; no hook rejects a tenantless request.
- **Invalid tenant: no validation at all.** `isValidTenantId()` exists (`src/utils/tenant.server.ts:91-94`) but is called only from the compilation path (`src/utils/compilation/compile.ts:200`). `grep -rn "isValidTenantId" src` returns exactly those two hits. An unknown host label becomes a brand-new empty tenant scope rather than an error.
- **First real gate is the DB layer:** `src/utils/security/safe-query.ts:78-98` throws `TENANT_CONTEXT_MISSING` only when `tenantId` is `undefined` or `""` (`:86-90`); `null` is treated as the **explicit global scope** (`:72-76` comment, `:87-89`), which is why `assertTenantContext` alone cannot stop a tenantless request from reading/writing the global layer.
- **API-boundary gates exist per handler, not centrally:** `src/routes/api/[...path]/handlers/media.ts:152-155`, `handlers/system/system-transfer.ts:51-53` and `:83-85`, `handlers/system/system-shared.ts:54-59`, `handlers/system/system-ai.ts:142`.
- **Media file delivery does fail closed:** `src/routes/files/[...path]/+server.ts:486-499` rejects when `MULTI_TENANT` is on and `locals.tenantId` is missing or does not match the path tenant.

## 3. Is PostgreSQL Row-Level Security actually implemented?

The code exists and is coherent. It is **not wired**, so today it protects nothing. `enforceTenantPolicy()` now **fails closed** — after the DDL it reads back the catalog and refuses to report success when the policy cannot filter — so calling it can no longer produce a false sense of safety.

## 5. Prioritised missing data-safety tests

Each case is written so it **fails on the branch it was written against** — that is the point of adding it. Items 1 and 5 have since shipped (their rows above are marked fixed); they are retained as the acceptance criteria that the new tests pin.

### 1. GraphQL data operations must reject a foreign `tenantId` argument (shipped)

- **Precondition:** `MULTI_TENANT=true`; logged-in non-admin user of `tenant-a`; a collection `posts` with a row owned by `tenant-b`.
- **Action:** `mutation { contentExportRun(collections:["posts"], tenantId:"tenant-b") { manifest } }` against `/api/graphql`.
- **Expected behaviour (now implemented):** 403 (or GraphQL error), and no `tenant-b` content in the response. `resolveGraphQLTenant()` (`data-operations.ts:346-367`) rejects a differing tenant for anyone below `super-admin`, and a multi-tenant deployment with no session tenant throws. Pinned by `tests/unit/api/graphql-tenant-scope.test.ts`.
- **Also covered:** the same resolver gate is applied to every data-operation field that accepts `tenantId` (the 15 fields); other resolvers keep their own checks.
- **Suggested file:** `tests/unit/api/graphql-tenant-scope.test.ts`.

### 2. Provisioning a collection must enable and be able to prove PostgreSQL RLS

- **Precondition:** PostgreSQL adapter, `MULTI_TENANT=true`, connected as the table owner.
- **Action:** create collection `rls_probe`, then query `SELECT relrowsecurity FROM pg_class WHERE relname='collection_rlsprobe'` and `SELECT polname FROM pg_policy`.
- **Expected failure mode (still open):** `relrowsecurity = true` and a `tenant_isolation` policy exists is the **correct** end state, but it is not reachable today: `relrowsecurity = false` and `pg_policy` is empty, because `enforceTenantPolicy` has no caller (`adapter-core.ts:2231`, interface at `db-interface.ts:1703`). Calling it directly now fails closed (owner-bypass read-back) rather than reporting success.
- **Suggested file:** `tests/integration/databases/tenant-rls-wiring.test.ts` (skip unless `DB_TYPE=postgresql`).

### 3. A tenantless request must be rejected at the HTTP boundary, not written to the global layer

- **Precondition:** `MULTI_TENANT=true`; authenticated admin; request to a bare two-label host (`cms.example.com`) so `getTenantIdFromHostname` returns `null` (`tenant.ts:47`) and no session tenant is present.
- **Action:** `POST /api/collections/posts` with a valid body and no `?tenantId=`.
- **Expected failure mode:** `400 TENANT_REQUIRED`, and `SELECT count(*) FROM collection_posts WHERE "tenantId" IS NULL` unchanged. Today the hook leaves the tenant null (`handle-authentication.ts:1117`, `:1201`), the raw adapter is exposed (`tenant-adapter.ts:157`), and `assertTenantContext` accepts `null` as the global scope (`safe-query.ts:87-89`), so the row can be written with `tenantId NULL` — the layer every other tenantless request can read.
- **Suggested file:** `tests/integration/api/tenantless-write-fails-closed.test.ts`.

### 4. Full-text search must not inherit the ambient tenant of another request

- **Precondition:** `MULTI_TENANT=true`; two tenants with identical titles; adapter `fts` available.
- **Action:** `applyAdapterTenantContext(db, "tenant-a")`, then `applyAdapterTenantContext(db, "tenant-b")`, then call `db.fts.search(collection, query)` **without** `options.tenantId`.
- **Expected failure mode:** either throw `TENANT_CONTEXT_MISSING`, or run with the caller's tenant — never with `tenant-b`. Today the PostgreSQL clause is built from `options?.tenantId ?? core.currentTenantId` (`postgresql/fts-adapter.ts:323`, `:447`) and `currentTenantId` is mutable adapter state (`core/tenant-pool-manager.ts:41-59`), so the search runs under whichever tenant set context last. MariaDB builds the predicate from `options` only (`mariadb/fts-adapter.ts:155-168`), so the equivalent failure there is a dropped predicate (a global read), not a stale tenant. Add the converse case: two interleaved requests must not cross.
- **Suggested file:** `tests/unit/databases/fts-tenant-context.test.ts`.

### 5. An integration leak assertion must not accept "200 or 401" as a pass (shipped)

- **Precondition:** `MULTI_TENANT=true`; marker row seeded under `tenant-a`; admin session; `x-test-tenant-id: tenant-b`.
- **Action:** `GET /api/collections/<coll>?publicationFilter=all` as tenant B.
- **Expected behaviour (now implemented):** exactly `200` **and** the marker absent; if the request is unauthenticated it must be `401`, and the test fails rather than skips. The former permissive assertion in `tenant-isolation.test.ts` accepted both statuses and only checked the body on 200; it now requires 401/403, or 200 with an explicitly empty tenant-B slice, and a DB-less run skips with a reason.
- **Suggested file:** keep `tests/integration/databases/tenant-isolation.test.ts` tight, plus the same assertion for GraphQL (`/api/graphql`).
