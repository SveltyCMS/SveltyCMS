# Database Documentation Hub

Welcome to the SveltyCMS Database Engine documentation. Our architecture is built on the principle of **Strict Database Agnosticism**, allowing you to swap between NoSQL and Relational engines without changing a single line of application logic or frontend code.

## What Does "Database-Agnostic" Mean in SveltyCMS?

In traditional CMS architectures, changing databases usually requires rewriting schemas, ORM models, or migration files. SveltyCMS solves this through the **Unified `IDBAdapter` Interface**:

1. **Local & Edge (SQLite)**: Sub-millisecond queries in WAL mode with zero network latency. Ideal for local development, testing, and single-node production.
2. **Enterprise Relational (PostgreSQL & MariaDB)**: Native connection pooling, ACID transaction guarantees, and compiled prepared-statement plans for high-concurrency clustered workloads.
3. **Document Store (MongoDB)**: High-throughput document operations with type-safe query guards and automatic connection failover.
4. **Zero Code Changes**: Collections, field widgets, workflows, and search indexes behave identically across all four supported engines.

## 🛡️ Shared Security Principles (All Adapters)

- **4-Layer Defense-in-Depth**: Middleware → Dispatcher → Handler → Page Action
- **Tenant Isolation**: Every query scoped by `tenantId` at adapter level — architecturally impossible to bypass
- **Credential Hashing**: Website tokens and API keys are stored as SHA-256 digests only; plaintext is returned once on creation. See [`system.websiteTokens`](./database-methods.mdx#-credential-storage-website-tokens--api-keys).
- **Tenant-Scoped Bearer Lookup**: Auth passes `locals.tenantId` into credential lookups (aligned with `auth.getApiKey`) to narrow multi-tenant queries.

- **MongoDB Soft-Delete Safety**: `safeQuery()` applies `isDeleted: { $ne: true }` so legacy documents without the field remain visible to active queries.
- **SQL Soft-Delete Clamp (parity)**: `SqlAdapterCore.clampSoftDeleted` AND-s `isDeleted = false` into `findMany`/`findOne`/`count`/`exists`/`findByIds`/`streamMany`/`findPage`/`aggregate` unless the caller opts in with `includeDeleted` (or a system `bypassSafeQuery`), the table has no `isDeleted` column, or the query already pins `isDeleted` (the trash view). `findById` clamps the raw projection directly.
- **SSRF Prevention**: Cloud storage adapters validate endpoints before connection
- **NoSQL Injection Protection**: `sanitizeMongoQuery` blocks `$where`, `$function`, `$expr`
- **CSPRNG-Only Tokens**: `globalThis.crypto.getRandomValues()`, no `Math.random()` fallback
- **Fail-Closed API**: Unmapped namespaces return 403 by default

## 🔄 Shared Resilience Patterns (All Adapters)

- **Circuit Breaker**: 5 consecutive failures → 60s open → probe recovery
- **Self-Healing Reconnection**: Auto-recovery on connection loss + HMR reload
- **Exponential Backoff with Jitter**: 1s→2s→4s→8s→16s, ±500ms
- **Connection Pool Diagnostics**: `GET /api/database/pool-diagnostics` + dashboard widget — see [Database Resilience](./database-resilience.mdx)
- **Migration Safety**: `CREATE TABLE IF NOT EXISTS` — idempotent

## Adapter & Cache Selection Guide

| Scale                             | Recommended DB                             | Redis L2?         | Why                                                                                                                                            |
| :-------------------------------- | :----------------------------------------- | :---------------- | :--------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dev, edge, small teams**        | **SQLite** (default)                       | **No** (Optional) | In-process, zero network overhead, sub-ms CRUD. RAM L1 cache handles hot reads.                                                                |
| **Production single node**        | **PostgreSQL** or **MariaDB**              | **Optional**      | Native JSONB/JSON, relational ACID, robust pooling. Enable Redis for high-traffic spikes.                                                      |
| **High-volume NoSQL**             | **MongoDB**                                | **Recommended**   | Cuts BSON serialization overhead by ~20% and lowers p95 read latencies.                                                                        |
| **Enterprise Multi-Node Cluster** | **PostgreSQL** / **MariaDB** / **MongoDB** | **Recommended**   | Synchronizes cluster nodes via Redis Pub/Sub (`svelty:cache:invalidation`), prevents cache stampedes, and lowers p95 tail latencies by 30–35%. |

> [!NOTE]
> **Redis is Strictly Optional Across All 4 Adapters**: Without Redis, SveltyCMS automatically operates using its built-in in-memory LRU cache (`<0.001ms` hit time) with zero degraded features.

## 🧭 Supported Database Engine Versions & Latest Optimizations (2026–2027)

SveltyCMS targets a **lean 2-generation active window** across all four engines. The window guarantees a modern native baseline; the newest generation unlocks the fastest paths (see the caveats below). Hard floors are enforced at connection boot; older majors boot only through the migration escape hatch.

### Support tiers

| Tier                               | Engines                                                                         | Guarantee                                                                                                                               |
| :--------------------------------- | :------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------- |
| **Supported (boot-enforced)**      | PostgreSQL 18–19 · MariaDB 11.4–13.2 · MongoDB 8.0–9.0 · SQLite 3.51–3.54.1     | Tested in the adapter contract suites; boot fails below the floor.                                                                      |
| **Compatibility (migration only)** | PostgreSQL 15–17 · MariaDB 10.5.2–11.3 · MongoDB 6.0–7.x · SQLite 3.38–3.50     | Boots only with `SVELTY_ALLOW_LEGACY_DB=1`; emits a boot warning; not covered by CI; use for a one-off import, then upgrade the server. |
| **Unsupported (technical floor)**  | PostgreSQL ≤14 · MariaDB ≤10.5.1 / Oracle MySQL 8 · MongoDB ≤5.0 · SQLite ≤3.37 | Refused even with the escape hatch — the adapter uses syntax those engines reject.                                                      |

> [!IMPORTANT]
> **`SVELTY_ALLOW_LEGACY_DB=1` is a migration escape hatch, not a supported production mode.** It bypasses all four floor checks, logs a warning, and leaves you on untested code paths. Run the import, then upgrade the server before serving traffic.

### Window caveats

- **MariaDB 11.4–12.x** does not have `UPDATE ... RETURNING` (added in 13.0). Those versions use the 2-round-trip `INSERT ... RETURNING` + `skipReturning` / base-update fallback. The single-round-trip update path is guaranteed only on 13.0+.
- **PostgreSQL 18** does not have `REPACK (CONCURRENTLY)` or `WAIT FOR LSN` (added in 19). Read-Your-Writes reads on PG 18 stay pinned to the primary for `readYourWritesWindowMs`; on PG 19+ the router waits on a standby and serves the read there when synchronized.
- **MongoDB transactions** remain disabled by default (`supportsTransactions: false`). The 8.0 floor makes them available, but they are not wired into the default write path.
- **SQLite** is checked with `sqlite_version()`; FTS5 also requires the runtime's SQLite build to include `ENABLE_FTS5` (Node ≥ 24.22.1 and Bun ≥ 1.3.12 bundle it).
