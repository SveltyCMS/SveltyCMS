# Performance Architecture

## 📊 Performance Benchmarks (2026-2027)

SveltyCMS delivers enterprise-grade performance through its database-agnostic architecture. For the complete set of verified benchmarks, stress test results, and hardware context, please refer to the [Performance Benchmarks](/docs/project/benchmarks/index) document.

### The 4-Cell Benchmark Contract {#4-cell-benchmark-contract}

Every performance claim about the data layer is classified into one of four cells, so an in-memory
cache hit can never be presented as database throughput (the category error this contract exists to
prevent):

| Cell                                   | Classification        | What it measures                                                        | Target / behaviour                                                    |
| :------------------------------------- | :-------------------- | :---------------------------------------------------------------------- | :-------------------------------------------------------------------- |
| **Cell 1: L1 / 304 Hit**               | Cache Plane           | In-memory single-flight / HTTP 304 `If-None-Match` short-circuit        | 10 000+ RPS (zero DB I/O, independent of driver)                      |
| **Cell 2: Origin Miss (Domain Plane)** | Canonical CMS Miss    | Drizzle ORM query + DTO mapping + FLAC + `JSON.stringify()`             | 500–1 500 RPS (baseline canonical pipeline)                           |
| **Cell 3: Origin Miss (Wire Plane)**   | Accelerated Wire Miss | Pre-compiled `json_build_object` / `json_object` streaming              | Measurable RPS↑, p95↓, RSS↓ vs Cell 2 (PostgreSQL & SQLite)           |
| **Cell 4: Raw Driver Ceiling**         | Physical Driver Limit | Bare driver throughput via `raw-db-ceiling.ts`, plus its raw HTTP floor | Machine-specific reference printed by `raw-db-ceiling.ts` on that run |

> [!IMPORTANT]
> **Merge laws**
>
> 1. **Cell 1 must never appear in a "vs ceiling" percentage.** It is an in-memory short-circuit;
>    claiming 10k+ RPS as database performance is a category error.
> 2. **Cell 3 must beat Cell 2 on PostgreSQL and SQLite** on the identical commit, verified with
>    byte-identity envelope snapshots (`trimPointReadEnvelope`). **Still pending** — the compiled
>    point path ships on all four adapters, list-wire is not routed from any route, and no Cell-3
>    matrix has been published; see [roadmap-2026](../../project/roadmap-2026.mdx).
> 3. **Cell 4 stays a machine-specific reference ceiling**, never a target the CMS claims to exceed.
> 4. The honest yardstick for HTTP-layer records is **`% of the raw HTTP floor`** (driver + HTTP +
>    JSON framing), not `% of the in-process driver ceiling` — the latter compares across domains.
>    On SQLite the floor is what binds (driver ≈ 250k RPS in-process, HTTP floor 29.2k for a point
>    read), which is why `findById` measures ~32 % of the floor while `listPlain` reaches ~59 %.

### Dual-Runtime Profile (Node.js V8 vs. Bun JavaScriptCore)

SveltyCMS provides first-class support for both **Node.js (>=24)** and **Bun (>=1.3 / 1.4)**:

- **Node.js 24+ (V8 TurboFan)**: Recommended for **long-running production servers**. In full-stack CMS workloads involving deep middleware chains, session HMAC cryptography, GraphQL AST parsing, and Drizzle query construction, V8's TurboFan JIT compiler delivers **1.8× to 2.4× higher sustained throughput (4,000+ RPS on `findById`)** and tighter p99 tail latency.
  - **V8 Young Generation Tuning & Soak-Test Hardening**: In high-throughput 60s soak tests (1,342 avg RPS, peak 2,398 RPS, 81,488 total requests), SvelteKit allocates 30–35 MB/s of ephemeral objects (Request, Response, URL, locals, ASTs). With the Node.js default 16 MB Semi-Space, the Young Generation overflows in milliseconds, forcing V8 to promote short-lived garbage into Old Space (**Premature Tenuring**). This accumulates ~500 MB of garbage and causes major Full GC pauses at ~15s and ~55s.
  - **The Fix**: Setting `NODE_OPTIONS="--max-semi-space-size=64 --max-old-space-size=1024"` (matching the production `Dockerfile`) expands the young generation headroom. V8 cleans up transient allocations in sub-millisecond minor scavenge cycles (<1 ms) without tenuring them into Old Space, eliminating GC throughput drops and stabilizing memory at ~200–300 MB under sustained load. The semi-space was originally tuned to 128 MB and lowered to **64 MB on 2026-09-27** after a paired A/B (128/64/64/128, same code) showed no throughput cost with ~128 MB less committed heap; the dated operating-point numbers below were measured at 128 MB.
  - **Where that operating point settles (measured 2026-09-22 at semi-space 128, 1 h soak row, SQLite, ~97 req/s)**: three independent runs converge on `heapTotal` **342.8 / 344.0 / 347.9 MB** — the 2 × 128 MB semi-space plus old space — with `heapUsed` oscillating 72–176 MB and **no trend** (tail slope −0.10 to +0.06 MB/min, |t| ≤ 0.3) and flat `external`. An `idle` control releases the entire commitment (RSS 221.9 → 77.6 MB). Treat the committed ceiling as the young-generation budget, not as retention: it is ~3.5× the post-GC live set by design. **The 1 GB old-space cap is a safety budget, not a tuning target**: the vendor comparison's capped rows paid major GCs under a 384 MB cap, while our `heapUsed` peaks at ~176 MB (≈17 % of 1024 MB) with a flat slope — raising it buys no speed and risks an OOM-kill under a real container limit. Row matrix and controls: [achievements-2026](../../project/achievements-2026.mdx).
  - **Containerization**: The official production `Dockerfile` is built on `node:24-slim` with these flags pre-configured, coupled with a fast, zero-dependency `curl` healthcheck (~3 ms vs ~200 ms Node evaluation).
- **Bun 1.4+ (`Bun.serve`)**: Recommended for **developer tooling (`bun install` / `bun test`), CLI scripts, and serverless / edge containers** where sub-10ms cold start latency and low idle memory are prioritized.

### Core ↔ adapter communication (all 4 engines) {#core--adapter-communication-all-4-engines}

Every request — LocalCMS SDK or HTTP — uses the same write pipeline. The database adapter is a **direct in-process call**, not an HTTP hop:

1. Valibot sanitization (once, in core).
2. Cached schema + widget transforms (`fields._activeWidgets`, reused accessor).
3. `db.crud.insert` / `update` / `find` on the active adapter.
4. Single-statement native driver execution (SQL `UPDATE … RETURNING` / Mongo `findOneAndUpdate` `$set`).
5. Off-path microtasks: outbox, L2 invalidation, webhooks, audit.

Adapters do **not** re-validate payloads (Mongo `runValidators: false` on hot writes). `createdAt` is insert-only on SQL and Mongo. Partial SQL updates omit an empty `data={}` blob.

**`BENCHMARK` is not a write-path cheat.** `isBenchmarkExternalServicesDisabled()` only skips **outbound** webhooks, SMTP, and similar network I/O so the matrix does not contact third parties. Persistence, Valibot, RBAC, RETURNING/`$set`, and L1 invalidation run the production path. `skipSideEffects: true` is an explicit SDK option (bulk seed / import), reported as a separate **(detached)** column — it is not toggled by `BENCHMARK`. Ambient `BENCHMARK` was removed from SQL `skipReturning` so insert/update benches measure the same SQL as production.

| --------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------- |
| Core schema / widgets | In-memory LRU + field-cached transforms                                            | —                                        |
| Adapter write         | One prepared statement / atomic `$set`                                             | —                                        |

### In-Memory Plan & Metadata Caching: WeakMap vs. Standard Map {#weakmap-vs-map-security-analysis}

The CMS engine uses `WeakMap` extensively across hot paths (e.g. `_dateKeyCache`, `prepPlanCache`, `collectionModelCache`, and WAF request header inspection memoization).

#### Architecture & Mechanics Comparison

| Characteristic         | Standard `Map<K, V>`                                               | `WeakMap<K, V>`                                               | Architectural Impact in SveltyCMS                                                                      |
| :--------------------- | :----------------------------------------------------------------- | :------------------------------------------------------------ | :----------------------------------------------------------------------------------------------------- |
| **Key Reference Type** | Strong (prevents Garbage Collection of key)                        | Weak (key reference does not prevent GC)                      | WeakMap allows dynamic collection reloads, schemas, and plugin teardowns to be collected cleanly.      |
| **Memory Lifecycle**   | Manual cleanup required (`.delete()`, `.clear()`, or LRU eviction) | Automatic (entry vanishes when key object is collected)       | Zero memory leak surface. Impossible to cause memory-growth DoS via dynamic schema or plugin creation. |
| **Enumerability**      | Iterable (`.keys()`, `.values()`, `for...of`, `JSON.stringify`)    | Non-iterable (no enumeration or size inspection)              | Keys and values cannot be inspected, enumerated, or dumped via heap reflection or prototype pollution. |
| **Key Types**          | Any primitive or object (`string`, `number`, `object`)             | Objects only (`object`, `Function`, `symbol` where supported) | Used for object-anchored runtime metadata (table definitions, AST plans, request instances).           |
| **Lookup Cost**        | $O(1)$ amortized hash table lookup                                 | $O(1)$ amortized engine-level ephemeron lookup                | Identical sub-microsecond hot-path performance without LRU pruning overhead.                           |

#### Security Analysis: Does WeakMap Compromise Security?

**No. In fact, `WeakMap` enforces a stronger security posture than standard `Map`:**

1. **Denial of Service (DoS) & Memory Leak Mitigation**:
   Standard Maps holding cached query plans or schema metadata require explicit eviction policies (LRU/TTL). Under tenant churn, frequent plugin hot-reloading, or dynamic collection generation, a standard Map risks unbounded memory leaks, eventually triggering process out-of-memory (OOM) crashes. With `WeakMap`, as soon as a schema definition or table instance goes out of scope, its associated cache entries are immediately reclaimable by the V8/JavaScript engine garbage collector.
2. **Structural Information-Hiding & Anti-Introspection**:
   Because `WeakMap` does not expose `.keys()`, `.entries()`, or `.size`, an attacker gaining arbitrary code execution or prototype access cannot dump or enumerate cached database table metadata or query structures. Access to the cached value strictly requires holding a direct reference to the exact key object.
3. **Tenant & Data Isolation**:
   `WeakMap` in SveltyCMS is used strictly for **structural engine plans** (e.g. date-column names, column selection sets, compiled sanitization functions), **never** for tenant data, user records, or cryptographic secrets. Data isolation remains strictly governed by `tenantId` boundaries in the database adapters and middleware.

### Lean Payload Evolution: Smart Minimal Payloads for 2027 {#smart-minimal-payloads-2027}

In traditional REST APIs, write operations (`POST` / `PATCH`) echo the full persisted document back to the client. In SveltyCMS, a typical document with default schema fields, audit metadata, and relations occupies **1.9 KB to 3.5 KB**. For high-throughput services, IoT ingest, and automated pipelines, parsing and transferring this discarded representation wastes over 95% of bandwidth and CPU cycles.

#### Two Activation Vectors: RFC 7240 Header or Query Projection

SveltyCMS provides zero-overhead minimal responses via two non-breaking mechanisms:

1. **RFC 7240 Standard Header**:
   ```http
   Prefer: return=minimal
   ```
2. **Smart URL Query Projection (2027 Wire Convenience)**:
   ```http
   POST /api/collections/articles?fields=_id
   PATCH /api/collections/articles/123?return=minimal
   POST /api/collections/articles?fields=none
   ```

#### Write Execution Paths

| Client Request Mode                            | DB Read-Back (`RETURNING` / `findOne`) | Wire Payload Size | Wire Payload Example         | Status Code                     |
| :--------------------------------------------- | :------------------------------------- | :---------------- | :--------------------------- | :------------------------------ |
| **Default** (no header/param)                  | Executed (re-reads merged entity)      | ~1.9 KB – 3.5 KB  | Full document representation | `201` (create) / `200` (update) |
| **Minimal Return** (`Prefer` or `?fields=_id`) | **Skipped** (`skipReturning: true`)    | **~43–70 Bytes**  | `{"_id":"0192847a-..."}`     | `201` (create) / `200` (update) |

By setting `skipReturning: true` directly in the database adapter call, the database skips the `RETURNING` clause or secondary `findOne` fetch, eliminating both DB serialization cost and network transfer overhead while remaining 100% backward-compatible with legacy REST consumers.

## Product-layer list & count (equal on all engines) {#product-layer-list--count-equal-on-all-engines}

> **Design rule:** Prefer cheaper correctness tiers by default. Exact cardinality is opt-in. Optimizations live in the shared `ICrudAdapter` contract — not engine-specific call sites — so SQLite, PostgreSQL, MariaDB, and MongoDB gain together.

### `findPage` + `hasMore` (limit + 1)

Admin and API list UIs no longer need `findMany` + `count` for “next page?” semantics.

```typescript
const page = await db.crud.findPage(
  "posts",
  { status: "publish" },
  {
    limit: 50,
    tenantId,
    total: "none", // default — no COUNT(*)
  },
);
// page.data = { items, hasMore, pageSize, nextCursor? }
```

| Option                         | Behavior                                                |
| ------------------------------ | ------------------------------------------------------- |
| `total: "none"` (default)      | Single query with `limit + 1`; `hasMore` from row count |
| `total: "exact"`               | Adds exact `count` after the page fetch                 |
| `total: "estimate"` / `"auto"` | Adds approximate total when safe (see count modes)      |

**Implementation:** `SqlAdapterCore.findPage`, `MongoCrudMethods.findPage`, pure helpers in `core/page-utils.ts`. Tenant guard forwards `findPage`. Schema proxy: `db.posts.findPage({ filter, limit, cursor })`.

### Keyset cursor (deep pages)

`nextCursor` is an opaque base64url payload (`id` + optional sort field/value + direction). Pass it as `options.cursor` on the next call:

- **Ignores `offset`** when cursor is set (avoids `OFFSET N` scans)
- Filter merge uses Mongo-style `$lt`/`$gt`/`$or`/`$and` — SQL `mapQuery` and Mongo both understand them
- Default sort when omitted: `{ _id: -1 }` for stable keyset order
- **Tiebreak follows the sort direction**: the `_id` tiebreak appended to a paginated `ORDER BY`/`sort()` runs in the same direction as the sort key it follows (`createdAt DESC` → `_id DESC`), so the composite stays monotonic and one index can serve it (a backward scan covers the same-direction keyset indexes); a mixed-direction composite (`createdAt DESC, _id ASC`) is served by no B-tree and forces a filesort / blocking `SORT` stage
- **Direction spellings are normalized per engine**: the wire form (`"asc"`/`"desc"`) and the Mongo-style numeric form (`1` ascending / `-1` descending, as emitted by `defaultPageSortOption`) produce the same clause everywhere — `normalizeSortDirection()` in `core/page-utils.ts` is the single definition
- Legacy plain `_id` strings still decode as cursors

When `total` is requested, **findMany and count run in parallel** (count still hits the 30s L1 cache).

### Unified `count(..., { mode })`

| Mode             | When                                | Semantic                                               |
| ---------------- | ----------------------------------- | ------------------------------------------------------ |
| `exact`          | Billing, RBAC, uniqueness           | True cardinality                                       |
| `estimate`       | Dashboards / badges when unfiltered | Engine stats / metadata                                |
| `auto` (default) | General                             | Estimate if **empty filter + no tenantId**; else exact |

### PostgreSQL raw-path identifier quoting fix (2026-08-11)

**Bug**: the PG adapter's raw `findById` and raw `UPDATE…RETURNING` paths interpolated the table name **unquoted** (`exec.unsafe(getTableName(table))`). ## Philosophy

SveltyCMS implements **best-practice performance patterns from day one**. Every feature is built with performance as a core requirement, not an afterthought. The 2027 allocation-floor work pushes the database layer to the practical limit of the current architecture (Drizzle ORM + DatabaseResult contract). Product-layer list/count contracts (above) reduce round-trips **before** that floor matters.

## 2027 Allocation-Floor Optimizations

### Row conversion & schema registration

**Schema-aware row conversion.** Instead of checking every row key against `DATE_FIELDS`/`JSON_FIELDS` Set lookups on every row read/write, table schemas are pre-computed once during table creation. Only known date and JSON columns are converted — eliminating per-row `Set.has()` calls and enabling targeted iteration.

```typescript
// Before: checks every key against Sets
for (const k in row) {
  if (DATE_FIELDS.has(k)) {
    /* convert date */
  } else if (JSON_FIELDS.has(k)) {
    /* parse JSON */
  }
  result[k] = row[k];
}

// After: only touches known columns
registerTableSchema("posts", ["_id", "title", "createdAt", "metadata"]);
// converts only "createdAt" (date) and "metadata" (JSON) — skips everything else
```

Registrations are **additive** — knowledge only grows: a later `registerTableSchema` call that includes materialized/boolean columns augments an earlier base-only registration (and a later partial registration never shrinks the maps). Both the physical (`collection_…`) and logical table names are registered so raw and Drizzle paths share the same schema knowledge.

**Canonical collection naming (2026-08-20).** All physical collection table/model names derive from **one** function — `normalizeCollectionTableName()` in `src/databases/core/collection-name.ts` (prefix-aware, hyphen-stripping, idempotent). Consumers: the SQL adapters' `getTable()`/`_warmTableRegistry()`/`createModel` cleanup, `createIndexes()` (DDL), `registerTableSchema()` variant keys, MongoDB's `normalizeCollectionName()`/`createModel()`/`deleteModel()`, the Local SDK, and API handlers. This closes two latent hyphenated-id mismatches: SQL `CREATE INDEX` previously targeted a phantom table name, and MongoDB previously registered two different Mongoose models (full-schema vs generic) for the same hyphenated collection.

**MariaDB double-parse isolation.** MariaDB's native JSON columns can double-encode. The double-parse loop is now opt-in (`mariaDoubleParseJson: true`) — PostgreSQL and SQLite paths never pay this cost.

### Prepared statements & caches

**SQLite INSERT/UPDATE templates (2026-08-23).** SQLite `rawInsertReturning` now matches PostgreSQL: one cached `INSERT … VALUES (?)` per table/column-set, **no `RETURNING *`**, row synthesized from bound values (CMS tables have no insert triggers). UPDATE SQL is cached per `(table, column-set, tenant clause, skipReturning)` so the SET list is not rebuilt on every PATCH.

**SQLite RETURNING cache.** The `insertMany` path caches whether `RETURNING` is supported per SQLite instance. Avoids repeated try/catch + logger.warn overhead in benchmarks and unsupported table scenarios.

**QueryBuilder list conversion (2026-08-23).** Admin collection lists use `queryBuilder().execute()`, not `crud.findMany`. That path registers the table schema and converts rows **in place** (same maps as `findMany`) so MariaDB/PostgreSQL/SQLite lists do not allocate a new object per row or walk unknown keys. As of 2026-10-06, `execute()` and `count()` compile equality filters on physical columns, a physical `ORDER BY`, and limit/offset into one cached SQL string and run it on the driver statement cache (postgres.js `prepare`, mysql2 `execute`, SQLite `prepare`). JSON search and multi-operator ranges stay on Drizzle; physical `OR` groups and `$and`-wrapped keyset filters compile too. The first paginated sort on a physical column other than `updatedAt` schedules a covering list index — `(tenantId, column, _id)` when the filter equals `tenantId`, otherwise `(column, _id)` — so `ORDER BY createdAt DESC, _id DESC` is an index scan. `SVELTY_LAZY_SORT_INDEXES=0` skips that index. `exists()` is `SELECT _id … LIMIT 1` (Mongo: `findOne` + `_id` projection) instead of `COUNT(*)` / `countDocuments`. Mongo `upsert` is one `findOneAndUpdate` with `upsert: true` — `_id` stays on the filter so `$setOnInsert` never carries it (Mongoose 9 rejects `_id` there).

### Allocation pooling

**Ring-buffer result pool.** All `BaseAdapter.wrap()` calls now use a 64-slot ring-buffer pool for `{ success, data }` result wrappers. Pooled slots are safe in single-threaded JS — callers consume results synchronously after `await`. Eliminates 100% of result wrapper allocations.

**Ring-buffer conditions array pool.** Filtered queries (`mapQuery`) reuse `conditions: SQL[]` arrays from a 32-slot ring-buffer pool instead of allocating `[]` each time. Arrays are cleared via `.length = 0` without deallocation.

**Pre-allocated meta object.** The `{ executionTime }` meta sub-object is pre-allocated once per adapter. `wrap()` mutates `this._meta.executionTime` instead of creating a new object per call.

### Hot-path bypasses

**GraphQL Yoga bypass for catalog/health (2026-08-23).** `contentSystemHealth` and `allCollections` are single-root in-memory queries. After auth, the GraphQL handler answers them without Yoga/JIT (field projection from the selection set). Shared parse cache so comment-busted response-cache keys still reuse the same `DocumentNode` for JIT on everything else.

**Automation event→flow index (2026-08-23).** `AutomationService` keeps a per-tenant `event → active event-triggered flows` Map, rebuilt on cache refresh, save, and delete. `handleEvent` does one Map lookup and returns immediately when nothing subscribes to the event — content mutations no longer scan every flow. An earlier SQLite micro-cache for every list shape was measured when a read was ~6 µs and did not move a REST request. The 2026-10-06 plan above is one prepared statement for the equality, order, and limit shape.

**Zero-tax SDK dispatcher.** Self-overwriting getters eliminate Proxy overhead after first access. Verified: **0.00% middleware tax** (LocalCMS is statistically identical to direct adapter calls).

### Fused Query Construction (SQL + MongoDB)

Both `mapQuery` implementations now build database conditions directly from user queries without intermediate IR (Intermediate Representation) objects. The old pattern (query → QueryIR → LogicalGroup → QueryCondition[] → SQL conditions) is replaced with a single fused walk.

- **SQL path** (`drizzle-sql-helpers.ts`): `addFilterConds` + `addSingleCondition` build `SQL[]` directly
- **Mongo path** (`mongodb/adapter-core.ts`): `addMongoConds` + `addMongoCondition` build filter objects directly
- **Eliminated**: QueryIR, LogicalGroup, QueryCondition[] intermediates (~3-5 objects per filtered query)
- **Eliminated**: All `Object.entries()` array allocations (replaced with `for...in`)

## Phase 1: Database Indexing & Optimization

**Status:** ✅ FULLY IMPLEMENTED
**Impact:** Exponential query speedup (O(n) → O(log n))

Index provisioning is **schema-driven inside `createModel`** — a collection's `indexed`/`unique` fields, its tenant-scoped sort indexes (`("tenantId", status, "updatedAt" DESC, "_id" DESC)`) and PostgreSQL's `jsonb_path_ops` GIN index for dynamic-field containment are created in the same call that creates the table. Dynamic **sort** fields get a lazy expression index on first use (`CREATE INDEX IF NOT EXISTS ((data->>'field'))`). MongoDB creates its compound/text indexes from the schema in `MongoCollectionMethods.createIndexes`. Multi-database support: MongoDB Compound/Text, SQL B-Tree.

### Covering-composite policy (shared by PostgreSQL, MariaDB, SQLite)

The covering composite `(tenantId, status, <col>, _id)` — the index that serves `WHERE tenantId=? AND status=? ORDER BY <col> DESC, _id DESC` without a sort node — is provisioned **only for declared query targets**: fields marked `indexed: true`, numeric fields (`number`/`integer`, the default `listFilterSort` sort target), and the `publishedAt` base column. Equality-lookup base columns (`collection`, `slug`, `locale`) and storage-only columns (`unique`, `materialize: true`) keep their single-column index (still filterable) but no covering twin. The predicate is `buildCompositeIndexColumns()` / `earnsCompositeIndex()` in `src/databases/core/drizzle-sql-helpers.ts`, consumed by all three SQL engines so the provisioned index set is identical; legacy twins for ineligible columns are dropped explicitly, following the `…_tenant_status_updated` twin-drop precedent. The default list order is unaffected — it is served by `…_tenant_status_updated_id`, which is always created.

Why: every extra index is maintained on **every** write. `updatedAt` is indexed and rewritten by each update, so PostgreSQL can never take the HOT path and inserts into all indexes of the table. Measured (PostgreSQL, 2 000-row batches across alternating orders, 3 vs 4 indexes): **+11–17 % per extra index** (≈ 0.7 µs/row/index); on the 113 k-row benchmark table the policy takes the set from 15 to 12 indexes.

**What this does and does not buy.** It is a write-amplification / WAL-volume reduction, not an HTTP-lane latency win: on Docker-on-Windows the update lane's `dbwrite` phase is 75–85 % durable-commit wait (single-row autocommit `UPDATE` 1.57–4.50 ms with `synchronous_commit=on` vs 0.31–0.43 ms with `off`; 200 rows in one transaction = 42–44 µs/row for all tuple+index work), so a single-digit-µs index saving is invisible there. Guarded by `tests/unit/databases/composite-index-policy.test.ts` and `Composite-index policy — {engine}` in `tests/integration/databases/dynamic-field-filter-index.test.ts` (green on SQLite and PostgreSQL).

## Read-Replica Splitting & Read-Your-Writes (RYW) Horizontal Scaling

Horizontal read scaling via `ReplicaRouterAdapter` offloads read traffic (`find*`, `count`, `aggregate`) across an arbitrary number of read-only replica nodes while steering all writes (`insert`, `update`, `delete`, `batch.*`) to the primary:

- **100% Read Offload**: When read replicas are active, 100% of non-transactional read traffic is served by replicas via configurable load balancing (`round-robin`, `least-connections`, `random`).
- **Guaranteed Read-Your-Writes (RYW) Consistency**: Tracks per-client write watermarks (`readYourWritesWindowMs`, default 2,000ms). When a client writes data, subsequent reads from that specific client route directly to the primary, guaranteeing fresh data and eliminating replication lag races.
- **Fail-Safe Circuit Breaker**: Each replica node monitors errors; nodes exceeding 3 consecutive errors enter a 15s cooldown. Queries automatically fail over to the primary database with zero caller errors.
- **Zero Overhead on Single Node**: When no replicas are configured, `createReplicaRouterAdapter` returns the primary adapter directly without any proxy layer or routing overhead.

### 🔌 Connection Pool Architecture & Keep-Warm Defaults (All 4 Adapters)

In real production workloads, traffic is rarely uniform — bursts and quiet periods alternate. In older versions or unoptimized setups, connection pools were configured with aggressive idle timeouts (e.g. 30s in PostgreSQL, 60s in MariaDB). Under fluctuating traffic, this caused recurring **connection storms**:

1. After 30–60 seconds of low traffic, connections were terminated by the client pool.
2. The next burst of incoming requests forced the adapter to establish dozens of fresh TCP handshakes, TLS negotiations, and authentication handshakes concurrently against the database server.
3. This resulted in observable tail-latency spikes (500ms–2000ms p99) and unnecessary CPU load on both the CMS node and the database server.

**SveltyCMS 2026-09 Hardening**:

- **PostgreSQL (`postgres` driver)**: `idle_timeout: 0` by default. Sockets remain connected and warm. Configurable via `DATABASE_IDLE_TIMEOUT` (in seconds).
- **MariaDB (`mysql2/promise` pool)**: `idleTimeout: 0` by default. Configurable via `MARIADB_IDLE_TIMEOUT` (in milliseconds).
- **MongoDB (`mongodb` driver)**: `maxIdleTimeMS: 0` by default. Sockets remain alive and ready. Configurable via `MONGODB_IDLE_TIMEOUT_MS`.
- **SQLite (`bun:sqlite` / `better-sqlite3`)**: Single-file direct memory engine; zero connection pool overhead, no TCP sockets, zero connection storm risk.

> [!NOTE]
> For serverless or short-lived container environments (e.g. AWS Lambda) where holding open idle connections could exhaust external database connection limits, operators can set `DATABASE_IDLE_TIMEOUT=30` or `MARIADB_IDLE_TIMEOUT=30000` via environment variables.

### 🚀 Core CMS Application Code Optimizations (Universal Across All 4 Adapters)

In addition to database-level session settings, SveltyCMS incorporates pure application-layer code optimizations in the core API dispatcher, schema validation engine, and audit pipeline. These zero-allocation optimizations apply **universally to all 4 database adapters (PostgreSQL, MariaDB, SQLite, MongoDB)** as well as core CMS database tables:

1. **Copy-On-Write Request Body Sanitization (`src/content/content-utils.ts`)**:
   - `prepareCollectionFields()` uses a single-pass Copy-On-Write pattern (sanitize + maxLength + null-row strip in one schema walk).
   - For 99% of normal write payloads, **zero shallow object copies (`{ ...data }`) are allocated**, eliminating memory churn before reaching any database adapter.

2. **Asynchronous Non-Blocking Microtask Audit Logger (`src/services/security/audit-service.ts`)**:
   - Uses static `node:crypto` imports during SSR module load and a serialized `chainLock` queue to guarantee cryptographic hash chain integrity under concurrent writes.
   - Database `after-insert` audit hooks operate via non-blocking microtasks (`this.log(...).catch(...)`).
   - Enables tamper-evident SHA-256 hash chaining in memory without delaying HTTP response latency.

3. **High-Efficiency Role & Permission Cache (`src/databases/auth/permissions.ts`)**:
   - Evaluates RBAC permissions using compiled `Uint32Array` role bitsets and 5-minute LRU permission caching.
   - Reuses mapped `roleIds` across cache reads and writes to eliminate duplicate array mapping allocations.

### High Performance Core vs Enterprise Compliance Mode (`AUDIT_CHAIN_SYNC`)

SveltyCMS supports two operational modes for audit logging and revision management:

1. **High Performance Core (Default: `AUDIT_CHAIN_SYNC=false`)**:
   - Database writes (`INSERT` / `UPDATE`) return **sub-5ms latencies** directly to the caller.

### Memory governor (runtime)

V8 does not hand committed pages back on its own: after a burst (seeding, bulk import, media upload) `heapUsed` can fall to a fraction of the RSS `docker stats` reports, and the process stays at its high-water mark until it is restarted. In a local probe on Node 24 (2026-09-21, single Windows host — not re-measured by the test suite) a 370 MB burst fell to 59 MB on the first full GC, a second pass freed the remaining external arenas, and **3 s of idle released nothing**.

The system watchdog therefore runs a governor (`src/services/system/memory-governor.ts`) on its own timer. It fires when any signal is over its threshold:

| Signal           | Threshold                                                                | Why it exists                                                                        |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **heap**         | `heapUsed / heap_size_limit > 0.7`                                       | Classic live-heap pressure                                                           |
| **live-set**     | `(heapUsed + external + arrayBuffers) / limit > 0.7`                     | HTTP body/buffer bursts keep `heapUsed` flat — a heap-only check never sees them     |
| **rss**          | `rss > 0.75 × cgroup limit`, else `1.25 × V8 heap limit`                 | The number that actually gets the container OOM-killed                               |
| **idle reclaim** | quiet loop, `rss > 192 MB`, and `rss > max(1.6 × floor, floor + 128 MB)` | Returns the process to its own low-water mark — nothing to do with a container limit |

The floor is the live set plus 64 MB of non-reclaimable runtime; it rises with a genuinely larger working set and ratchets down whenever a lower idle RSS is observed. `SVELTY_MEMORY_RSS_MB` overrides the derived RSS target in all cases — set it when the container has no cgroup limit and the derived `1.25 × heap limit` is too generous (that is the default when `process.constrainedMemory()` reports nothing).

A sweep runs an **async** major GC first (marking concurrent, off the request path), a **sync** pass only when the first one handed back less than 8 MB and the process is still over a threshold, and trims the response-cache L1 tiers only if the live heap is _still_ over the ratio — an RSS spike alone is not a reason to throw away turbo hits. The trim awaits the cache handle, so a pressured sweep during boot waits for the module instead of silently doing nothing. Cooldown starts at 5 s and doubles up to 2 minutes while sweeps stay unproductive, so a steady working set is not GC-thrashed.

| Env var                           | Default | Effect                                                                         |
| --------------------------------- | ------- | ------------------------------------------------------------------------------ |
| `SVELTY_MEMORY_TRIGGER_RATIO`     | `0.7`   | Heap / live-set share of the V8 heap limit that triggers a sweep               |
| `SVELTY_MEMORY_RSS_MB`            | derived | Explicit RSS ceiling; unset derives from the cgroup limit (else heap limit)    |
| `SVELTY_MEMORY_CHECK_MS`          | `2000`  | Governor tick — a burst tail is caught within seconds, not a minute            |
| `SVELTY_L1_MAX_MB`                | `64`    | Byte budget for the list-response L1 tier (entry counts alone do not bound it) |
| `SVELTY_L1_POINT_MAX_MB`          | `16`    | Byte budget for the point-read L1 tier                                         |
| `SVELTY_FILE_EXISTS_CACHE_MAX`    | `5000`  | Entry cap for the media storage existence-probe cache (LRU, per storage path)  |
| `SVELTY_FILE_EXISTS_CACHE_TTL_MS` | `10000` | TTL for a cached existence probe (positive or negative)                        |

**Native memory is not on this list.** SQLite in production is configured by the hardware profile: `PRAGMA cache_size=-256000` (256 MB page cache on a large host) and `PRAGMA mmap_size=536870912` (512 MB window). Both are process-resident, so on a memory-capped container they — not the JS heap — are what an RSS ceiling actually has to hold; `SQLITE_CACHE_SIZE` / `SQLITE_MMAP_SIZE` are the knobs, and a 3-minute soak measured the same +53 MB RSS climb with both of them minimised, i.e. the climb in that window is not SQLite's (see the soak evidence in [achievements-2026](../../project/achievements-2026.mdx)).

**Observing it:** every sweep logs one evidence line — `🧹 [Memory] pass 1/2 (rss) rss 389→286MB · heap 100→57MB · ext+ab 242→172MB · limit 4288MB · busy 88%` — which is what to correlate with `docker stats` after a seeding run. Give the container a real `--memory` limit (Node reads it via `process.constrainedMemory()`) or set `SVELTY_MEMORY_RSS_MB`; keep `--max-old-space-size` in line with it so V8's own limit and the cgroup agree. `--heapsnapshot-signal=USR2` gives a heap diff when a release still looks wrong.

### Module graph: what loads when

Caching a module graph is only a saving if the graph was _cut_ first — the registry caches what was used, and a process cannot predict a working set that was never separated from "everything". The current split, verified in the source:

| Chunk             | Contents                                                                                                             | When it is evaluated                                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Request chunk** | Read lane, write lane, session check, active adapter, security headers — statically imported                         | Process start; this is what a cached `findById` touches                                                                                                                                |
| **Widget chunks** | One loader per factory (`widgets/scanner.ts`, non-eager `import.meta.glob`); input/display stay lazy component loads | When a collection schema names the widget — the SDK resolves a schema, calls `widgetNamesOf()`, and loads only that set. The full catalog loads only when the admin widget store opens |
| **Background**    | Job queue, scheduler, outbox, watchdog, automation, telemetry, behavioral learner                                    | **Still static in `hooks.server.ts`** and started at READY — see below                                                                                                                 |

The widget side is also used predictively: `CacheWarmingService` reads the behavioral learner's hot collections, peeks their (already warm) schemas, and evaluates exactly the widget factories those collections name — so the first edit of a hot collection does not pay the chunk import. Nothing here loads the catalog.

**Why the background services are still in the request graph:** an earlier attempt to `await import()` them from the hook left their production exports `undefined` under Rolldown's cyclic-chunk initializers, so they were pinned as static imports. Moving them out for real needs a separate entry (`index.cjs` must not import it into the same process, or the modules are evaluated anyway) — scoped with its prerequisites in [roadmap-2026](../../project/roadmap-2026.mdx). Expect 30–80 MB resident and roughly 5–10% on `create` when it lands; cached reads stay at the HTTP floor either way, because they already do.

1. **Phase 1: Boot Statement Warm-Up (`src/databases/postgresql/statement-warmup.ts`)**
   - **Mechanism**: Executes 4 key probe shapes × 6 repetitions across connection pool workers at boot using impossible UUID sentinels and `LIMIT 0` reads.
   - **Impact**: Forces PostgreSQL's query planner to transition prepared statements from custom plans (0.36 ms) to cached generic plans (0.11 ms) before live traffic arrives.
   - **Control**: Toggleable via `SVELTY_PG_STATEMENT_WARMUP=0` (disabled) / `1` (enabled, default).

2. **Phase 2: Adaptive Write Coalescing (`src/databases/core/write-coalescer.ts`)**
   - **Mechanism**: Intercepts mutation requests (`insert`, `update`, `delete`, `upsert`) arriving within the same event-loop microtask tick and groups them into concurrent micro-batches with per-operation error isolation.
   - **Impact**: Reduces WAL sync contention and connection pool queue lockups during concurrency spikes (measured **361x throughput speedup** under 200 concurrent writes).
   - **Control**: Toggleable via `SVELTY_WRITE_COALESCING=0` (disabled) / `1` (enabled, default).

3. **Phase 3: Compiled Wire-Plane Projection (`src/databases/core/wire-descriptor.ts`)**
   - **Mechanism**: Pre-compiles database-native JSON construction statements (`jsonb_build_object` on PostgreSQL, `json_object` on SQLite, `JSON_OBJECT` on MariaDB, `$project` on MongoDB) cached via `WeakMap`.
   - **Impact**: Streams formatted JSON directly from database kernel to HTTP sockets, bypassing JS object hydration, intermediate DTO allocations, and runtime `JSON.stringify()`. Measured **27.8M compilations/sec (0.04 µs overhead)**.

4. **Phase 4: Canonical QueryIR AST (`src/databases/core/query-ir.ts`)**
   - **Mechanism**: Replaces string concatenation and dialect branching with an immutable AST query specification emitted directly into optimized dialect SQL and MongoDB pipelines.
   - **Impact**: Zero runtime regex or string parsing overhead (measured **3.26M queries/sec, 0.31 µs per compilation**).
