This page records what the source does, not what a settings screen or a prose doc promises. It was
built by reading the tree at `fix/enterprise-readiness-20261110` (`efa57c55e`). No test suite was run
(a write-path benchmark was active on the host); every statement below is a source citation, and every
"not found" is paired with the exact search that returned nothing.

Status vocabulary:

| Status                   | Meaning                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| **Implemented + tested** | Code path exists and a named test exercises the behaviour described.                          |
| **Implemented, no test** | Code path exists; no test asserts it.                                                         |
| **Partial**              | Code exists but a named part of the contract (validation, revocation, persistence) is absent. |
| **Not found**            | No code path exists. The search that proves it is given.                                      |

> [!IMPORTANT]
> The repository has an HTTP-mutation log and a separate database audit service. They are not the
> same thing and neither is transactional. Read [§3](#3-audit-logging) before relying on either for
> compliance evidence.

## 2. Where the identity code is NOT wired to audit

The audit subsystem is reachable only by explicit calls. These four modules contain **zero** audit
references (case-insensitive `grep -n -i 'audit'` on each file returned no lines):

| Module                                      | Consequence                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `src/routes/api/[...path]/handlers/auth.ts` | API login, logout, OIDC login/logout, SAML SSO, 2FA, role updates are unaudited.            |
| `src/routes/api/[...path]/handlers/scim.ts` | Every SCIM provision/deprovision/deprovision-failure is unaudited.                          |
| `src/databases/auth/saml-auth.ts`           | SSO authentication, JIT provisioning and IdP reconfiguration are unaudited.                 |
| `src/databases/auth/sso-session.ts`         | Provider configuration changes, RP-initiated, front- and back-channel logout are unaudited. |

The only identity audit call sites in the tree are:

- form login — `src/routes/login/auth.remote.ts:648-659` (fire-and-forget, `.catch()` swallows the failure)
- role matrix write — `src/services/sdk/namespaces/auth-namespace.ts:808-816`
- individual role create/update — `auth-namespace.ts:770-784`
- GDPR erasure — `src/services/security/gdpr-service.ts:241-248`

`src/routes/login/auth.remote.ts:1081-1165` (passkey login) contains no audit call either.

### 3.2 The outbox is not an outbox

`src/services/outbox/outbox-service.ts:18-24` states it directly: _"This is NOT a transactional outbox
— there is no atomic same-transaction write… a crash between the content commit and the queue flush can
drop the delivery intent."_ Enqueue is a synchronous in-memory push with a 25 ms debounce
(`:27-28,506-521`). Audit records do not use it at all; they use the separate buffer in
`audit-service.ts`.

**Net answer to "is the audit write atomic with the business change?"** No. Three independent writes
exist — the business row, the buffered audit row (`audit-service.ts:233-238`), the buffered outbox
event (`outbox-service.ts:213`) — sequenced after the fact, each with its own failure mode.

## 4. The five missing tests that matter most for data safety

Each is written as a failing-then-passing case: the "expected failure mode" is what the current code
does, so the test pins the bug before the fix.

### T1 — Deprovisioning must kill the session, not just the metadata

- **Precondition:** OIDC provider configured with a JWKS; user `u1` with one active session
  `sess-1` (`setSsoSessionMetadata("sess-1", {provider: "p1"}, "tenant-a")`); `db.auth.validateSession("sess-1")` returns `u1`.
- **Action:** `handleBackChannelLogout(validLogoutToken)` then re-validate `sess-1`; repeat the same
  sequence with `handleFrontChannelLogout(issuer, sid)` for the front-channel endpoint.
- **Expected failure mode (today):** `getSsoSessionMetadata("sess-1")` is `undefined`
  (`sso-session.ts:1122`) but `validateSession("sess-1")` still returns `u1`, and the session cookie
  still authenticates — a disabled IdP account keeps writing content for up to 24 h. The test must
  assert `validateSession === null` and a 401 on the next API call.
- **Why first:** it is the only gap where an attacker-supplied _or_ legitimate IdP event produces a
  false sense of termination. `tests/integration/auth/oidc-live.test.ts:311-314` currently locks in
  the weaker behaviour.

### T2 — `active: false` from SCIM must lock the account

- **Precondition:** SCIM bearer token for `tenant-a`; user `u2` created through SCIM; one live session
  and a valid session cookie.
- **Action:** `PATCH /api/scim/v2/Users/u2` with
  `{Operations:[{op:"replace", path:"active", value:false}]}`, then call an authenticated write
  endpoint with the existing cookie.
- **Expected failure mode (today):** the handler writes `isActive: false`
  (`scim-utils.ts:206`, applied at `scim.ts:181`), the per-request gate reads `user.blocked`
  (`handle-authentication.ts:707,766`) and finds it unset, so the write succeeds. Assert a 401/403 and
  a session row that is gone or `blocked`.

### T3 — Audit records must survive a mid-request crash

- **Precondition:** `AUDIT_CHAIN_SYNC` unset (default `false`, `audit-flags.ts:44`); DB adapter with a
  settable `failNextInsert`; audit table empty.
- **Action:** call `auditService.log(...)` for a privileged action (e.g. `USER_ROLE_CHANGED`), do
  **not** await a flush, and simulate process death (`vi.resetModules()` after clearing the module
  registry, or spawn a child that `process.exit(1)`s immediately after `log()` resolves); then boot a
  fresh service and query the table.
- **Expected failure mode (today):** `log()` resolves as soon as the entry is in the in-memory array
  (`audit-service.ts:421`), so the record is absent after the restart while the API reported success.
  The test must assert either the row exists, or that `log()` rejected — never "success, no row".
- **Companion assertion in the same test:** with the DB insert failing, after 201 queued entries the
  oldest are dropped silently (`:263-267`) — assert an explicit, observable drop counter rather than a
  `logger.warn`.

### T4 — The verifier must fail only when the chain is actually broken

- **Precondition:** write three entries through `auditService.log` with `AUDIT_CHAIN_SYNC=true`; no
  tampering.
- **Action:** call `auditChainService.verifyChain(tenantId)` — the exact call the UI makes
  (`audit-history.remote.ts:54`).
- **Expected failure mode (today):** every entry is reported as tampered, because `verifyChain` reads
  `entry.chainHash` (`audit-chain.ts:230`) while `auditService` writes `hash`
  (`audit-service.ts:418`) and `createLog` — the only writer of `chainHash` — is never called. Then
  delete one middle row and re-verify: the test must prove deletion is _also_ detected, which today it
  cannot be, because the first assertion already fails for the wrong reason.

### T5 — Auditing must not be switchable off by the actor it records

- **Precondition:** admin session; `DISABLE_AUDIT_LOGS` absent; one existing audit row.
- **Action:** as an admin, write the value `true` to the `DISABLE_AUDIT_LOGS` system setting, perform a
  privileged mutation (role change + user delete), then read the audit table.
- **Expected failure mode (today):** `audit-flags.ts:69-83` reads the key 5 s later and both pipelines
  short-circuit (`handle-audit-logging.ts:129,166`, `audit-service.ts:221-224,380,388`), so the
  mutation leaves no record and no marker that logging was off during that window. Also assert the
  second half: GDPR erasure must not remove the trail of the erased subject's privileged actions —
  `gdpr-service.ts:202-207` deletes every `audit_logs` row whose **`actorId` is the erased user**
  (i.e. exactly those actions), and the `DATA_DELETION` record written afterwards
  (`:241-248`) survives only because it is logged with `id: "system"`.
