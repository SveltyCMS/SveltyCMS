## 1. Workflow and approval enforcement

### 1.1 What the model actually is

There are **two independent status systems**, and they are not synchronised:

| System            | Values / shape                                                                                                               | Where                              |
| :---------------- | :--------------------------------------------------------------------------------------------------------------------------- | :--------------------------------- |
| Entry `status`    | `archive`, `draft`, `publish`, `unpublish`, `schedule`, `clone`, `delete` — **no `review` value**                            | `src/content/status.ts:14-22`      |
| Workflow instance | Free-form FSM states (`states[]`, `transitions[]`, `gatePublication`) owned by `workflow_definitions` / `workflow_instances` | `src/types/workflow-types.ts:6-59` |

A review workflow therefore lives **only** in the workflow tables. No code maps a workflow state onto `entry.status`: `transition()` writes the instance and the audit log (`src/services/background/workflow-service.ts:371-419`) and never touches the content row. Publishing is a separate write that is (conditionally) checked against the instance.

### 1.2 The single gate function and its call sites

`assertPublishAllowed()` (`src/services/background/workflow-service.ts:503-549`) is the whole approval mechanism:

- admins/super-admins short-circuit (`:509`);
- no definition, or `gatePublication !== true` → allow (`:512`);
- create-path call without `entryId` → always reject (`:514-520`);
- otherwise the instance must exist and sit in a state with `isFinal` (`:522-548`); a missing instance is lazily enrolled and the write rejected (`:526-539`).

## 2. Reverse proxy and session behaviour

### 2.1 Request-trust chain as implemented

1. `getClientIp()` reads the **transport** peer (`event.getClientAddress()`, `src/utils/hook-utils.ts:286-295`), then — only if that peer is in `TRUSTED_PROXIES` — reads forwarded headers in the order `cf-connecting-ip` → `x-real-ip` → first hop of `x-forwarded-for` (`:301-315`). Result is memoised on `locals.__clientIp` (`:282-284`, `:317`).
2. `TRUSTED_PROXIES` is parsed in `src/databases/config-state.ts:439-460` (`"all"`/`"*"` sentinel, comma string or array, cached against a config stamp).

## 4. The five most important missing tests for data safety

Each case is written to fail on today's code. Expected failure modes are the ones implied by the cited lines, not guesses.

### T1 — Bulk publish bypasses the publication gate

- **Target file:** `tests/integration/api/workflow-bulk-gate.test.ts` (new)
- **Precondition:** collection `posts` with a workflow definition where `gatePublication: true` and the entry's instance sits in a non-final state (`draft`). Editor user with `collections:update`, no admin. `plan.hasWorkflows` must be true (set the schema flag the gate reads, per `execution-plan.ts:79-84`).
- **Action:** `PATCH /api/collections/posts/bulk` with `[{ id, data: { status: "publish" } }]`; repeat with `POST /api/collections/posts/batch { action: "status", entryIds: [id], status: "publish" }`; repeat with `POST /api/collections/posts/bulk` carrying `status: "publish"` rows.
- **Expected behaviour (now implemented for bulk update):** `PATCH /api/collections/posts/bulk` and `POST /api/collections/posts/batch {action:"status"}` now call `assertPublishAllowed` per publishing row (`bulk-operations.ts:186-200`) and return `403 WORKFLOW_PUBLISH_GATE`. Bulk **create** (`POST /api/collections/posts/bulk` with `status: "publish"` rows) still inserts without the gate — that half of the test remains open.

### T2 — A workflow definition alone does not gate publishing

- **Target file:** `tests/integration/api/workflow-gate-reachability.test.ts` (new)
- **Precondition:** fresh database; a collection created through the normal collection-builder payload (no `workflow`, `hasWorkflow`, `reviewWorkflow` or `plugins: ["workflow"]` fields); `POST /api/workflows` with `gatePublication: true` and a non-final initial state.
- **Action:** as a non-admin editor, `POST /api/collections/posts` with `status: "publish"`, then `PATCH /api/collections/posts/:id { status: "publish" }`.
- **Expected failure mode:** both writes succeed and the row is published. The gate is guarded by `plan.hasWorkflows` (`collections-namespace.ts:957`, `:1207`), which is `false` because nothing writes the flag (`execution-plan.ts:79-84`; no writer found by `grep -rn "hasWorkflow\|reviewWorkflow" src`). The test should demand `403 WORKFLOW_PUBLISH_GATE` after saving a workflow — i.e. it encodes the invariant "a saved definition is enforced, or `saveWorkflow` refuses to save".

### T3 — Editing approved content republishes without re-review

- **Target file:** `tests/integration/api/workflow-stale-approval.test.ts` (new)
- **Precondition:** `gatePublication: true`; entry published through the workflow (instance in a final state); non-admin editor with `collections:update`.

- **Expected failure mode:** the public read returns the edited copy while the workflow instance is still in the final state — no transition, no re-review, no audit entry. Cause: gating only runs for an explicit publish (`collections-namespace.ts:1199-1207`), and `transition()`/`update()` never reset or re-open the instance (`workflow-service.ts:371-419`; `post-write.ts:280-307` initialises on create only). ### T4 — Scheduled transition and import paths write around the write lane
