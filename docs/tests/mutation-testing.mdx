# Mutation Testing — Security & Data-Integrity Seams

**North star:** a protected seam is _proven_ against semantic mutations, not just exercised by a
happy-path assertion. Line coverage says a seam ran; only a killed mutant proves a _change_ to it
is caught.

> [!IMPORTANT]
> **A 100 % score describes the seams in the config — not the security posture of the product.**
> See [Scope and blind spots](#scope-and-blind-spots). Absent code has no mutant.

---

## What the gate runs

| Command                          | Harness                       | Scope                                      |
| :------------------------------- | :---------------------------- | :----------------------------------------- |
| `bun run test:mutation`          | `scripts/test/mutate-core.ts` | 31 seams across 15 files (all targets)     |
| `bun run test:mutation:security` | same, `--security-only`       | 24 seams across 13 files (security subset) |

It runs **last** in `.githooks/pre-push` (`Mutation (changed seams)`) and in CI `04-unit`, after the
browser gate. `scripts/security/check-test-strength.ts` reads the resulting
`.mutation/report.json`; `bun run security:assurance` fails when a scored area drops below its floor.

### How it works

1. **Reads** the real source file and asserts the `find` fragment matches **exactly once**
   (a refactor that moves the seam fails loudly instead of mutating the wrong lines).
2. **Writes** the semantic mutant in place, backing up the original.
3. **Runs** only the unit files mapped to that seam (`tests:` on the entry).
4. **Restores** in `finally` (plus an exit handler and `git checkout -- <file>` as a last resort).
   A target with uncommitted changes is **refused** (`exiting 3`) — never mutate a dirty tree.

Each mutant must be **killed** (the mapped suite fails). A surviving mutant or an invalid `find`
fails the gate; an "invalid" mutant means the config is stale and must be updated in the same
change that moved the seam.

### Why not StrykerJS?

Stryker (`@stryker-mutator/vitest-runner@10`) hardcodes `pool: "threads"`, while this project
requires `pool: "forks"` because several unit tests call `process.chdir()`. The dry run failed with
`process.chdir() is not supported in workers`, so the self-contained harness replaced it.

## Scope and blind spots

Mutation testing proves the **mechanism** inside a scored function. It cannot prove the
**composition** around it. Four limits, stated plainly:

| Blind spot                            | Why                                                                                                                                                                                                                                                   | Where the gap is covered instead                                                                                                                        |
| :------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- | ---------------------------------------------------------------- |
| **Absent code has no mutant**         | A missing check, an incomplete denylist entry, or a field never read is not "changed by a mutant" — the code is correct as written. `stripPrivilegedUserFields` at 100 % validates the stripping loop, not that the list names every sensitive field. | Denylist/allowlist completeness is a review concern; the threat model records the field set (`docs/reference/security/threat-models/auth-session.mdx`). |
| **Helper score ≠ call-site coverage** | A route that never invokes the sanitizer scores green, because the mutation only runs the mapped unit file.                                                                                                                                           | `bun run test:security`, the hook suites and the E2E contracts exercise invocation.                                                                     |
| **Curated mutants, not operators**    | The set is deliberately semantic (one per documented regression class); it is not exhaustive `&&`/`                                                                                                                                                   |                                                                                                                                                         | `/boundary coverage. | New seams are added only with a regression they pin (see below). |
| **Config scope**                      | Targets live in `src/utils/**`, `src/databases/**`, `src/services/sdk/namespaces/collections/write-pipeline.ts` and one route handler (`handlers/tokens.ts`). `src/hooks/**` and other `src/routes/**` handlers are **not** in the mutation set.      | Hook behaviour is covered by `tests/unit/hooks/**` and the E2E gates.                                                                                   |

### Composition coverage (what proves the wiring)

| Control                                                                            | Scored mutation?              | Invocation evidence                                                                                                                                                                                 |
| :--------------------------------------------------------------------------------- | :---------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sanitizeClientUserAttributePatch` (privileged strip + deep `__proto__`/`$` guard) | helper is scored              | `handlers/auth.ts:1089` (create), `src/utils/server/user-attribute-update.server.ts:124` (self-service and admin patch)                                                                             |
| `sanitizeMongoQuery`                                                               | scored                        | `src/databases/mongodb/adapter-core.ts:526` (query results). **Not** applied to the user PATCH path — that path is guarded by the attribute policy above.                                           |
| `/files/[...path]` traversal / tenant / global-admin gate                          | route is not scored           | `tests/unit/hooks/file-server-tenant.test.ts` pins the decision table, including "non-admin with `tenantId: global` is rejected".                                                                   |
| `VITE_TEST_MODE` production gate                                                   | hook is not scored            | `tests/unit/hooks/authorization-test-mode-gate.test.ts` asserts an unauthenticated `/api` request still returns 401 when `NODE_ENV=production` and `VITE_TEST_MODE=true` without `TEST_API_SECRET`. |
| `access: "public" \| "private"` on media                                           | **no check exists to mutate** | Recorded as a known residual in `docs/reference/security/threat-models/media-files.mdx`; the serving route authorizes on tenant path plus opt-in signed URLs.                                       |

The lesson from the last audit: a green mutation score on pure helpers says nothing about whether
a route reads a field, guards a branch, or calls the helper at all. When a security finding is
about wiring, add the assertion to the route/hook suite **and** a seam to the config only if the
control is a pure function.

## Interpreting the score

- **Killed** — the mutant changed behaviour and the mapped invariant failed (the desired outcome).
- **Survived** — behaviour changed but the invariant held; the gate fails and prints the seam id.
- **Invalid** — the `find` text no longer matches exactly once; the config is stale. Fix the seam,
  never delete the entry silently.

Mutation score = `killed ÷ total × 100`. `bun run security:assurance` enforces per-area floors, and
`--require-mutation` makes a missing report fail instead of skip.

## Adding a seam

1. Add a `Mutation` entry to `MUTATIONS` (data-integrity) or `SECURITY_TARGETS` (security) in
   `scripts/test/mutate-core.ts`.
2. Provide an exact-once `find`/`replace` pair and the `tests` array that must fail.
3. Prefer a segment that encodes a documented regression class — not a random operator.
4. Re-run `bun run test:mutation` and confirm the score stays at the baseline (or document the
   surviving mutant with the reason).

> [!NOTE]
> `tests/mutation/seam-mutation.test.ts` (the original 9-mutant seam harness) is still in the tree
> but is **not referenced** by any script, hook or CI job — `test:mutation` runs
> `scripts/test/mutate-core.ts`. Keep it in sync or delete it; do not cite its score as the gate's.
