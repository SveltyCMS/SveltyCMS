# Media Pipeline Plan (2026)

> **Status: plan + partially shipped.** What already shipped is listed in [§3](#3-status); everything else is scheduled work, not a description of current behaviour. Numbers are self-measured on SQLite, single host, 2026-09-22 unless stated otherwise.

Shipped so far: the on-demand delivery transform, the dedupe-before-generation order (#2) and the ladder clamp / no-redundant-write rules (#3), both with registered benchmark rows. Still open: the pipeline collapse (#1), disk reclaim (#4), and background precompilation.

## 1. Principles

1. **Derivative-first internals.** Every UI surface — gallery, picker, details preview, watermark picker, widget preview — works with a derivative. The byte-exact original is reserved for the image editor, explicit downloads, and archival actions. Today's audit found that rule followed by the gallery but violated by four surfaces, and one `srcset`-capable component (`src/components/ui/image.svelte`) with zero importers.
2. **Never do heavy work in the request that the user is waiting for.** Upload/save returns after the original plus metadata. Everything else — extra sizes, formats, watermarks, focal-point crops — is generated by a background job, idempotently and coalesced. "SIZES" is operator-defined, so it must never be paid for synchronously.
3. **Only generate what is asked for.** An on-demand transform endpoint (shipped, [§3](#3-status)) serves the requested width/format from cache and generates once on miss; the precompiler fills the gaps for what the frontend predictably requests.
4. **Fit the resource to the job.** Delivery must not buffer originals in RAM, must not push bytes through Node when an object store/CDN can serve them, and must not encode the same image twice. Decode once, encode the requested set, cache, and stream.
5. **Frontend correctness is part of the pipeline.** Watermark and focal-point data belong to the asset, so the delivered image is already the right crop and the right treatment — not something the browser has to fix with CSS.

## 2. Target architecture

```
upload ──► original stored (streamed) + metadata (w/h/hash/mime)
           │
           ├─► media record: watermark refs, focal point, SIZES preset set
           │
           └─► background job (idempotent, coalesced, rate-limited)
                 ├─ variants for operator-defined SIZES (ladder-clamped)
                 ├─ watermarked variants (pre-rendered, not per-request)
                 └─ derived metadata (placeholder, dominant colour)

delivery  /files/<tenant>/…?w=&h=&q=&fmt=   ──► cache hit → stream
                                            └─ miss → single-flight encode → save → stream
                                            └─ ineligible (SVG/animated/too large) → stream original

frontend  GraphQL/REST returns the variant ladder for the asset
          + watermark state + focal point ⇒ srcset/sizes are derived, not guessed
```

Key decisions:

- **Two caches, one layout.** Variants and on-demand transforms share `{tenant}/{hash}/variants/…` via `src/services/media/image-variant-storage.ts`. One layout means deletion and GC can be correct for both.
- **Ladder-clamped dimensions.** Requests snap to a fixed width ladder and quality band (see the transform section in [Media System](/docs/reference/architecture/media-system.mdx)); arbitrary sizes are rejected rather than cached, which bounds disk and decode memory.
- **Watermarks are pre-rendered.** A delivery-time composite would re-encode on every cold miss; pre-rendering per (`variant`, `watermark`) keeps delivery a file read and turns the cost into disk, which is the cheaper resource here. Focal-point crops stay delivery-time, because they are a crop of an existing variant and cost no encode when the crop is expressed via `object-position`.
- **SIZES is operator data, not code.** Presets are validated against the ladder, versioned on the media record, and backfilled by the background job so an operator can add a size later without touching uploads.

### P1 — CPU and disk (the bulk of the win)

**#2 Dedupe before derivative generation** — **shipped** (2026-09-22, see the table above). The content-hash lookup now runs before any derivative work, so a duplicate upload performs zero encodes; the row's original/derivative files are verified first and repaired in place when a GC sweep removed them (never served as dead URLs). Acceptance met: duplicate upload = 0 encodes, measured as `0/5` rewritten files against the `W/"size-mtime"` ETags.

**#3 Never upscale** — **shipped** (2026-09-22, see the table above). `saveResized` filters the ladder by the decoded source width and backstops it with `withoutEnlargement`, so no variant is ever written larger than its source. Acceptance met: a 400 px icon now writes one step (2 files, 600 B) instead of four (8 files, 16,984 B).

**#1 Collapse the two derivative pipelines.** Today an upload runs `saveResized` (4 sizes + WebP sidecars) _and_ a deferred `processImageWithPresets(["thumbnail","card","default"])` that re-reads the whole original — up to ~18 encodes and ~17 files per image (~2.2–3.5× the original's bytes), 12 encodes concurrent. Target: one pipeline, one layout, one encode per (`variant`, `format`), driven by the operator's SIZES. Acceptance: files-per-image and encodes-per-image drop at or below the SIZES count; existing derivative URLs keep resolving (or are transparently re-derived). The new fan-out rows report both halves (`ladder / total` files per image) so the second pipeline stays visible until it is collapsed.

**#4 Reclaim disk.** `remove()` unlinks files, not directories, so deleted media leave originals and variants behind; the storage dashboard sums the DB `size` column (originals only) and therefore under-reports real disk. Target: directory-aware removal, a derivative-GC/orphan sweep job (idempotent, dry-run first, tenant-scoped, respecting the published-reference gate), and analytics that report physical bytes. #2's file verification is the safety net that keeps a reclaimed derivative from being served as a broken URL: the next upload of those bytes repairs the row instead.

### P2 — delivery and content

- **Background precompilation of SIZES**, including newly added presets, with progress visible in the job queue and no request-path fallback to synchronous generation.
- **Watermark + focal point as first-class asset data**, exposed through the REST/GraphQL payloads so a consumer can build `srcset` from the variant ladder and the correct crop without guessing.
- **Adopt `<Image>` across widgets** (`media-upload`, galleries, SEO/OG tags), replacing ad-hoc `<img>` where a derivative exists.
- **True streaming upload**: the multipart parser already streams, but its consumer buffers the file into `chunks[]` before writing; piping through a hashing transform removes the double buffer and the peak RSS.
- **Metadata probes via ranged reads** instead of reading the whole file for a dimension check.

## 4. Measurement plan

The audit's blunt finding: **no registered benchmark currently counts derivative files, encoded bytes, or duplicate-upload cost**, and the old `HTTP: Asset Stream (Thumbnail)` row fetched `?w=300&h=200&q=80` while nothing honoured those parameters — it measured the original. That row is now `HTTP: On-Demand Transform (cached 320px WebP)` and measures a real cached variant.

Rows to add (registered in `scripts/benchmark-matrix/benchmark-scripts.ts` — the matrix runs the _file_, `exportResult()` keys each trend series on the row `name`):

1. **Derivative fan-out** — **shipped (2026-09-22)**: `Media: Derivative Fan-Out (1920px source)` and `Media: Derivative Fan-Out (400px source)` in `tests/benchmarks/media-performance.test.ts`. Each row uploads a fresh image per timed iteration, then counts the files and bytes its response advertises (the ladder `saveResized` wrote) plus the files physically present in the sandbox (`ladder / total`, so the second pipeline stays visible), and fails the row when a variant exceeds its source width, when a sub-ladder source writes more files than `SIZES`, or when the 400 px source writes anything but the `thumbnail` step. Exported: `media.derivatives.*_per_image`, `media.derivatives.sizes_configured`.
2. **Duplicate upload** — **shipped (2026-09-22)**: `Media: Duplicate Upload (identical bytes)` (24 iterations × 2 runs). It primes one asset, snapshots every `{rel, size, mtimeMs}` the asset owns, re-uploads the identical bytes each iteration (asserting the same record id comes back) and re-snapshots: any difference is a rewrite, so `0` rewrites is the encode count. Exported: `media.duplicate.latency_avg_ms`, `media.duplicate.latency_p95_ms`, `media.duplicate.rewrites`.
3. **Cached transform p95** — already covered by the renamed row; add a cold-miss iteration so first-hit cost is visible separately from steady state.
4. **Upload RSS at 4c** — peak `rssDelta` for 1–10 MB images (falsifies the streaming work).
5. **Variant GC** — integration assertion that deleting media leaves no files behind (falsifies #4), following the create → delete → assert-storage-empty → cleanup control-map rule.

Ledger note: renaming a benchmark row starts a new trend series (`exportResult()` keys on `r.name`). Rows 1–2 above are new series by definition — the generated ledgers pick them up on the next full matrix run, not before. The counts themselves are also written into the ledger's run summary table (`Derivative fan-out … files`, `Derivative bytes …`, `Duplicate upload latency (0 rewrites)`).

## 5. Constraints that do not bend

Tenant scoping on every path and cache key; `sanitizeSvg` stays buffer-and-sanitize (never pure-stream) and SVG is excluded from raster transforms; `validateEgressUrl` + `safeFetch` for remote fetches; media permissions unchanged (`media:write` upload, `media:delete` delete); ladder clamps and `MAX_OUTPUT_DIMENSION` bound every generated dimension; single-flight plus the concurrency cap bound aggregate decode memory; signed-URL and tenant gates run **before** any transform work; no direct database access outside adapters.

## 6. Open questions

- Do watermarked variants get their own cache dimension (`{hash}/variants/wm-…`) or a separate tree? The former keeps one GC path; the latter keeps the unwatermarked ladder clean for public delivery.
- Should SIZES changes re-derive lazily on request (first hit pays) or strictly in the background (a window where the UI falls back to the next-largest variant exists)?
- `AGENTS.md` §6.19 mandates an `invalidateMediaUrlCache()` helper that does not exist; today only a `storageType` change rebuilds the storage adapter, so bucket/region/key edits keep serving stale URLs for up to 5 minutes. Fix alongside #4.
