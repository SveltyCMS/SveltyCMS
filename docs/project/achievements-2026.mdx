## 1. Introduction: The Post-Monolithic Era of Content Management

The content management system (CMS) landscape of 2026 is defined by a rigorous bifurcation between legacy monolithic architectures and modern, composable, headless solutions. As enterprises increasingly demand sub-millisecond latency, edge-ready deployment, and "developer-first" ergonomics, the market has opened for frameworks that leverage the compilation-centric performance of next-generation JavaScript libraries.

To accurately assess SveltyCMS, one must establish the baseline for SOTA technology in the current year. The benchmarks for 2026 include:

- **Zero-Runtime Overhead:** The shift away from heavy client-side JavaScript bundles toward compiled, lightweight output.
- **Ultra-Fast Developer Feedback:** Sub-1.2s Hot Module Replacement (HMR) for content structure changes, a 60% improvement over legacy patterns.
- **Native Svelte 5 UI Library (March 2026):** Zero-dependency, native Svelte 5 UI architecture, achieving <150 requests per page and solving the "ESM Storm" overhead.

  - **Zero-Warning Codebase:** Automated and manual audit cleared all 84 legacy warnings.

  - **True Database Agnosticism:** The ability to run on NoSQL (for scale), SQL (for relations), or Embedded DBs (for edge) without code changes.

- **Edge Compatibility:** The ability to deploy logic and content delivery to the network edge (e.g., Cloudflare Workers, Vercel Edge).

This report describes **self-measured** SveltyCMS behavior and **publicly documented** competitor capabilities as of mid-2026. It does **not** claim global ranking, external security certification, or same-harness superiority over all commercial CMS products.

## 2. The Architectural Foundation: SvelteKit and the Compiler Paradigm

### 2.1 The "No-Runtime" Advantage

SveltyCMS leverages Svelte's compiler to generate highly optimized vanilla JavaScript during the build process.

- **Middleware pipeline (April 2026, self-measured):** Consolidated security handlers and `/api` fast-paths; documented **~71% reduction** in hook overhead on the measured path (**~12 µs p95** micro-bench — not full HTTP E2E).
- **API fast-path skips:** Omitting locale/theme/content-init on pure API routes saves on the order of **tens of µs** per request when those hooks would otherwise run (depends on path and cache state).
- **Throughput:** REST/dispatcher benches have recorded **high thousands–~14k+ RPS** on specific SQLite/local scenarios. **Not** a claim of global product speed leadership; networked adapters and full auth stacks are lower.

### 2.2 Performance & Security Infrastructure (New)

In March 2026, SveltyCMS implemented several enterprise-grade infrastructure optimizations:

- **Single-Trip Mutations:** Standardized `.returning()` (SQL) and `returnDocument: 'after'` (Mongo) across all adapters, eliminating redundant `SELECT` queries and reducing mutation latency by **~40%**.
- **Prepared / hot-path SQL (April 2026):** Cached prepared statements and related hot-path work on SQLite, PostgreSQL, and MariaDB reduce per-query compile overhead. **Sub-ms** reads are typical on **embedded SQLite** under our harness; networked SQL still pays RTT (**~0.5–2 ms** class on local Docker, 2026-08-04).
- **Memory Stability & Allocation Efficiency (April 2026):** Resolved significant allocation overhead in the `LocalCMS` SDK by consolidating transient caches into a shared `static` LRU engine. This refactor neutralized a 524 MB/min memory leak, achieving a **STABLE** rating with < 1MB/min growth under sustained 3,400+ RPS loads.

- **Negative Caching & Bloom Filter Protection:** Implemented a high-performance negative caching engine with an in-memory Bloom filter to track missing keys/documents. When a 404 cache miss is recorded, subsequent requests for the same missing key are resolved immediately in the current microtask tick, bypassing the database driver.

  Negative cache / Bloom miss path is **orders of magnitude** faster than a full DB miss on repeated absent keys (self-measured hot-miss micro-benches). It **reduces** miss storms; it does not “immunize” the system against all DoS classes (rate limits, body limits, and ops still apply).

- **Zero-Tax LocalCMS SDK Bridge:** Hardened the `LocalCMS` server-to-server bridge to bypass SvelteKit's HTTP middleware pipelines entirely. Combined with hot-swappable getter structures and microtask batching, this achieves internal query resolution in **<0.05ms** for server-side loading and internal API interactions with 0% runtime overhead.
- **Enterprise Redis L2 Cache Optimization (October 2026, self-measured):**
  - **TCP Socket Performance (`TCP_NODELAY` + Keep-Alive)**: Eliminated Nagle packet coalescing delays on small JSON payloads (<1.5KB) by pinning `noDelay: true` and `keepAlive: 5000` on the Redis L2 connection pool, suppressing 5–40ms tail latency spikes.
  - **Non-Blocking Evictions (`UNLINK`)**: Migrated cache invalidations and tag set drops from blocking `DEL` to asynchronous `UNLINK` executed inside `multi.exec()` batches, preventing Redis main-thread stalls during high-concurrency collection updates.
  - **Batch `mGet` Relation Probing**: Wired bulk Redis `mGet` lookups into `populate-resolver.ts` to resolve missing relational entity IDs in a single round-trip before issuing SQL/NoSQL `findMany` queries.
  - **Zero-Dependency Optionality**: Maintained strict architectural optionality — Redis remains 100% optional, seamlessly falling back to in-memory L1 cache with sub-µs hits when disabled.
- **Active Driver Validation (Anti-False Positive):** Implemented mandatory `SELECT 1` verification in the MariaDB and PostgreSQL adapters. This ensures that the Setup Wizard provides immediate, clear feedback for missing or incorrect credentials, eliminating "lazy connection" false positives found in legacy ORM implementations.
- **Micro-Telemetry:** Native per-operation timing (`performance.now()`) is bubbled up from the DB adapter to the API `meta` field, providing high-resolution observability without external dependencies.

- **Automated Bottleneck Detection: Heap Stability, Pool Contention & P95/P99 Variance (2026-09-26):**
  - **Heap Stability Regression Guard** (`tests/unit/benchmarks/heap-stability.test.ts`): Three automated tests that fail fast when a code change causes unbounded heap growth: (1) 1 k-doc transformation burst asserts <25 MB retained delta post-GC; (2) 3-burst asymptotic leak check asserts <15 MB gradient across 500-doc waves — catches commitment-ratchet leaks that only converge over many rounds; (3) 256-item LRU eviction cap asserts <10 MB post-GC after 2,000 inserts of 8 KB payloads, matching the internal `BoundedCache` contract.
  - **Connection Pool & Mutex Contention Test** (`tests/integration/databases/pool-contention.test.ts`): Fires 20 concurrent background-worker-pattern tasks (outbox/audit/status-poll simulation) against 20 concurrent foreground CRUD writes and asserts: zero deadlocks, all 40 operations succeed, sub-50 ms post-contention query latency. Runs on SQLite locally, switches to PostgreSQL in CI via `currentDbType()`.
  - **P95/P99 Latency Variance Report** (`scripts/verify-benchmark-local.ts`): `generateLatencyVarianceReport(db)` grades the **last recorded** `competitive-workload-replica` run — rows selected by `testFile` and grouped by `runId`, never by filename — using the run's own **recorded** p50/p99 percentiles, the sample count behind them, and the absolute tail excess (`p99 − p50`). Each workload is classified `EXCELLENT` (<2× tail ratio) / `ACCEPTABLE` (≤3×) / `WATCH` (≤4.5×) / `HIGH_VARIANCE` (>4.5×); a row whose percentiles are absent, or backed by fewer than 100 samples (where “p99” is the maximum), is reported `UNMEASURED` with the reason instead of an estimated band. Aggregate rows (p50 = 0 ms, e.g. the seed burst) are listed as excluded, not as unmeasured, so `--strict` stays passable. `printLatencyVarianceReport()` renders the table (naming the graded run and its age) and `latencyVariancePasses()` is the strict verdict — a 🔴 tail or an unmeasured row fails it, 🟡/🔵 stay informational. **Superseded** (see §3.34): an earlier revision reconstructed p50/p99 from `avg`/`p95`/`cv` when the JSON lacked them and graded those estimates, and read ten hardcoded filenames from a metric-naming scheme the harness had stopped writing.
  - **Background Worker Stability** (`src/services/background/background-runtime-env.ts`): The standalone background worker was crashing and restarting in production because its esbuild bundle could not resolve `$app/env` (a SvelteKit virtual module). The fix: a lightweight runtime replacement (`browser=false`, `building=false`, `dev=NODE_ENV!==production`, `version=npm_package_version`) aliased in vite.config.ts so the worker never tries to load SvelteKit's virtual module loader. A companion esbuild plugin now strips TypeScript and compiles `.svelte.ts` rune modules (`$state`/`$derived`) inside the bundle so runes never leak into the Node child as undefined globals. Verified in `tests/unit/services/background-supervisor.test.ts`.
  - **RFC 7240 `Prefer: return=minimal` Fast Path (create + update)**: `handleCollectionCreate` and `handleCollectionUpdate` now detect the `Prefer: return=minimal` request header (or `?return=minimal` query param) and pass `skipReturning: true` to the adapter, then return a lean `{"_id":"..."}` response (~70 B) instead of the full merged document (~3.5 KB). Removes the full `RETURNING *` PostgreSQL round-trip on the happy path for callers that only need confirmation. Measured: update +4.3% RPS paired median on PostgreSQL 5k docs 8c.
  - **PostgreSQL Schema Migration Guard** (`adapter-core.ts`): `addedColumns` Set tracks which columns were actually `ADD COLUMN`ed in the current migration run. The subsequent `CREATE INDEX` loop now skips columns that already had indexes — eliminates redundant `CREATE INDEX IF NOT EXISTS` calls on large schemas with many existing materialized fields.
  - Tests: `tests/unit/benchmarks/heap-stability.test.ts` (3) · `tests/integration/databases/pool-contention.test.ts` (2) · `tests/unit/services/background-supervisor.test.ts` (5, extended). Pre-commit gate: 6/6 checks pass in 2 m 2 s.

Physical adapters store only ciphertext; L1/L2 caches keep ciphertext (decrypt clones on the way out). Filter/sort on encrypted fields fail closed (`ENCRYPTED_FIELD_NOT_QUERYABLE`). Unique indexes and SQL materialization are skipped. Tests: `tests/unit/utils/field-encryption.test.ts`, `tests/unit/services/field-encryption-pipeline.test.ts`. ### 2.3 The Typed Widget Revolution (March 2026)

One of the most significant architectural leaps in 2026 was the migration of the "Three Pillars" widget system from string-based paths to **Type-Safe Component Loaders**.

- **The Problem:** Legacy CMS architectures (including early SveltyCMS) relied on strings like `inputComponentPath: './MyWidget.svelte'`. This prevented IDE refactoring, required giant `import.meta.glob` scans, and led to runtime "module not found" errors.
- **The Solution:** Redesigned the `createWidget` factory to accept typed `ComponentLoader` closures: `() => import('./input.svelte')`.
- **Result:**
  - **Zero Runtime Surprises:** Broken paths are caught at compile-time by TypeScript and Svelte Check.
  - **Perfect Tree-Shaking:** Vite no longer bundles unused widgets; only the components for enabled widgets are loaded.
  - **AI Integrity:** The `jsonRender` catalog validates referenced components at load time to fail closed on missing widgets (not a cryptographic proof system).

#### Understanding Executive Latency Uniformity Across Adapters

It is entirely normal and expected for raw CRUD execution matrices to look nearly identical for individual operations within a single database dialect (e.g., PostgreSQL `FIND ONE` at ~0.85ms vs `UPDATE` at ~2.15ms across runs). This occurs because:

1. **Network RTT & Loopback IPC Overhead**: Under local containerized testing (Docker), loopback socket traversal and TCP handshake serialization impose a fixed **0.4–0.8ms latency floor** regardless of query complexity.
2. **Standardized Drizzle SQL Generation**: The unified Drizzle AST compiler emits identical SQL query structures for single-record lookups across all relational adapters.
3. **Hardware Engine Isolation**: Below the `hooks.server.ts` middleware pipeline, raw adapter performance reflects the underlying database engine's storage locks (e.g. WiredTiger in Mongo, InnoDB in MariaDB, WAL in SQLite).

### 3.24 September 2026 — Bounded caches, exact L1 accounting, batch seed lane

Three separate findings from a soak/seeding/CPU pass, each with its own measurement (`4f3216920` + this change, SQLite, production-parity standalone benchmarks, shared 24-core host):

- **The media storage existence cache is bounded now (was an unbounded `Map`).** `src/utils/media/media-storage.server.ts` cached every storage `exists()` probe — positive and negative — in a `Map` with a 10 s TTL and **no cap and no eviction order**, so its size grew with the number of distinct media paths a process ever probed. - **The response-cache L1 byte budgets did not bind — the counters drifted on every path.** `src/services/cache/response-cache.ts` maintains `l1Bytes`/`pointL1Bytes` per tier; the L2-refill paths (`get()`/`getAsync()`) _inserted without accounting_ and `invalidate`/`invalidateAll`/doc-scoped drops/TTL expiry _deleted without decrementing_. ## 5. Phase 3: The Enterprise Leap (Q2-Q3 2026) ✅ COMPLETE

To cement its position as the undisputed category leader against platforms like Payload CMS, SveltyCMS is deploying three critical architectural features that transform it from a high-performance engine into a fully-fledged enterprise application platform.

### 5.1 Database-Backed Background Jobs Queue

- **The Gap:** Edge and serverless functions (like Vercel) time out during heavy operations (e.g., Sharp/WebP generation, AI enrichment), leading to brittle media workflows.
- **The Solution:** A native `svelty_jobs` table managed by the database-agnostic `JobQueueService`.
- **Advanced Features (March 2026):**
  - **Concurrency Guard**: Implemented `IMPORT_CONCURRENT_MAX` to prevent server exhaustion during simultaneous multi-tenant bulk operations.
  - **Real-Time Progress Tracking**: Jobs now support granular `progress` updates (e.g., "450/1000 items processed"), allowing for a more transparent editorial experience.
  - **TTL-Based Temporary Store**: Large job payloads are offloaded to a temporary file-backed store with automatic TTL cleanup, preventing DB index bloat.
- **Impact:** Heavy workloads are offloaded to a persistent polling worker (or CRON fallback), eliminating front-end blocking and save-failures entirely. This is the cornerstone of enterprise stability.

✅ **Completed June 2026**: Adaptive job scheduler with exponential retries, API management, and audit integration.

### 5.2 The Zero-Latency "Local SDK"

- **The Gap:** Fetching content via HTTP within the same SvelteKit runtime adds unnecessary serialization overhead.
- **The Solution:** Injected a formal, typed `cms` instance into `event.locals` via middleware.
- **Impact:** Developers can query the database directly in `+page.server.ts` (`await locals.cms.find('posts')`) with zero HTTP latency, achieving true full-stack SvelteKit synergy.

### 5.3 Virtual "Join" Fields

- **The Gap:** Traditional relational graphs cause either N+1 query performance deaths or massive over-fetching. Traditional databases also struggle with "inverse" relationships (e.g., finding all comments for a post) without redundant field storage.
- **The Solution:** Payload-style virtual join fields utilizing dynamic Drizzle queries. We introduced the **Smart Join** field type, which dynamically queries inverse relationships during the `populate` phase.
- **Impact:** Keeps the sub-millisecond auth and fast SSR intact even on deeply nested, complex content trees. Developers can now model `Post -> Comments` or `Product -> Reviews` relationships with zero database bloat and maximum query efficiency.

### 5.4 Durable Webhook Engine & DLQ

- **The Gap:** Standard webhooks often fail silently or flood endpoints during high-traffic bursts. Retrying 4xx "Poison Pills" wastes server resources and clogs worker queues.
- **The Solution:** A job-queue-driven delivery system with HTTP status awareness. Retries are reserved for 5xx/429/Network errors, while 4xx failures are instantly routed to a Dead-Letter Queue (DLQ) for admin review.
- **Impact:** Improves delivery reliability (retry on 5xx/429/network; 4xx → DLQ). **Not** a mathematical 100% delivery guarantee under prolonged outages.

### 5.5 Native Soft Deletes (Trash System)

- **The Gap:** Accidental deletions in enterprise CMS environments often lead to permanent data loss or manual database restoration. Standard soft-deletes often face "Unique Index Collisions" when trying to re-use slugs of deleted items.
- **The Solution:** A native trash system with "Mangle-on-Delete" logic. Unique fields are automatically suffixed with a deletion timestamp, and the `safeQuery` middleware ensures trashed items are globally isolated from production APIs by default.
- **Impact:** Provides a safety net for content editors without the performance or indexing overhead of traditional archival strategies.

### 5.6 Per-Field Content Localization ✅

- **The Gap:** Document-level i18n requires switching entire documents per language, making side-by-side editing impossible.
- **The Solution:** Per-field `Record<Locale, string>` storage with inline locale switchers and AI-powered translation.
- **Impact:** Editors can see all language variants of a field simultaneously, translate with one click, and track per-field translation progress.

- **Partial-Update Data Loss Fixed — JSON `data` Merge on All Four Engines (September 2026)**:
  - **The bug**: `crud.update()` built one whole-column assignment for the JSON `data` blob (`SET "data" = $n::jsonb` on PostgreSQL, `` `data` = ? `` on SQLite/MariaDB), so a **partial PATCH replaced every dynamic field it did not mention**. Measured externally before the fix: **30,940 of 100,000 documents collapsed from a ~1.5 KB median to 61-byte stubs** — and because their own `findByIdRandom`/graphql rows read `ids[0]`, the corruption also inflated a cached-read benchmark number. MongoDB was never affected (`$set` merges per field), which is what fixed the target semantics: a **shallow, null-keeping merge**. A patched object replaces wholesale (no recursion), and `null` is a stored value rather than a deletion.
  - **The fix**: `prepareValues()` marks a partial dynamic-field payload as a patch (a `WeakMap` entry keyed by the prepared values — invisible to `Object.keys`, spreads and Drizzle `.set()`), and each dialect applies it at zero extra cost: PostgreSQL merges inside the UPDATE (`COALESCE("data",'{}'::jsonb) || $n::jsonb`), SQLite `json_patch(...)`, MariaDB `JSON_MERGE_PATCH(...)`. Both of those are RFC 7396 — recursive, and they _delete_ keys patched with `null` — so patches containing nested objects or explicit `null` hydrate the stored blob and merge in JS instead (`jsonPatchNeedsJsMerge()`); scalar/array patches keep the single-statement fast path. The Drizzle fallback merges in JS too, so no path can silently fall back to the destructive write. Full-document writers (sync, seeds) opt out explicitly with `replaceData: true`, which `skipReturning: true` already implies — that path reconstructs the row from the prepared values, so a merge would misreport the untouched columns.
  - **Fail-closed, not silent**: if the blob for a JS-merge cannot be read (missing row), the update **throws** rather than persisting the patch as the whole document.
  - **Verification**: `tests/unit/databases/json-data-patch-merge.test.ts` (exactness boundary, blob decoding, marker invisibility) and four new cases in `tests/integration/databases/adapter-parity.test.ts` — partial patch keeps untouched fields, nested object replaces shallowly, explicit `null` is kept, and the `replaceData` opt-out. Run green on **SQLite 21/21, PostgreSQL 21/21, MariaDB 21/21, MongoDB 20/20 + 1 intentional skip** (`replaceData` has no MongoDB counterpart — its `$set` never replaced anything). The reported request shape is also covered end-to-end through the HTTP API (`tests/integration/api/collections-mutations.test.ts`: `PATCH {views: 2}` on a document with `title`/`body` must return and persist all three), green on SQLite and PostgreSQL.
  - **Still to do** (roadmap): none for the schema path — the spec is the only trail now.
- **Partial-Update Merge Extended to Every Bulk Write Path (September 2026)**:
  - **Bulk paths merged**: `crud.updateMany`, `batch.bulkUpdate` (homogeneous single-statement path, heterogeneous `rawBulkUpdate` CASE builder on SQLite/MariaDB/PostgreSQL, and the transactional per-row fallback) and the query-builder `updateMany` all merge the JSON `data` patch now — they used to write the patch as the entire blob for every matched row. Where the dialect operator is exact the merge stays **inside the statement** (zero reads, zero extra round trips); a nested-object or explicit-null patch on SQLite/MariaDB cannot be expressed in one `SET`, so the CASE builder refuses the fast path and the row-by-row path merges each row against its own stored blob.
  - **Query-builder silent drop fixed**: `SqlQueryBuilder.updateMany` dumped its payload straight into Drizzle `.set()`, which **discards** every field that is not a physical column — blob fields (e.g. `title`) never persisted through that path. It now routes through the same `prepareValues` contract as `crud.update`/`batch.bulkUpdate`.
  - **MongoDB update parity**: Mongoose `strict` (the schema default) **dropped undeclared `$set` paths**, so patching a dynamic field the collection schema did not declare was a silent no-op on MongoDB while SQL adapters stored it in `data`. All Mongo update sites (`crud.update`/`updateMany`, `bulkWrite`, both query builders) now pass `strict: false`; the namespace/field-permission layer remains the schema gate. Covered by a new cross-engine case that patches an undeclared field.
  - **MongoDB query-builder resolution bug (found while testing)**: `MongoDBAdapter.queryBuilder()` resolved its model with the **raw** collection name while `crud.*` normalizes it — the lookup missed, and `_getOrCreateModel` built a generic model bound to a _differently named_ MongoDB collection. Every builder operation (find/count/updateMany/deleteMany) silently ran against an empty collection. Now resolved exactly like `MongoCrudModule._getRepo`.
  - **Verification**: `tests/integration/databases/bulk-operations-contract.test.ts` (partial-patch merge, nested-patch merge, per-row blob fields, homogeneous blob patch, query-builder persistence) and the parity suite's dynamic-field case — green on **SQLite, PostgreSQL, MariaDB and MongoDB**.
- **Engine-Native Dynamic-Field Filters: Containment + GIN on PostgreSQL (September 2026)**:
  - **The gap**: a field that is not materialized into a column lives in the JSON `data` blob, and an equality filter on it was translated on every SQL engine to a text extraction (`data->>'field' = $1`) — a form **no index can serve**. Measured 2026-09-22 on 100k rows (PostgreSQL): **Seq Scan 7.9–10.9 ms** per filtered read, growing linearly with the table.
  - **The fix (engine-specific by construction)**: PostgreSQL now emits **containment** — `data @> '{"field": value}'::jsonb` (`getJsonEquals`, wired through `mapQuery` for `$eq` and `$in`, one probe per scalar value in an `OR` for lists ≤ 32) — and `createModel` provisions a **`jsonb_path_ops` GIN index** (`<table>_data_gin`) for every dynamic collection table. Measured after: **Bitmap Index Scan 0.1–1.7 ms**, and the cost stops growing with table size. Index build 347 ms once at provisioning; write cost measured within run-to-run noise (interleaved A/B/A rounds: −0.9 % inserts, +5.4 % updates). Write-only collections opt out with `schema.jsonIndex === false`.
  - **Type fidelity**: the probe serializes the RAW filter value, so a number filter probes a JSON number and a string filter a JSON string — `{views: 101}` matches a stored number but not a stored `"101"`. SQLite (typed `json_extract`) and MongoDB (type-aware comparison) already behaved that way; the previous PostgreSQL text comparison did not, so this _increases_ cross-engine parity. MariaDB stays the documented looser exception (`JSON_UNQUOTE` comparison coerces). Dotted paths probe nested objects (`a.b` → `{"a":{"b":…}}`), matching the `data#>>'{a,b}'` form.
  - **Why the other engines keep the extraction form**: SQLite and MariaDB have no single index that serves arbitrary JSON paths. Their native answer is already shipped — the row-store hybrid: declare the field `indexed: true` (or `materialize: true`) and it becomes a real column with a real index. The implementation notes now say so explicitly instead of leaving it implicit.
  - **Verification**: `tests/integration/databases/dynamic-field-filter-index.test.ts` — semantics (number/string/`$in` probes, type fidelity) on **all four engines**, the engine-native SQL shape per dialect, and on PostgreSQL an `EXPLAIN (ANALYZE)` of **the adapter's own rendered filter SQL** asserting the GIN index is used and no `Seq Scan` appears (bulk-seeded table with real statistics, isolated from the row probes). Full sweep: SQLite 49/49 · PostgreSQL 51/51 · MariaDB 49/49 · MongoDB 48/48 across the parity, bulk-contract, mutation and dynamic-filter suites.
- **System-Schema Fingerprint + Legacy Tails Removed — Boot No Longer Touches an Unchanged Schema (September 2026)**:
  - **Measured before**: a provisioned PostgreSQL paid **124 ms per boot** re-running all 118 `CREATE TABLE/INDEX IF NOT EXISTS` statements (0.4–1 ms per round trip), plus ~35 `ALTER TABLE … ADD COLUMN IF NOT EXISTS` repair statements (~60 ms; each one costs 1.7–5 ms versus 0.96 ms for a trivial `SELECT`).
  - **Fingerprint**: `svelty_schema_state` stores a sha-256 over `SYSTEM_SCHEMA` **per dialect**; a match skips the spec-derived pass. Any spec change (new table, changed type/default, new index) changes the fingerprint and re-runs the pass, so it is drift-free by construction rather than a hand-bumped version; a pass with a failed statement **does not** store the marker, so a half-applied schema is retried instead of trusted, and any marker error degrades to “run the pass”.
  - **Legacy tails deleted**: the per-engine repair tails are gone — the spec is the only schema trail. Audited first: every column they added (`auth_users.isDeleted/deletedAt`, `auth_api_keys.rateLimit/status/lastUsed/keyHash`) was dead legacy (the current model uses `lastUsedAt`/`lastUsedIp`/`revoked`, and the users table never soft-deleted), and the one substantive repair (MariaDB `mfaVerifiedAt` → `DATETIME(3)`) is already declared **in the spec**, so fresh installs keep millisecond MFA precision. The v0.0.8-era `security` → `password` and `redirects_mv.from|to` renames are dropped with them; the compatibility consequence is documented in [Upgrading SveltyCMS](../guides/configuration/upgrading.mdx).
  - **Measured after** (fresh database → provisioned by the spec alone): **327 ms** once, creating **27 tables + 117 indexes**; every later boot **2.1 ms** (`skipped: true`) — ~122 ms saved per start on PostgreSQL. Verified through the compiled build on fresh databases for **SQLite, PostgreSQL and MariaDB** (all boot with `Bootstrapping system schema...` then `System schema up to date (<fp>) — skipped the DDL pass` on the next boot), with the adapter-parity suite green on each.
- **Cross-Engine `crud.aggregate()` — the MongoDB Pipeline Runs on SQL (September 2026)**:
  - **The gap**: `aggregate()` was MongoDB-only, so SQLite/PostgreSQL/MariaDB answered every pipeline with `NOT_SUPPORTED` and a generic caller could not express a grouped count without raw SQL. The capability flags admitted it (`supportsAggregation: false`).
  - **The translation** (`core/aggregation-translator.ts`, pure and unit-testable): `$match` → `WHERE` through the adapter's own query mapper, so JSON fields, containment and the tenant scope behave exactly like `find*`; `$group` → `GROUP BY` with `$sum` / `$avg` / `$min` / `$max` / `$count` and a scalar `_id` (dotted paths allowed, `$sum: 1` → `COUNT(*)`); `$sort` / `$skip` / `$limit` → `ORDER BY` / `OFFSET` / `LIMIT`; `$count` and include-only `$project` → the select list. Without a group/`$project` the result is the `findMany` document shape, which is what MongoDB's `aggregate` returns too.
  - **Fail-closed by design**: `$lookup`, `$unwind`, `$facet`, a compound `_id`, out-of-order stages and a `$match` that maps to no condition return a named `NOT_SUPPORTED` message that names the workaround — never a silently wrong number. The refusals are returned **outside** `wrap()`, which would otherwise nest the envelope into `{ success: true, data: { success: false, … } }` and make a refusal read as a success (caught by the new contract test, not by the type system).
  - **`$min`/`$max` are the one engine-dependent stage, and they now say so**: PostgreSQL and MariaDB extract JSON as TEXT, so `MIN` over `{10, 2}` returns `"10"` (measured on both; PostgreSQL additionally defines no `min(jsonb)`), while SQLite's typed `json_extract` and MongoDB compare natively. A blob field therefore gets a refusal naming the fix — declare it `indexed` / `materialize: true` — instead of a lexicographic answer; a materialized column aggregates natively on every engine (new dialect hook `getJsonOrderedField`).
  - **PostgreSQL numeric range filters fixed on the way**: `views >= 4` compared TEXT (`'16' < '4'`, so stored `16`/`32` were missed), and the naive JSONB replacement was worse in the other direction — jsonb orders String _below_ Number, so an unguarded `<` admitted a stored `"101"` into `views < 4` (verified: `'"101"'::jsonb < '4'::jsonb` is true). Ranges now read `jsonb_typeof(data->'views') = 'number' AND data->'views' >= '4'::jsonb`, type-strict in both directions and identical to SQLite/MongoDB behaviour.
  - **SQLite dotted-path parity**: `json_extract(data, '$."meta.lang"')` treated the dotted name as one literal key, so a `{"meta.lang": "en"}` filter matched nothing there while PostgreSQL (`data#>>'{meta,lang}'`) and MariaDB (`$.meta.lang`) resolved the nested value. Segments are quoted individually now (`$."meta"."lang"`).
  - **Capability flags and SDK surface**: `supportsAggregation` is `true` on SQLite/PostgreSQL/MariaDB — the documented subset, with unsupported stages still failing closed, which the pre-existing contract test now asserts (`3 × active` / `2 × inactive` instead of an envelope check). `CollectionModel.aggregate` on MongoDB routes through `crud.aggregate` (tenant `$match` injection, normalized collection resolution, logged failures) instead of the raw `model.aggregate`, and both SDK wrappers log a refused or erroring aggregate instead of silently returning `[]`.
  - **Verification**: `tests/unit/databases/aggregation-translator.test.ts` (20 cases — plan shapes, accumulator mapping, purity, every refusal) and `tests/integration/databases/aggregation-contract.test.ts` (12 cases — group/match/count/sort/limit/project, tenant scoping without an explicit `$match`, materialized `$min`/`$max`, the engine-dependent `$min` refusal, `NOT_SUPPORTED` parity), green on **SQLite 12/12 · PostgreSQL 12/12 · MariaDB 12/12 · MongoDB 9 + 3 intentional skips**; the same-commit sweep of the parity, bulk-contract, dynamic-filter and advanced-CRUD suites is green on all four engines.
- **Competitive lanes: read payload de-duplicated, write ack made adapter-agnostic (September 2026)**:
  - **The defect**: every SQL read merged the JSON `data` blob into the document root and _also_ serialized the blob as a nested field. The external harness counted **3,339 B for a 1,558 B document (2.14x)** — "~200 B system columns + `data{…1558}` + the same 8 content fields flattened again" — and it was the only excess in that comparison that was pure duplication rather than envelope convention (Keystone 1.00x, Strapi 1.03x, Wagtail 1.09x).
  - **The fix**: flattening now consumes the blob — the key is dropped by _key_, not identity, because `normalizeJsonFieldValue` PARSES a TEXT blob (SQLite/MariaDB) into a different object, which is exactly why an identity check silently kept it on the wire — and each of the three call sites stopped copying the raw blob (or its TEXT form) back onto the row. A collection field literally named `data` is merged and survives; a legacy string-encoded blob still resolves through the JSON layers.
  - **Measured end-to-end** (the payload-budget integration case logs it): point read **3,339 B → 1,851 B (1.23x a 1.5 KB document)**, PATCH **3,519 B → 1,814 B** — i.e. document + the ~200 B of real system columns, no second copy.
  - **`Prefer: return=minimal` (RFC 7240)** on `PATCH`/`PUT` answers `{success, data:{_id}}` — **70 B** measured — on both the warm-session write lane and the API dispatcher. Absent or unknown values keep the full representation, so no existing client changes behaviour.
  - **Adapter-agnostic write ack**: the preference maps onto the existing `BaseQueryOptions.skipReturning` contract instead of being a response-shape trick, so the row read-back is skipped too — SQL engines omit `RETURNING` and reconstruct the ack from the prepared payload, and **MongoDB now honours the flag as well** (it called `findOneAndUpdate` unconditionally, i.e. the no-read-back path was silently SQL-only). Pinned by the new `write ack (skipReturning)` parity case: **SQLite 24/24 · PostgreSQL 24/24 · MariaDB 24/24 · MongoDB 23/23**.
  - **Point-tier admission filter**: admitting a point read on its first touch meant a 100k-uniform-random scan filled the 2,000-slot L1 point tier with entries that were evicted before ever being read — `putEntry` + byte accounting + `indexKey` + FIFO sweep + a second encoded buffer per cold read, for zero hits. An id now takes a slot on its **second** sighting (bounded FIFO filter): a cold scan costs one Set insert and no response slot, while a repeated id is cached from its second request on.
  - **Verification**: unit 4,855/4,855; SQLite integration 685/685; `tests/unit/databases/read-payload-shape.test.ts` (payload shape, the `data`-named-field case, the legacy string form), `tests/unit/utils/http-preferences.test.ts` (header parsing incl. last-wins), `tests/unit/benchmarks/document-integrity.test.ts` (the benchmark guard that found the upsert loss) and the payload-budget case in `tests/integration/api/collections-mutations.test.ts`.

### 3.26 September 2026 — Fast lanes on by default, gated by system state

The raw-transport fast lanes answered a narrow request class (warm-session admin collection reads) straight to the socket, skipping adapter-node's `IncomingMessage → Request` and `Response → stream` bridging while calling the very same lane function the pipeline calls. They shipped opt-in (`SVELTY_FAST_LANE=1`, default off) with two open questions: the bypass point sits before every hook, and no lane re-applied the `system-state` decision.

- **`system-state` is now re-implemented for lane traffic** (`src/hooks/lane-state-gate.ts`), against the same module-level state mirror the gatekeeper reads, with the same predicate as `handleTurboPipeline`: `READY`/`WARMED`/`WARMING`/`DEGRADED` serve, `SETUP`/`IDLE`/`INITIALIZING`/`MAINTENANCE`/`RECOVERY`/`FAILED` decline to the pipeline. Consulted in the read lane, the write lane and the registry dispatch — the last one so a lane added later cannot serve a state the operator took the instance out of.
- **Default flipped to ON** (`SVELTY_FAST_LANE=0` opts out) so the setting is a documented deployment default rather than a benchmark-only flag, and the transport is symmetric rather than a comparison artifact.
- **Regression caught by measurement**: the lane shim converted the prebuilt body with `Response.text()` and handed the string to `res.end()`, so every wide list body was decoded and re-encoded per request — `listLarge` TURBO-HIT **2.64 ms bridged → 4.76 ms through the lane**. Handing Node the bytes (`arrayBuffer()`, `content-length` from `byteLength`) restores **2.85 ms**.
- **Measured, paired** (PostgreSQL, 10 000 docs, 8c, replica protocol, 3–4 rounds per arm): `findByIdRandom` **3,235 → 3,655 RPS median (+13 %)** with the lane on versus off; `findById` **7,067 → 9,194**; `listPlain` **7,187 → 10,876**; `findMissing` **8,138 → 9,496**. A dedicated 20,000-read load driver agrees: **3,080 → 4,401 RPS**, with the server-only CPU profile putting ~10 % of samples in undici `Request` construction, 5.7 % in adapter-node's static-asset check and ~12 % in socket writes.
- **Confirmed at the published dataset size** (100,000 docs, paired, `update` carried as the control lane because it is not lane-served): `findByIdRandom` **2,631 → 3,919 (+49 %)** and **3,139 → 3,883 (+24 %)**, median **2,885 → 3,901 RPS (+35 %)** — **+11 % over the published competitor row (3,504 RPS)** — while the control stayed flat at ±3 %. This supersedes an earlier session's reading that the row goes neutral or negative at 100 k; that reading predated the byte hand-off fix and was taken with the lane still opt-in.
- **Write coalescing was built, gated, and rejected by its own gate** (`SVELTY_WRITE_COALESCE`, since deleted) — see the roadmap entry: 120/128 concurrent PATCHes batched correctly at an average size of 5 and every caller got its own row, but the lane measured **−29 % median over three alternated pairs** on PostgreSQL (median 1,305 → 933 RPS, warm p95 7.7 → 15.7–20.4 ms) against a flat control, because at 8 workers PostgreSQL already group-commits overlapping statements. The negative result is recorded rather than shipped as an off-by-default path.
- **Verification**: unit **4,866/4,866**; `tests/unit/hooks/fast-lane-policy.test.ts` pins the state matrix, the dispatch backstop and the default-on/opt-out contract; `collection-read-lane.test.ts` establishes its operational-state precondition explicitly.

### 3.29 September 2026 — 2027 Two-Plane Core: Wire Plane Admission, Compiled Point Reads & Dynamic Bitsets

Separated read operations into an opt-in compiled Wire Plane and an enterprise Domain Plane, establishing the foundation for sub-millisecond edge queries with full fallback safety:

- **Strict Wire Plane Admission & Compiled Point Reads (`isWirePlaneAdmissible` + `computeCollectionWireMeta` in `src/hooks/handle-collection-read-lane.ts`; `findPointWireStream` on the adapters)** — Only simple, published single-entry reads with compiled default-locale alignment were admitted to the wire path; admitted reads ran as cached point statements emitting engine-side JSON (`json_object` / `jsonb_build_object` / `JSON_OBJECT`) on the SQL adapters, and everything else fell through to the Domain Plane.
- **Fail-Closed Wire Admission Predicate (`isWirePlaneAdmissible` in `src/hooks/handle-collection-read-lane.ts`)** — Rigorous admission gate guarding Direct-to-Wire SQL streams: checks published status (rejects drafts, review status, and preview cookies), prohibits dynamic relational expansions (`populate`), validates compiled default locale alignment, enforces projection equivalence (`fields`), and verifies absence of mutating `afterRead` hooks.

The raw fast-lane transport only carried warm-session collection reads; writes stayed on adapter-node's bridged path because they need the request body. The write lane now has a transport twin, **opt-in** (`SVELTY_FAST_LANE_WRITE=1`, default off) until an equivalence run:

- **One implementation, not two** — `collectionWriteLane` calls the same `tryCollectionWriteLane` the pipeline calls, so WAF path inspect, CSRF same-origin/double-submit, rate limiting, warm-session admin/RBAC, per-request tenant resolution and the security-header contract are all reused unchanged.
- **Never consume a body you cannot answer** — the lane refactor passes the already-resolved turbo context into `serveWarmCollectionWrite`, which now guarantees a `Response` after commit (no TTL race), and the entry exposes the body **lazily** (`readBody()`): a lane that declines (cold session, non-simple path, maintenance state) returns to the pipeline with the stream unread. A hard body cap (256 KiB default, `SVELTY_FAST_LANE_MAX_BODY`) rejects oversized payloads before they are buffered.
- **Rate-limit parity by construction** — the entry resolves the client address with adapter-node's exact `ADDRESS_HEADER`/`XFF_DEPTH` rules and reproduces its failure mode (`undefined` → throw → `getClientIp` fails closed to `0.0.0.0`), so lane and pipeline bucket identically; `Set-Cookie` emitted inside the lane is carried on the result.
- **Verification** — `tests/unit/hooks/fast-lane-write-policy.test.ts` pins the four invariants: write lane unregistered without the opt-in, declines without consuming the body, reads the body exactly once when committed, and fails closed on the client address.

### 3.30 September 2026 — Wire Plane visibility parity, lane gates & single-transport lean-out

A security review of the 2027 Two-Plane work found that the fast read lane had drifted from the
pipeline it mirrors. The lane builds its own `Response`, so every check that lives in a skipped
hook had to be re-established deliberately — three had not been.

**1. Publication clamp bypassed on the wire path.** The compiled point statement had no `status`
predicate, so a session that the Domain Plane clamps to `published` could fetch a draft by id.
The wire contract now carries `requirePublished`:

- PostgreSQL (`jsonb_build_object`), SQLite (`json_object`), MariaDB (`JSON_OBJECT`) compile
  `AND "status" = 'publish'` into the cached statement (both the plain and tenant variants).
- MongoDB adds `status: { $in: ["publish", "published"] }` to the lean query.
- Where a table has no `status` column the adapter **fails closed** (`null`), and the base-class
  fallback re-checks the row object before serializing, so an unfiltered fallback read can never
  emit unpublished bytes.
- The read lane passes the flag only when `resolvePublicationFilter` says the caller is clamped —
  the same function the Domain Plane uses, so the two cannot disagree. Admins keep the unguarded
  (faster) statement for drafts, and a draft returns `null` → Domain Plane decides.

**2. The clamp never matched anything.** `loadOneById` compared the _filter_ name (`published`)
against the stored value (`publish`), which denied every status-bearing row to a clamped caller and
would have admitted any row stored as `published`. It now uses the shared `isPublishedStatus()`
predicate (accepts both spellings) and leaves status-less rows untouched, preserving the previous
behaviour for non-status-versioned tables.

**3. Read-lane gates re-established** (all evaluated before any cache lookup, so a stored body can
never outlive a policy change):

| Gate            | Before                                                                                                                      | After                                                                                                                                                                                                                                         |
| :-------------- | :-------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Endpoint parity | `collection:read` **or** `collections:read`                                                                                 | `collections:read` only — exactly what `ENDPOINT_PERMISSIONS` requires for `/api/collections` GET                                                                                                                                             |
| FLAC            | Not evaluated: the lane never reaches `handleTokenResolution`, the read path's only `applyFieldPermissionsToBody` call site | `isLaneFlacExempt()` declines when a `FIELD_PERMISSIONS` policy or a `readRoles`-guarded field applies; fails closed on error                                                                                                                 |
| Grant freshness | `turbo.permMask` served until the sliding TTL expired                                                                       | `isPermissionBitsetStale(turbo.permRev)` declines on epoch change; `setTurboAuthContext` stamps the epoch, so `invalidateRoleBitsetsGlobally()` (already called by `setRolePermissions`/`invalidatePermissionCache`) now reaches lane traffic |

tag, the manifest is committed as `chore(release): bump version to vX.Y.Z` — the subject the release

consumed by `scripts/git-safe.ts`, which exports `SVELTY_RELEASE` for the hook, because git never
forwards hook arguments to it.

Two properties are deliberate. The step runs **after** the full gate, never before: `auto-release.yaml`
tags whatever `package.json` holds, so a bump for a tree the gate never validated is exactly the stray
bump AGENTS.md §8 warns about. And the release commit cannot travel inside the push that triggered it —
git resolves the pushed refs before the hook runs — so the hook prints the command to repeat instead of
implying the push was the release; the bump stays local and reversible until that second push. Re-running
is a no-op: within one release cycle the derivation is stable, so a second push finds the manifest already
at the version and commits nothing. Skipped on the docs-only and `--only-failures` paths (both warn), and
refused with a non-zero exit when `version.ts` refuses — a push that looks released but is not would be
worse than a blocked push.

> **Known trap, observed 2026-09-27, removed 2026-09-30:** a test tag `v0.2.0` on the 5 July 2026 commit
> `6dc2d89` (that commit’s manifest was `0.0.7`) was reachable, so `auto` derived `0.1.2 → 0.3.0`
> (highest reachable tag wins over `git describe`'s nearest `v0.1.2`). The tag was local only and was
> deleted. It was never on `origin`. With it gone, the highest reachable tag is `v0.1.2`.

**A manifest writer that could not find the field it was looking at.** `replaceVersionField()` was
line-anchored (`^\s*"version"\s*:…$` with the `m` flag), so a manifest whose version field shares a line
with other keys was refused with `could not locate the top-level "version" field in package.json`,
although the field was right there. It was found by the throwaway-repo probe that verifies the release
step, not by a user report. The writer is now a depth-tracking scan (`locateVersionValue()`) that skips
whole string tokens: a nested `"version"`, the word inside another value, and braces or escaped quotes
inside strings cannot fool it, and minified and pretty-printed manifests both rewrite byte-for-byte except
for the value (10 new tests in `tests/unit/scripts/version-manifest-write.test.ts`; the 33 policy tests of
`version-bump.test.ts` unchanged and green).

**Escapes that printed as escapes.** `info()` / `warn()` in `.githooks/lib.sh` passed their message
through `%s`, so every `${BOLD}…${NC}` embedded in a hint — four pre-existing failure hints plus the new
release hint — rendered as a literal `\033[1m` in a color terminal. They now use `%b`; the message
arguments are hardcoded strings plus validated enums, so interpreting escapes cannot mangle caller data.

**Verification:** the release step was exercised end-to-end in a throwaway repo (tag `v0.1.0` + one `feat`
commit): run 1 bumped `0.1.0 → 0.2.0` and committed it, run 2 no-opped, run 3 (dirty manifest) refused and
returned non-zero — the exit code that blocks the push. Unit tests: `git-safe-release` (7),
`version-manifest-write` (10) and `version-bump` (33) green; `bun run scripts/version.ts --dry-run` against
this repository prints its decision without writing. No throughput claim attaches to this entry — it is
release tooling.

### 3.35 September 2026 — The write tail attributed: WAL checkpoint I/O, not GC

The two 🔴 rows from §3.34 (`update @8c` 5.08→26.67 ms, `mixed` sequential 0.79→4.62 ms) have one root
cause, and it is not the application: **SQLite's auto-checkpoint fsyncing while requests wait**.

**Method.** `PROFILE_WRITE=1` on the replica attributes each write to its spans (`ns:persist`,
`db:upd|ins:stmt`, `prepare-values`, `conv`, `outbox`), and ~5 000 statements per run resolve a rare tail
far better than a 300-sample benchmark row. The switch had never worked: the benchmark server env is a
whitelist (`getBenchmarkTestEnv`), so `PROFILE_WRITE` never reached the server. `scripts/benchmark-matrix/index.ts`
now forwards `PROFILE_WRITE` / `LOG_LEVEL` / `SQLITE_*` explicitly, prints a banner for override runs, and
persists the server log to `results/<db>/diagnostic-server.log` (the in-memory buffer was dropped on success).

**Where the tail is** (9 726 writes, one profiled run): everything above the statement is microseconds —
sanitize+validate p99 0.059 ms, encrypt 0.060, outbox 0.029, `prepare-values` 0.020, `conv` 0.016. The whole
tail sits in the SQL statement: `db:upd:stmt` p50 **0.108 ms**, p99 0.716 ms, max **17.4 ms**.

**Interleaved A/B** (five arms, one replica run each; stalls = statements > 10 ms, out of ~5 200):

| Arm                                     | `db:upd:stmt` > 10 ms |         max | `db:ins:stmt` > 10 ms |         max |
| :-------------------------------------- | --------------------: | ----------: | --------------------: | ----------: |
| control                                 |                    31 |     22.5 ms |                    33 |     20.1 ms |
| control (repeat)                        |                    26 |     25.0 ms |                    25 |     25.1 ms |
| `SQLITE_SYNCHRONOUS=OFF`                |                 **0** |      5.0 ms |                 **0** |      6.1 ms |
| `SQLITE_WAL_AUTOCHECKPOINT=0`           |                 **0** |      5.3 ms |                 **0** |      5.1 ms |
| `WAL_AUTOCHECKPOINT=16000` (128 MB WAL) |                     7 | **36.2 ms** |                    16 | **43.2 ms** |

Removing _either_ the checkpoint or its fsync removes every stall; making checkpoints rarer makes the
surviving ones **bigger** (their cost scales with the WAL size), so "raise the threshold" is the wrong
lever. `SYNCHRONOUS=OFF` is not shippable (power-loss durability) and `AUTOCHECKPOINT=0` alone leaves the
WAL unbounded — the fix is moving housekeeping **off the request path** (checkpoint from a separate
connection or a background scheduler, size cap as the safety valve), tracked as the roadmap item above.

**Also measured in the same session:** with zero statement stalls the write rows' ratios fall from 7.4× to
2.7× (`update`) and 3.6× (`create`) — the residual spread is the synchronous driver serializing eight
concurrent writers, which is the second lever (worker-connection writes) and is not yet shipped. The
`auth-performance` 500 seen once in the interrupted full matrix did **not** reproduce in isolation (the
reject path answers 401/403 and logs `Invalid or non-existent API key provided`), so it is recorded here as
unverified rather than fixed.

### 3.39 September 2026 — Lane responses get their compression back (and the >64 KiB tier gets its first honest number)

**The gap.** Fast-lane responses bypass `handleCompression` (`LANE_BYPASSED_HOOKS`) and
`serveTurboCacheEntry` can only serve an encoding that was attached to the entry — so every lane-served
list left the socket as identity bytes. Measured 2026-09-28 through the zstd audit: a **260 791 B** body
answered a zstd-only client uncompressed, and the whole zstd/co-tenant scenario in `api-latency.test.ts`
reported `api.zstd.available=0` (skipped) — the tier was unmeasurable, not slow.

**What shipped.** `src/hooks/response-compression-stash.ts` — one shared variant implementation for the
read lane and the API dispatcher, with a precise contract:

- **Hits are free**: list entries carry `compressed` variants (`zstd` with the CMS dictionary, `br`/`gzip`
  ≤ `SYNC_MAX_SIZE`); `serveTurboCacheEntry` already negotiates `Accept-Encoding` per request. The
  response-cache's internal precompute turned out to be **commented-out dead code**, so lane entries had
  never carried a variant at all.
- **First re-hit warms lazily**: point-read misses are high-cardinality and skip the CPU; the second
  request for any key schedules the stash — a re-read is the proof that the key is worth compressing.
- **Miss path inside the buffered budget**: the lane compresses ≤ 64 KiB synchronously (exactly the
  pipeline's own sync tier) and seeds the variant into both the response and the cache entry.
- **Safety rails**: in-flight guard per key, expanded output dropped, a body that produced nothing is
  marked attempted (`compressed: {}`) so later hits do not retry, `preserveStale` keeps a concurrent
  write's staleness decision (the old `set()` forced `stale = false`), and a superseded body is never
  overwritten (body/etag re-check before the re-set). `entryBytes()` now counts variant bytes, so the L1
  budget no longer drifts when variants are attached.

**Beyond 64 KiB the lane declines to the pipeline** (compress-while-sending, no full-body wait). Buffering
the same 255 KiB body in-lane measured **10.8 ms/request, 183 RPS, co-tenant p95 0.33 → 2.50 ms** — rejected.
The pipeline's streaming tier is now measurable end-to-end and lands at **22.7 ms warm / p95 24.8 ms /
87 RPS with co-tenant p95 0.30 → 7.39 ms** on this host (cache-busted, so every request pays a fresh
compression). That is a property of the app-wide streaming compression tier — now visible for the first
time — not of the lane change; a level/threshold decision for > 64 KiB bodies is the next lever, tracked in
the roadmap.

**Verification**: `tests/unit/hooks/response-compression-stash.test.ts` (9 cases: gates, builder guards,
hit-stash, supersession, staleness, size no-op) + 51/51 across the neighbouring hook suites; the api-latency
probe now reports `zstd active: … body 254.7 KiB (> 64 KiB async tier)` instead of a skip.

**Follow-up A/B (same day) — the level/threshold hypothesis is falsified.** The 22.7 ms / +7.4 ms co-tenant
in that probe invited a compression-settings fix; isolation says otherwise. `zstdCompress` on a 244 KiB body
measures **0.30–0.55 ms at every level 1→15**, and the CMS dictionary artifact (`static/dictionaries/cms-payloads.dict`)
is **absent in-repo**, so `{dict}` is a no-op — neither level nor dictionary is a lever. End-to-end, the same
256 074 B list: **identity warm 0.95 ms · identity miss 14.10 ms · zstd warm (stashed variant) 0.72 ms ·
zstd miss (lane declines → pipeline, compression included) 15.16 ms**, co-tenant point read 0.38 → 0.65 ms.
So compression is **~1 ms of a ~15 ms miss** — the cost is the cache-busted miss path itself (DB read +
build + 256 KB serialisation/drain), and cached hits serve the variant for free at sub-millisecond latency.
No level/threshold change was warranted; the open lever is the list-miss path, not the encoding.

**Round 2 (same day) — the miss path decomposed, and a wrong turn corrected.** Lane marks (`x-srv-split`)
plus `ENABLE_HOOK_TIMING=1` on a 199-row / 257 027 B list (SQLite) read: **lane HIT 0.79 ms (ttfb 0.79,
drain 0.00)** vs **miss ttfb 14.98 / drain 0.23 ms** — the server is late, not the wire — and the whole
nested hook chain accounted for only ~3.7 ms, so the rest was the row build (≈0.055 ms/row). Two fixes:

- **`streamingJsonResponse` (and `streamingExportResponse`) are pull-driven now.** The old writer ran a
  `start()` loop and slept a hard-coded `setTimeout(10)` whenever `desiredSize <= 0` — a count-based stream's
  HWM is 1, so that was _most_ iterations (the `limit = MAX_PAGE_SIZE` path had been measured at ~3.1 s per
  request), and the export writer yielded `setTimeout(0)` **per record** (a 10 k-row export paid ~10 s of
  timers). The stream now calls `pull()` only when it wants data: backpressure is structural, zero timers.
  Pinned by `tests/unit/api/streaming-json-response.test.ts` (identical bytes, `maxItems`, error marker, and
  a 500-item drain that would take ≥ 5 s under the old sleep).
- **The lane no longer declines > 64 KiB lists to the pipeline.** Declining meant the lane had already built
  the rows, discarded them, and the pipeline rebuilt them: **15.0 ms vs 10.8 ms** for the same list, co-tenant
  p95 **7.39 → 2.50 ms**. The lane now compresses the negotiated encoding itself — sync at ≤ 64 KiB, one-shot
  **async** (libuv pool, `compressAsync`) above — and seeds the variant into the response and the entry.

**Measured after both fixes** (api-latency zstd audit, SQLite, 254.7 KiB cache-busted list): warm
**22.7 → 11.4 ms**, **87 → 175 RPS**, co-tenant p95 during the burst **7.39 → 2.93 ms**; turbo point read in
the same run 0.711 ms / 11 097 RPS. The remaining ~7 ms of the 11.4 is the SDK list build itself (row
hydration + per-row JSON) — the list wire plane is the next lever, recorded in the roadmap.

**8c re-verification, same session** (`BENCH_ZSTD_CONCURRENCY=2` vs `=8` on one build — the audit row is
knob-controlled now and the matrix forwards it): the row goes **13.0 ms / 153 RPS (2c) → 49.4 ms / 154 RPS
(8c)**. Latency scales with concurrency while throughput stays flat, so the large-list miss path is
_saturated_ at ~150–175 RPS, and the ceiling matches the synchronous SDK row build (~6–7 ms of event-loop
work per request, interleaved across 8 in-flight builds, while compression itself is off-thread). The
point-read rows at the same 8c kept 9 676 RPS, which isolates the cap to the list build — the empirical
case for the list wire plane below. (The c=2 point re-measured 13.0 / 153 here against 11.4 / 175 in the
earlier session — host drift between sessions is 7–59 % on this box.)

- **Health is truthful now.** Three responders reported `overallStatus: "READY"` from DB presence alone
  while the boot cache-warming subsystem was still `initializing` — every harness (and operator probe)
  then measured the warm-up itself. The turbo pipeline's `buildHealthResponse`, the dispatcher's
  HYPER-TURBO health branch and the hooks.server responder now all emit the derived state plus the
  strict `ready` predicate (`isSystemReady()`: operational state AND the boot pre-warm settled), and the
  benchmark harnesses (`isHealthReady` in the matrix, the standalone wait) require `ready !== false`
  before measuring. Verified live: `{"status":"healthy","overallStatus":"READY","ready":true,…}` on the
  bench server; the waits still pass.
- **Unsorted list reads have a deterministic order.** `defaultListSortOption()` (`updatedAt` desc,
  `_id` desc) is now the SDK `find` default for every non-keyset read. Without an ORDER BY the engine
  picks the access path, so the same logical query could return _different LIMIT/OFFSET windows_ under
  two plans (proven: `SELECT rowid,_id` served from the `_id` auto-index vs `SELECT <all cols>` served
  from a table scan, same table, different first rows) — a real pagination bug, and the reason a
  compiled list statement could never be byte-stable. The order matches the keyset default and rides
  the `(tenantId, updatedAt, _id)` index (no temp B-tree, verified via `EXPLAIN QUERY PLAN`). Note for a
  rolling deploy: the default-list response cache key stays `…:find:default_50`, so entries cached
  under the old (unspecified) order live out their TTL — bodies are otherwise identical.
- **The list wire plane (engine-built `data` JSON) was implemented to byte parity and measured — it
  loses.** On SQLite it was built to completion (row = `json_object` over the physical selection +
  `json_remove` blob splice; fail-closed `bad_rows` guard for NULL/non-object blobs; the lane frames the
  exact envelope incl. `meta.executionTime` = BaseAdapter's constant wrap meta and the
  `_collection`-only-when-rows rule) and reached **provable byte parity**: the integration differential
  suite compares wire output against the domain envelope byte-for-byte, and an HTTP A/B on the bench
  server (`x-wire: list` marker) returned **37 916 B == 37 916 B**. Then the timing: on a _fresh_ bench
  DB (201 rows), a 50-row × ~750 B list measures **wire p50 5.05 ms (SQL alone 1.7–2.9 ms) vs domain
  p50 2.43 ms** — SQLite's JSON functions are text-based (render + `json_remove` re-render + splice
  copies ≈ 58 µs/row) and `node:sqlite` is synchronous anyway, so nothing moves off the event loop.
  On PostgreSQL/MariaDB the same idea cannot be byte-identical at all: `json_build_object` /
  `JSON_OBJECT` render **spaced** JSON (`{"a" : 1}`) and `jsonb` additionally reorders keys, so V8
  `JSON.stringify` bytes are unattainable without value-corrupting string surgery (the shipped PG point
  wire already serves engine-formatted bytes, so parity there means _stability_, not identity);
  MongoDB has no engine-side JSON without `$function`. Conclusion: **the remaining ~7 ms of a large
  list miss is not removable by engine JSON** — the saturation evidence (153 RPS at 2c / 154 at 8c)
  stands, the lever does not. The SQLite implementation, the lane branch and the interfaces were
  removed again (no dead code); the reusable pieces kept are the deterministic order and the
  point-wire delegation fix below.
- **Point-wire delegation in the tenant guard.** `createTenantGuardedCrud` builds an explicit method
  list, so under MULTI_TENANT the wrapper hid `findPointWireStream` and every lane read silently fell
  back to the Domain Plane. The wire method is now delegated through the same tenant-options guard as
  every other op.
- **Row-shape lever profiled and falsified (same day).** A faithful stage replay of the list build
  (199 rows × ~1.3 KB blob, 16 keys/row, real `convertDatesToISO` + `trimListEnvelope` + stringify)
  costs **0.66 ms total (3.3 µs/row)**: blob `JSON.parse` 0.27 ms, parse+flatten+date/bool conversion
  0.38 ms, trim copy 0.03 ms, `JSON.stringify` of the 364 KB envelope 0.31 ms. A blob-only projection
  shape saves ~0.2 ms, dropping the blob entirely ~0.5 ms — the row shape is **not** where the list
  cost lives. The 310 KB (199 × ~1.5 KB) list's _real_ `x-srv-split` build mark is **6.4 ms**, ~10×
  the stage replay: the remaining mass is string materialisation (body + ETag hash + variant
  handling) and the GC that rides on it, not per-row parsing. Concurrency check on that shape
  (cache-bypassed, identity): p50 8.64 / 9.28 / 12.99 ms and RPS **116 → 194 → 567** at c=1/2/8 — the
  earlier “flat ~153/154 RPS” saturation reading did **not** reproduce outside the zstd audit's own

### 3.40 September 2026 — The 380 KB list miss's build mark, found and cut: an 8 ms FNV fold → native digest (−84 %)

**The open measurement, closed.** §3.39 left one explicit next step: re-measure the list saturation with the
compression path separated from the build path. The new diagnostic probe
`tests/benchmarks/probe-list-compression-ab.test.ts` does exactly that — `Accept-Encoding: identity` vs `zstd`
at c=1/2/4/8 on a 199-row / 381 681 B list (220 × ~1.5 KB rows seeded through the API into `BenchmarkStable`,
one unique `probe=` cache key per request so every request is a true miss and single-flight coalescing cannot
fold the arms together), reporting client p50/RPS plus the `x-srv-split` deltas (`db−lookup`, `build−db`,
`cachewrite−build`, `serve−cachewrite`).

**Result, before any change (SQLite, production build):** `buildΔ` (trim + stringify + etag) is **6.2–6.4 ms on
both encodings** — compression is not in the build; `cacheΔ` isolates it: identity 0.14–0.16 ms vs zstd
**0.96 / 7.16 / 15.6 / 29.1 ms** at c=1/2/4/8 (the awaited `compressAsync` plus its worker-pool queueing;
server `x-srv-dur` p50 grows 7.5 → 35.5 ms on the zstd arm). The zstd response is 5 132 B where identity is
381 681 B, so at c=8 the client is _faster_ on zstd (p50 53.2 vs 63.8 ms, 136 vs 119 RPS) despite the server
paying more — the compression wait buys a 74× smaller transfer and pays for itself on the wire.

**The build mark profiled:** an in-process profile of the exact lane steps on the captured 381 681-char body:
`Buffer.byteLength` 0.004 ms, `Buffer.from` 0.083 ms — and `generateContentEtag` (FNV-1a 64 over UTF-16 code
units) **8.2 ms (Bun) / 3.9–7.9 ms (Node)**. It is the entire build segment, and the single most expensive
per-request op on the large-list path. Two same-output rewrites were measured and rejected: int-limb fold
1.03×, reciprocal-multiply carry 1.00× — FNV-1a is a serial multiply-accumulate chain, so arithmetic
micro-optimisation cannot move it; byte-wise FNV (different output) only 2×.

**The fix — size-gated native digest.** `generateContentEtag` keeps the FNV fold byte-identical below 1 KiB
(small settings/GraphQL/point payloads: zero validator churn), and above it returns `"s256|<sha256-hex>"`
computed with `crypto.hash("sha256", body, "hex")` (fallback `createHash`). The T15 contract is unchanged —
the validator still covers the entire body, so any content change flips it — and the digest is 20–50× faster
at every measured size (0.0013 ms @1 KiB, 0.10–0.21 ms @380 KB). One function backs lane, dispatcher, GraphQL
and turbo-stash etags, so the win lands on every large-body miss path at once.

**Result, after (same probe, same shape):** `buildΔ` **6.4 → 0.94–1.01 ms (−84 %)**; identity p50 c=1
**8.84 → 3.26 ms**, RPS **99/119 → 252/343** at c=1/c=8; zstd `cacheΔ` @c=8 **29.1 → 7.75 ms** (less event-loop
contention in front of the worker pool); in-process etag cost 9.8 → **0.102 ms**. Regression test:
`tests/unit/core/request-classifier-and-response-cache.test.ts` pins `"…16-hex"` below the threshold,
`"s256|…64-hex"` above, plus determinism and sensitivity.

**Harness findings (the flagged 401, diagnosed).** The "fresh `DB_NAME`s 401" note from §3.39: in local profile
the pre-boot seeder creates the sandbox DB through the env-only adapter path, which materialises only the
content/collection schema — no `auth_users`/`system_preferences` — so `seedBenchmarkState`'s `createUser`
silently no-ops (its result is unchecked) and the server can never authenticate. Snapshotting a completed DB
(`VACUUM INTO config/test-database/<name>.sqlite`) restores it. Also: seeding POSTs must carry
`content-type: application/json` — Bun's fetch sends `text/plain` for string bodies and the write lane then
500s with `Unexpected end of JSON input` (probe-side bug, fixed in the probe).

### 3.41 September 2026 — Harness DBs stop landing in the user's folder, composite indexes get a policy, and the update lane's residual is _proven_ to be the durable commit

**Three threads, one honest measurement discipline: no claim without a falsification run.**

**1. The E2E/benchmark databases that appeared in `config/database/` (root cause: a `require`).** The
user's live-data folder had accumulated `e2e_auth_test.sqlite`, `bench_parent.sqlite`, `benchmark_shared.sqlite`,
`sveltycms_test.sqlite` and a set of `probe_*` scratch DBs — none of which belong there. Fingerprints showed
36-table, 0-row shells (auth/settings empty, only worker-written `svelty_jobs` rows), i.e. harness debris, not
user data. Root cause proven from the worker's own log
(`[DB] Registry resolved connection string: config/database/probe_test_whoF.sqlite`): `resolveSqlitePath()`
(`src/databases/config-state.ts`) created the test folder via a bare `require("node:fs")` **inside the `try` that
also returned the test path**. In the esbuild-built background-worker bundle that `require` throws
(`Dynamic require of "node:fs" is not supported`), the `catch` swallowed it, control fell through the
`if (isTest)` block, and the network-address branch answered `config/database/<name>.sqlite`. Fix: static ESM
imports (they cannot throw), best-effort `mkdirSync`, and the `return` **outside** the `try` so a mkdir failure can
never re-route the path again. The name heuristic now calls the shared `isIsolatedTestDbName()` classifier that
`enforceTestSafety()` already uses (`test`/`bench`/`e2e`/`_functional`, minus production-like names) instead of a
divergent `includes("test") || includes("benchmark")` copy. Verified after rebuild by running the worker directly:
harness flag + `probe_test_whoG` → `config/test-database/…`, harness flag + plain `probe_plainA` →
`config/test-database/…`, no flag + `probe_plainB` → `config/database/…` (true-dev behaviour preserved).
Regression guard: `tests/unit/databases/resolve-sqlite-path.test.ts` — 10 tests covering flag routing, classifier
names, dev names, explicit POSIX/Windows/relative hosts, `.sqlite` canonicalization, and — because this is the
actual incident — a **real** mkdir failure (a `process.cwd` spy pointing at an existing _file_, so no fs mocking
can be dodged). The guard was falsified before shipping: moving the `return` back inside the `try` makes it fail
with `expected 'config/test-database/probe_test_worker.sqlite' / received 'config/database/probe_test_worker.sqlite'`
— exactly the incident's signature.

**2. The covering composite index now has a policy (all three SQL engines).** `createModel` used to provision
`(tenantId, status, <col>, _id)` for **every** materialized column; each one is maintained on **every** write,
because `updatedAt` is indexed and rewritten by each update, so PostgreSQL can never take the HOT path and must
insert into all indexes on the table. A psql A/B on a narrow table (3 vs 4 indexes, 2 000-row batches, alternating
orders) measured that cost directly: **+11–17 % per extra index** (≈ 0.7 µs/row/index). The policy — shared by
PostgreSQL, MariaDB and SQLite via `buildCompositeIndexColumns()` in `src/databases/core/drizzle-sql-helpers.ts` —
provisions the composite only for **declared query targets**: `indexed: true` fields, numeric fields (the default
`listFilterSort` sort target), and the `publishedAt` base column. Equality-lookup base columns (`collection`,
`slug`, `locale`) and storage-only columns (`unique`, `materialize: true`) keep their single-column index (still
filterable) but no longer pay for a covering twin; legacy twins are dropped explicitly, following the existing
`…_tenant_status_updated` twin-drop precedent. The default list order is untouched — it is served by
`…_tenant_status_updated_id`, which the policy always creates. On the 113 k-row benchmark table the policy takes
the index set **15 → 12** (`pg_indexes`, verified after a shipped-code boot). Coverage:
`tests/unit/databases/composite-index-policy.test.ts` (eligibility + column-set contract) and the cross-engine
integration block `Composite-index policy — {engine}` in `tests/integration/databases/dynamic-field-filter-index.test.ts`
(a numeric field keeps its composite; `unique`/`materialize`/lookup columns do not; their single-column index
exists) — green on SQLite **and** PostgreSQL.

**3. Where the update lane's residual actually goes — the durable commit, measured.** The write-split probe
(`tests/benchmarks/probe-write-split.test.ts`, PostgreSQL, production-mode server, 2 400 iterations at 8c) puts the
update lane at `x-srv-dur` p50 **3.67 ms / avg 3.78 ms**, decomposed as security 0.014 · parse 0.081 · schema
0.000 · prep 0.028 · encrypt 0.011 · **dbwrite 3.548** · postwrite 0.026 · serve 0.058 ms. Every app phase sums to
**~0.16 ms (4 %)**; `dbwrite` owns 94 %. Then the same statement was measured with and without the durability
wait (psql, single-row autocommit = the app's pattern): **1.566 / 1.658 / 4.496 ms with `synchronous_commit=on`
vs 0.310 / 0.347 / 0.430 ms with `off`** — i.e. ~75–85 % of `dbwrite` is the WAL fsync/commit wait on this host's
Docker volume, and 200 rows in one transaction cost **42–44 µs/row** for all the actual tuple+index work. That is
why neither the composite policy nor the earlier numeric-materialization change can move the lane here: the
effect sizes are single-digit µs against a ~3.7 ms commit-dominated op, and the replica's own pair
(update 1 280 → 1 406 RPS) also moved the _read_ lanes +21–32 %, i.e. host drift, not policy. Both facts are now
recorded as such — the policy ships as a **write-amplification/WAL reduction**, not as a latency claim.

### 3.44 September 2026 — Schema model

The lean collection schema model shipped in `src/content/schema-model.ts`, `src/content/schema-hooks.ts`, and `src/databases/core/column-renames.ts`. Documented in [Schema model](../reference/architecture/schema-model.mdx). Relation values stay ids. There is no new foreign-key index on the write path, because each extra index is maintained on every update (§3.41). A full-document update is still the durable commit. The remaining model surfaces (compiled relation filters, nested writes, `onDelete`, `virtual`, `omit`) are tracked in the [roadmap](./roadmap-2026.mdx).

- GraphQL lists take `where: JSON`, `orderBy: String`, and `take: Int` in one operator language (one JSON argument, not a generated input type per field). `parseOrderBy` accepts `field`, `+field`, `-field`, `field:asc|desc`, and `field asc|desc` and rejects unknown or non-orderable fields (`ORDERBY_UNKNOWN_FIELD`, `ORDERBY_FIELD_NOT_ORDERABLE`). Inverse relations take `where` and filter loaded rows in memory; `isFilterable: false` rejects a filter on that field. Where shape cap: 8000 characters, depth 6, 64 nodes.
- Hooks, on the collection and on `field.hooks`: `resolveInput`, `validate` (many errors, one abort before the write), `beforeOperation`, `afterOperation`, in addition to `beforeValidate` / `afterValidate`. Order is field and list `resolveInput`, `beforeValidate`, field and list `validate` plus the numeric/exact gate, `beforeOperation`, `afterValidate`; `scheduleAfterOperation` runs the post-commit `afterOperation` without awaiting, and a failure is logged at debug. `prepareWritePayload` passes `schema.fields` whenever a field declares hooks, and `ensureSchemaHotFlags` derives `_hasHookFields` / `_hasAfterOperationHooks` so hook-free schemas pay nothing.
- `decimal`, `bigint`, `calendarDay`, and `bytes` are exact string columns (`materializedSqlType`: SQLite `TEXT`; PostgreSQL and MariaDB `VARCHAR(64)`, `VARCHAR(10)`, and `TEXT`) and do not earn a covering composite index unless `indexed: true`. `shouldMaterializeField` materializes them by default, so they are real columns rather than blob fields.
- Schema actions `{ permission, increment?: { field, amount }, patch?, run? }` are checked by the action permission in `CollectionsNamespace.runAction`. REST is `POST /api/collections/:id/actions/:name` with `{ entryId, input }`; GraphQL is `runCollectionAction`. REST does not also require `collections:write`. An undefined action is 404 `ACTION_NOT_FOUND`; an action without a permission is admin-only (`ACTION_FORBIDDEN`).
- `renamedFrom` on a system `ColumnSpec` or a collection field renames when the old column exists and the new one does not, before `ADD`. `column-renames.ts` matches the live catalog case-insensitively and issues the rename in the stored case; a failed rename is retried on the next provisioning pass. Mongo uses `$rename` once per process when the model is created. The dropped v0.0.8 repairs are still not replayed unless a column declares `renamedFrom`. Tests: `tests/unit/databases/column-renames.test.ts`, `tests/unit/content/schema-model.test.ts`, and `tests/unit/databases/schema-spec-parity.test.ts`.
- `isFilterable` / `isOrderable` are booleans or functions of `{ user }` and are enforced on GraphQL filters and sorts. `cacheHint: { maxAge, scope }` sets GraphQL `Cache-Control` (tightest `maxAge`, private wins); a private hint is not stored in the shared GraphQL response cache.
- Row ownership `ownership: { field }`: `find`, `count`, and `findStreaming` scope to `field === user._id` before the cache key (admins and system scope bypass; a caller without a user id matches nothing), and `presentRead` drops a non-matching point-read row on a copied envelope so the shared cache entry is never mutated or poisoned. Tests: `tests/unit/sdk/collections-ownership.test.ts`.
- `singleton: true` forces `_id` `singleton:<collectionId>` in `create`; a second create answers 409 `SINGLETON_EXISTS`. The `_id` primary key makes a concurrent double create fail on the insert instead of persisting two rows.

### 3.45 October 2026 — Durable-commit parity for every SQL engine, UNNEST/JSON_TABLE bulk writes & the system index overhaul

The 2026-09-23 engine-knob probe ended with "deliberately NOT shipped" because the knob was cluster-global. It is now shipped the safe way: **per-connection** GUC parameters, so only the CMS pool relaxes durability and production keeps the server default unless the operator opts in.

- **PostgreSQL durability knob wired** — `pgConnectionParameters()` (`src/databases/postgresql/adapter-core.ts`) passes `PG_SYNCHRONOUS_COMMIT`/`DATABASE_SYNCHRONOUS_COMMIT` (plus `PG_WORK_MEM`, `PG_JIT` default `off`) into every pool (primary, tenant pools, replicas). Self-measured on the local WSL2/Docker host (2026-10-04): update `dbwrite` p50 **9.76 ms → 2.3–2.9 ms** (96 % → ~70 % of the request), competitive update lane (warm 8c) **~1.5 k → 2.0–2.6 k RPS**.
- **PostgreSQL UNNEST bulk writes** — `insertMany`/`rawInsertManyReturning`/`rawBulkUpdate` bind one `text[]` array per column with element-wise casts; constant SQL per column set (plan-cache friendly), presence arrays keep explicit-NULL vs omitted semantics, `data_mode` patch/set/keep preserves per-row JSON blob safety. Param count drops from 2×N scalars to 1 array/column.
- **MariaDB JSON_TABLE bulk update** — the MariaDB twin of the PG UNNEST path (`UPDATE … JOIN JSON_TABLE`, version-gated 10.6+, CASE-ladder fallback below). **Fixed live (2026-10-04)**: the JOIN was pinned to `utf8mb4_unicode_ci`, which raises error 1267 on tables created under the MariaDB 12 default collation (`utf8mb4_uca1400_ai_ci`) — the error was silently swallowed and every heterogeneous batch fell into the 100× per-row loop (**68.4 ms**). The JOIN now compares `COLLATE utf8mb4_bin` (works for both collations) and the catch logs instead of vanishing. Self-measured after the fix: **BULK UPDATE (100 heterogeneous) 68.4 → 3.6 ms (~19×, 14 → 267 RPS)**, contract suite 18/18. **Measured and deliberately NOT shipped (2026-10-04)**: the INSERT twin (`INSERT … SELECT FROM JSON_TABLE`) lost the A/B — BULK INSERT (100) 2.70 → 3.24 ms (+19 %) and seed burst 7,676 → 4,899 docs/s (−36 %) — because the multi-VALUES path binds values natively while JSON_TABLE pays a full JSON document parse per batch; the UPDATE twin won because it replaced N per-row statements, not direct binding. The finding is documented in `rawInsertManyReturning`.
- **Durability parity baked into the harness DBs** (`tests/docker-compose.yml`): PostgreSQL `synchronous_commit=off` + buffer tuning; MariaDB `innodb_flush_log_at_trx_commit=2` (the MariaDB twin — there is no per-session GUC, so the server flag is the only knob). Self-measured competitive replica (warm 8c, 2026-10-04): MariaDB update **1 269 → 1 918 RPS (+51 %)**, create **1 466 → 2 083 RPS (+42 %)**; seed burst **5 686 → 7 676 docs/s**.
- **System index overhaul** (single source of truth `system-schema-spec.ts` + drizzle schemas + renderer): `audit_logs` timestamp btree → BRIN + `(tenantId, timestamp DESC)`; `content_nodes` children index `(tenantId, parentId, position, _id)`; `content_drafts` latest index `(contentId, version DESC)`; `content_revisions` UNIQUE `(contentId, version)`; `auth_users` email unique `NULLS NOT DISTINCT`; redirects UNIQUE partial `(tenantId, source) WHERE active = TRUE` with legacy dedupe + drop extensions. MariaDB/SQLite equivalents kept in parity. Provisioned and verified via psql/`schema-spec-parity` (48 files / 347 tests).
- **Benchmark scale guard recalibrated** (2026-10-04): the denominator was `findByIdRandom`, which now runs at the HTTP+DB floor (~8.8–9.5 k RPS), structurally capping any DB-bound write ratio at ~0.20. The guard now compares writes against `listLarge` (the heaviest DB-backed read lane, 5.1–6.5 k RPS) at a 0.25 threshold: PostgreSQL passes at **0.40/0.40**, MariaDB at **0.31/0.27** (both self-measured 2026-10-04, warm 8c).
- **Fast-lane oversized-body fix** (`index.server.mjs`): `content-length` > 256 KB now rejects with a proper 413 before the lane reads the body (no more `FAST_LANE_PAYLOAD_TOO_LARGE` 500s).
- **UPDATE `?fields=` projection (2026-10-05)**: `PATCH /api/collections/:id/:entryId?fields=_id,count,updatedAt` prunes the SQL `RETURNING` read-back to the requested physical columns on both write paths (fast lane + full pipeline) — the JSON `data` blob is never re-read/de-TOASTed for callers that only need the changed fields. Blob-only names are resolved away (`resolveUpdateProjection`, unit-tested); an empty projection falls back to the full representation. Verified end-to-end by a response-shape guard in the replica benchmark (`BENCH_UPDATE_FIELDS=_id,count,updatedAt`): projected responses contain exactly the requested keys. Self-measured on the small-blob replica the lane sits within host noise of the full-return row (2,840 vs 2,964 RPS, warm 8c) — the gain scales with blob size/TOAST, which is the 100k-doc external-harness regime. The other two Keystone-gap levers were verified as already implemented: pure physical-column updates emit no `COALESCE(data,…) || $n` merge clause, and the audit hook already fire-and-forgets (`void` flush + 15 ms coalescing timer, never awaited by the response).

### 3.47 October 2026 — Pre-compiled Query Builder Templates & Sub-Millisecond SQL CRUD Acceleration

- **Shared SQL query builder unification** (`src/databases/core/sql-query-builder.ts`): Unified the duplicated builder logic across SQLite, PostgreSQL, and MariaDB into a single `SqlQueryBuilder<T>` parameterized by `SqlDialect`. All engine-specific quoting, placeholder binding (`$1` vs `?`), JSON extraction, and ILIKE/LIKE operators are driven by dialect constants.
- **Compiled plan expansion**: Extended the compiled prepared-statement cache beyond scalar equality to support `whereIn`, `whereNotIn`, `whereBetween`, `whereNull`, `whereNotNull`, `orWhere`, and parameterized pattern searches (`search_or`). Any dynamic JSON field filters, unmapped expressions, or non-bindable objects safely degrade to Drizzle dynamic AST with zero runtime errors.
- **Dialect-safe LIKE ESCAPE binding**: MariaDB treats backslashes inside string literals as escape characters; binding the escape backslash as a query parameter (`ESCAPE ?` / `ESCAPE $N`) ensures cross-dialect compatibility without double-escaping bugs or syntax failures.
- **Standard CRUD read path acceleration** (`src/databases/core/sql-adapter-core.ts`): Added pre-compiled template fast paths to `findMany`, `findPage`, and `count`. Pre-compiled query shapes execute directly via `executeCompiled()`, bypass Drizzle runtime AST building and SQL string assembly, and hoist schema date-conversion metadata so read lists stop re-resolving table column schemas per row.

### 3.48 October 2026 — SQLite write tail: checkpointing moved off the request path by default, and group commit (opt-in) takes the 8c queue tail from 🔴 to 🟡

**Two levers, measured separately on the same build** (`competitive-workload-replica`, sqlite, warm 8c,
production server, 300 samples; each verdict is the repo's own 3-run ensemble median via
`bun run verify:benchmark-local`).

**Baseline (recorded pre-change run, both 🔴):** create p50 4.41 / p99 24.14 ms (+19.7 ms excess), update
p50 4.23 / p99 30.8 ms (+26.6 ms); the tail was entirely SQLite's synchronous auto-checkpoint (§3.35).

**Shipped default — off-request-path checkpointing.** `applyPragmas` now defaults to
`PRAGMA wal_autocheckpoint=0` unless `SQLITE_WAL_AUTOCHECKPOINT` is set explicitly, and
`startWalHousekeeping` runs `startWalCheckpointScheduler` by default (opt out `SVELTY_WAL_CHECKPOINT=0`)
with a new **WAL-size cap** (`SVELTY_WAL_MAX_BYTES`, default 64 MB) beside the existing idle and
60 s-force rules. `synchronous=NORMAL` is unchanged — durability is not weakened. Result (3-run ensemble):
create avg 4.17 / p50 4.0 / p95 5.41 / p99 10.48 / **+6.477 ms** 🔴, update avg 3.63 / p50 3.47 / p95 5.67 /
p99 7.68 / **+4.214 ms** 🔴 — **`slowCount` 0 on every write row** (no sample above 10 ms; the discrete ~25 ms
checkpoint spikes are gone), matching the earlier single-run A/B (`AUTOCHECKPOINT=0` → `slowCount` 0, residual
excess ≈ 6.5 ms). The absolute tail excess is still above the 4 ms `WATCH` bound: the checkpoint spikes were
removed, the write-mutex queue is not.

**Shipped default ON (2026-10-09) — group commit is the default write path.** The batcher is now constructed
by default (`SVELTY_SQLITE_GROUP_COMMIT` defaults to `1`; `=0` restores the per-write commit control lane).
Paired A/B on the 10k-doc matrix replica (`competitive-workload-replica`, `--db=sqlite`):
**create @8c 1,833 → 2,892 RPS (+57.8 %)** and **update @8c 1,896 → 3,347 RPS (+76.6 %)** with improved p95
(6.74 → 5.29 ms and 5.38 → 3.48 ms), `mixed @8c` +12.1 %, `Seed Burst` +8.0 %; sequential lanes neutral
(update +1.7 %) except create −9.9 % (single-pair, within the lane's CoV). The remaining acceptance gate
(no 🔴 row, `--strict-variance` green on a ≥3-run ensemble) is tracked in the roadmap.

**Opt-in (`SVELTY_SQLITE_GROUP_COMMIT=1`) — write coalescing (original measurement).** New `src/databases/sqlite/write-batcher.ts`
queues batchable single-statement writes and drains them on a bounded event-loop tick
(`setImmediate`/`queueMicrotask`, never a delay timer) into one `BEGIN IMMEDIATE … COMMIT`; each op keeps a
`SAVEPOINT` so one failure rolls back only itself, results are buffered and settled after `COMMIT`, and a lone
write takes the `runSingle` (no group transaction) path. The adapter only constructs the batcher behind the
flag; transaction-control/`PRAGMA` statements and active write spans (re-entrant/worker contexts) bypass it.
Result (3-run ensemble): create avg 2.86 / p50 2.6 / p95 4.38 / p99 5.54 / **+2.943 ms** 🟡, update avg 2.81 /
p50 2.72 / p95 4.07 / p99 4.95 / **+2.225 ms** 🟡, `slowCount` 0 — both rows out of 🔴, and p50 fell ~1.3 ms
(4.0 → 2.6 create, 3.5 → 2.7 update), so the drain is genuinely coalescing writes rather than just adding a hop.

**Residual floor, stated plainly:** ≈ **2.2–2.9 ms** `p99 − p50`, **not** ≤ 1 ms. Group commit only folds
writes that reach the queue within the same tick; at 8c the requests are staggered by the HTTP/auth pipeline,
so many drains still carry a single op, and the synchronous driver blocks the event loop for each batch's
execute phase — the queue is shortened, not flattened. §3.36's commit-collapse falsification still holds for the
per-statement commit itself; the win here is queue coalescing, not a cheaper commit. Kept opt-in as specified.

**Verification**: `tests/unit/databases/write-batcher.test.ts` (10 cases: batching, lone-write path,
`maxBatchSize` split, per-op isolation, throw/unsettled safety net, default-scheduler deferral) and
`tests/unit/databases/wal-scheduling.test.ts` (9 cases: size-cap band, interval gate, idle precedence,
scheduler wiring). `node ./node_modules/vitest/vitest.mjs run tests/unit/databases` → 53 files / 461 passed.
