## 🏗️ In Progress

- 🏗️ **Engine-native capability gaps (audited 2026-09-22)** — the remaining places where the DB-agnostic API is a least-common-denominator rather than each engine's potential, ranked: (1) **MariaDB streaming is disabled** (`supportsStreaming: false`) although mysql2 can stream non-buffered, so exports fall back to 500-row pages while PostgreSQL streams; (2) **MongoDB list+count costs two round trips** (`Promise.all` in `mongo-crud-methods.ts`) where a single `$facet` pipeline would do it in one; (3) **`$min`/`$max` on a non-materialized JSON field are refused on PostgreSQL/MariaDB** — their extraction is TEXT, so the answer would be lexicographic (`MIN` of `{10, 2}` is `"10"` on both, and PostgreSQL defines no `min(jsonb)`), and the intended answer is materializing the field; (4) **group keys read from the JSON blob come back as the extraction type** (text on PostgreSQL/MariaDB, typed on SQLite) rather than a native value, so a grouping caller has to normalize; (5) **MariaDB's `JSON_UNQUOTE` comparison coerces** (`"101"` matches `101`) — the one engine that is not type-strict on `$eq`. Already native (no work needed): full-text search (SQLite FTS5 + `bm25()`, PostgreSQL `tsvector`/`tsquery` + GIN, MariaDB `MATCH…AGAINST IN BOOLEAN MODE`, MongoDB `$text` with weights), atomic increments (`jsonb_set` / `JSON_SET` / `json_set` / `$inc`), native upserts, transport-local `RETURNING`, keyset pagination, ordered `bulkWrite`, PostgreSQL `COPY FROM` in the importer, and — shipped 2026-09-22 — cross-engine `aggregate()` (`core/aggregation-translator.ts`: the portable subset plus named `NOT_SUPPORTED` refusals), the per-engine partial-update merge, PostgreSQL containment+GIN dynamic-field filters, the PostgreSQL numeric range guard (`jsonb_typeof`), SQLite dotted-path filters, and the schema fingerprint that ended the legacy repair tails.

- 🏗️ **Media pipeline consolidation** — the remaining work: collapse the two derivative pipelines into one (today: the SIZES ladder plus a deferred `processImageWithPresets` pass, ~17 files per image), background precompilation of operator-defined SIZES, watermark + focal-point aware delivery, and a derivative-GC sweep that actually reclaims disk. Shipped 2026-09-22: dedupe **before** generation and the no-upscaling/no-redundant-write ladder clamp. Plan, status and the benchmark rows that prove each step: [Media Pipeline Plan](./media-pipeline-plan.mdx).

- 🏗️ **Media pipeline #4 — on-demand transform boundary** — media requests still resolve to stored derivatives only; the documented, benchmarked on-demand transform endpoint does not exist yet. Design, the derivative-GC interaction and the fetch path for a non-full-size original are in [Media Pipeline Plan](./media-pipeline-plan.mdx).

- 🏗️ **Plugin Admin Pages (`page` part)** — Finalize declarative sub-navigation, deep-linking, and full-page test suites for `/plugin/<path>` admin tools.
- 🏗️ **Native Commerce Pipeline Add-ons** — Complete the remaining commercial modules:
  - `ConditionPlugin` for complex promotion rules (cart minimums, coupon combinations, category discounts).
  - BOGO and tiered volume pricing calculator.

- 🏗️ **Reliable per-stage attribution for the write lane** — `readHookTimings()` can report `unavailable` mid-run because the terminal health bypass (`handle-turbo-pipeline.server.ts:381`/`:403`) answers with a minimal payload that carries no `hooks`. A dedicated authenticated diagnostics route (or including counters in the bypass when `verbose`) would make write-lane attribution dependable.
- 🏗️ **A multi-day memory row** — the 1 h row and its controls exist now (2026-09-22: `mixed` 1 h **STABLE (No Leak)**, `read-only` / `idle` controls, two page-cache A/B runs — matrix in [achievements-2026](./achievements-2026.mdx)), and the verbose health probe reports `arrayBuffers` per bucket again. What is still missing: (a) a **24 h+ row** — one hour separates a leak from a _step_ but not from a commitment ratchet that only converges over hours (`heapTotal` tail +0.15–0.30 MB/min at t ≈ 10–21, converging on 342.8–347.9 MB across three runs); (b) a **media-path profile** — the mix never probes a storage path, so the bounded existence cache (`SVELTY_FILE_EXISTS_CACHE_MAX`) cannot show up in any row; (c) a **non-SQLite long row** — the 2026-09-22 matrix is SQLite-only, and `node:sqlite` vs `bun:sqlite` have different native allocators; (d) **native commit vs residency in the verdict** — the mixed 1 h run's RSS tail read +1.35 MB/min (t = 6.5) from a late 45 MB _residency_ excursion with flat `heapTotal` / `external`, i.e. under the 2 MB/min materiality floor and therefore not a leak, but a maintainer reading only RSS would misread it. Sampling `privateBytes` beside RSS (as that investigation did) separates the two; folding it into the harness would make the distinction first-class.
- 🏗️ **`bulkCreate` passes no tenant options** — `CollectionsNamespace.bulkCreate` calls `adapter.batch.bulkInsert(name, entries)` / `crud.insertMany(name, entries)` without an options bag, so under `MULTI_TENANT=true` the fail-closed tenant guard (`crud-tenant-guard.ts`, mode `reject`) has nothing to assert on and the whole bulk path is unreachable (`MULTI_TENANT=false` locally, so no run here exercised it — code-path analysis, not a runtime observation). Fix: thread `{ tenantId }` through `batch.bulkInsert` and pass it to `crud.insertMany` in both branches.
- 🏗️ **Cold point-read row: close the framework/driver gap** — the `findByIdRandom` competitive row is lane-served (`HYPER_TURBO`, full pipeline skipped) with nothing left to remove in the lane's own steps: measured 55 µs SDK `findById` (27 µs of it the `node:sqlite` driver), 69 µs `Headers`+`Response` construction, ~10 % of server CPU in undici web-platform plumbing, against a 28 µs raw-HTTP floor. Levers, all out of scope for a surgical change and each needing its own tradeoff decision: (1) the driver/runtime pair — `node:sqlite` returns one indexed row in 27 µs where the raw `bun:sqlite` ceiling is 3–4 µs, so `RUNTIME=bun` (`index.bun.ts`) is worth a matrix run before any code moves; (2) `LocalCMS.getLocals` builds a 19-namespace facade per request (9 µs) — a shared instance needs a design that keeps namespace state request-scoped; (3) adapter-node's `Response` → socket writer goes through `Readable.fromWeb` for every body (vendored; patched today only for `ORIGIN`); (4) the point lane's 2000-entry FIFO is a size/size tradeoff, not a defect — it serves ~2 % of uniformly random ids at 100 k docs and ~20 % at 10 k, and enlarging it lengthens every collection write's invalidation scan. Method note for whoever picks this up: pin the build fingerprint (`md5sum build/server/chunks/*.js`) around each measured run — a concurrent build changed the artifact mid-run in this session and silently invalidated a pair of runs. **Profiled 2026-09-23** (`SVELTY_CPU_PROFILE` in the spawned server, 2 s snapshots, PostgreSQL, 10 k docs, 8c, 1386 samples): the server is **idle 53.7 % of wall time** on these lanes. Sampled self time is ~9 % our own chunks, 5.6 % Node's web-platform plumbing (header validation/buffer fill), ~5 % socket writes, ~4 % SvelteKit + readable streams, 6.6 % the sampler itself — so **neither lane is CPU-bound and no amount of JS micro-optimisation will close them**; what remains is PG-side statement work (the index reduction above), the response payload/`RETURNING` (the RFC 7240 lever), and framework request→`Response`→socket bridging. A raw `node:http` fast path for the lane would dodge that bridging but must re-implement auth, tenancy and the security header contract — the tradeoff to decide before anyone starts. Caution, measured: sampling costs about half the RPS on read lanes (`findById` 7783 → 5388, `findByIdRandom` 2063 → 1542) and 6.6 % of all samples are the sampler's own `post` — never profile a run whose numbers are published.

- 🏗️ **Beating the two remaining competitive lanes (`findByIdRandom`, `update`)** — 9 of 11 external lanes are won; these two are 1.14× / 1.09× behind KeystoneJS (3142 vs 2753 RPS; 1533 vs 1411 RPS, PostgreSQL, 100 k docs — competitor figures are the harness's own published session, based on publicly available results as of September 2026; the figures below are self-measured). Local attribution on our own replica (`tests/benchmarks/competitive-workload-replica.test.ts`, PostgreSQL, 10 k docs, 8 workers, 5-round medians) says the update lane is **I/O-commit-bound, not statement-CPU-bound**: removing two redundant indexes cut 27 % of the statement's per-row work (31.6 → 13.1 µs, GIN included) and changed nothing measurable on the lane, while read lanes drifted 0.91–1.05× between the same two variants. What does move it is the response — `Prefer: return=minimal` (RFC 7240) measured **1507 → 1572 RPS (+4.3 %)**, 1901 → 70 B, reproducible with `BENCH_PREFER_MINIMAL=1` against the replica. Pending: (a) the external harness applying `Prefer` to **every** row (disclosed in its METHODOLOGY §7/§10) or the benchmark-authored Keystone/Wagtail write routes returning the representation — without either, the row compares 1901 B of native resource against 43 B of harness ack (`docker/keystone/rest.ts`); (b) a CPU profile of the cold read lane (`SVELTY_CPU_PROFILE=<dir>`, see [server-hooks](../reference/architecture/server-hooks.mdx)) to decide whether the residual ~220 µs of in-lane JS justifies a compiled per-collection lane reader instead of the SDK facade.

**Paired A/B, 2026-09-23** (4 alternated pairs × 5 rounds, PostgreSQL replica, 5 000 docs, 8c, with an unaffected lane carried as the control): `cold.findByIdRandom` — which `Prefer` cannot touch — moved **−0.3 %** paired median (spread −9.4 … +0.9 %), which is what makes the design trustworthy on this host; `update` moved **+7.8 % paired median with all four pairs positive (+4.7 … +10.7 %)** for the RFC 7240 minimal ack, and `create` moved **−2.6 % (spread −12.3 … +1.9 %)** with POST support — so the POST half was reverted rather than shipped unproven. The lesson worth keeping: an _unpaired_ median moved ±10 % between arms on the control lane, i.e. a single A/B pair cannot resolve anything at this effect size, and any claim here needs alternated pairs plus a control lane.

**Raw-transport fast lanes, 2026-09-23** (opt-in via `SVELTY_FAST_LANE=1`, **default off**, and now a registry rather than a one-off bridge): the single shared server entry `index.server.mjs` — used by `index.cjs` on Node, `bun index.cjs` on Bun, and `start` — hands GET/HEAD requests to a lane registry the app publishes on `globalThis`. A lane calls the very same functions the SvelteKit path calls (`tryCollectionReadLane`), so auth, tenancy, publication filter, cache and security headers stay in one place — nothing is re-implemented — and writes the returned `{ status, headers, body }` straight to the socket, bypassing adapter-node's `IncomingMessage → Request` and `Response → stream` bridging. Adding a lane never touches the entry, and `LANE_BYPASSED_HOOKS` plus the guard test (`tests/unit/hooks/fast-lane-policy.test.ts`) fails when a new `hooks.server.ts` pipeline hook appears unclassified, so a hook cannot silently miss lane traffic. Equivalence is machine-checked inside a single server run by `BENCH_VERIFY_RAW=1` (the `x-fast-lane: off` request header forces the bridged path for that request only, so both transports share one session and one database): point read **200/200 · 1382 B identical**, missing id 200/200 · 28 B, list 200/200 · 11154 B, HEAD 200/200 · 0 B, `If-None-Match` **304/304**. Paired A/B (3 pairs × 5 rounds, PostgreSQL, 5 000 docs, 8c): **`findByIdRandom` +21.7 % (all three pairs +20.4 … +34.1 %), `findById` +82.7 %, `listPlain` +49.1 %**, while the lanes the bridge cannot touch moved ±7 % — the target gains sit outside that band, but the magnitude deserves a re-run now that the hit marker is observable, and the profile's earlier prediction (~10 % of server time in plumbing) underestimated the response-side stream cost. **Still open before this could default to on**: the write lanes are not bridged (they need the request body through the same path), and bypassing the vendored response writer deserves a deliberate security review — the lane still requires a warm admin session, but the bypass point sits before every hook.

- 🏗️ **Measured corrections to the fast-lane work (2026-09-23, later session)** — three findings that supersede earlier claims in this section, recorded so they are not re-derived:
  1. **The raw transport is regime-dependent, not a blanket win.** At 5 000 docs it measured **+21.7 % on `findByIdRandom`**; a full 11-workload A/B at 100 000 docs / 8 workers, with `update` carried as the control (write lanes are not bridged), put the read deltas at **+1.8 % (`findById`), −7.0 % (`findByIdRandom`), +1.4 % (`listPlain`)** against a **±8 % noise floor** — at 100 k the read lanes are DB/cache-bound, so bypassing the framework's request→`Response`→socket bridging buys ≈ nothing there. It remains real for warm hits and lists in transport-bound regimes (small datasets, high cache-hit installations).
  2. **The point-read route is already lane-served.** `isSimpleCollectionRead` accepts both `GET/HEAD /api/collections/:collection` and `/:collection/:entryId`, so all six read workloads are already eligible — extending lane coverage to other deterministic GET routes helps those endpoints, never this row.
  3. **The row's shape is cold-read locality, not transport.** Hot id vs random id at 8c: **6 014 → 3 100 RPS**, i.e. 1.33 ms vs 2.58 ms per request (**+1.25 ms**), while the comparison row is flat (2.28 ms both) — a flat ratio there can also mean uniform slowness rather than the absence of a defect. The split that decides the fix is `SVELTY_SRV_DUR=1`: compare `x-srv-dur` for a hot id against a random id in one run — ≈ 1.2 ms means a DB-class wait (page fetch/queueing, where the only levers are row/page economics with real write-side costs), ≈ 0.2–0.3 ms means miss-path app work (cache-key builds, admission bookkeeping, generic row flattening — all removable). With that floor, **nothing below ~15 % on this row is claimable.**

- 🏗️ **Engine-knob probe: commit-bound writes (2026-09-23, host-labelled, deliberately NOT shipped)** — `synchronous_commit=off` measured the external harness's update lane at **8 workers +21.7 %**, **1 worker +93.1 %**, and seeding **+18.9 %**. Two conclusions: the write path is commit-bound (which also explains why removing 27 % of per-row statement work moved no RPS — the WAL flush dominates, so index hygiene pays in WAL/disk/VACUUM instead), and this is the measured ceiling for a CMS-side coalescing implementation that keeps one durable flush per batch. It is **not shipped**: the setting is cluster-global, so every row on the same Postgres rises identically and the ratio does not move (1 306 → 1 590 vs 1 437 → 1 749). A CMS-side fix is per-row by construction; at 8 workers PostgreSQL already group-commits overlapping transactions, so expect roughly parity to +11 % on that lane — the defensible claim is **concurrent write throughput as a product property**, with parity on the published row accepted.

- 👨‍🔬 **The 1.25 ms is the MISS rebuild — split measured (2026-09-23, harness-side, sequential c=1, 400 requests, same 100k dataset and container boot)**: HOT (`ids[0]`) wall **1.17–1.26 ms** with **server `x-srv-dur` p50 0.070 ms** (TURBO-HIT ×400); COLD (distinct ids) wall **1.42–1.54 ms** with **server p50 0.470–0.480 ms** (MISS ×400). A ~1.1 ms per-request floor is identical hot and cold and lies _outside_ the stamped section (framework/adapter/HTTP/routing) — it caps absolute RPS but does not explain the gap. The ~0.45 ms of MISS-path server work surfaces as ~1.25 ms of added latency and ~20 % of throughput at 8 workers through queueing (`W = L/λ`). **Acceptance gate for read-path work: COLD `x-srv-dur` p50** — it read 0.480 vs 0.470 ms across a full rebuild while RPS moved ±8–20 %, so a change that does not move it is not a read-path win; its target is ≈ 0.30 ms (parity) plus the ~277 B payload trim as the separate bytes-column win. Two corrections to the suspect list: the point-read etag is already the cheap `id-updatedAt` form (`generateContentEtag` is the list path), and the two `dd317ae28` cuts measured < 0.05 ms — below this probe's resolution, exactly as dead-work removal should be, so the earlier +19 % attributed to them is retracted as lane spread.

- 🔧 **Harness-mirror fetch refspec (2026-09-24, operator note)**: a mirror checkout whose `remote.origin.fetch` tracks only `next` leaves `origin/main` silently stale (observed at `7a801f1bf` while `main` had moved) — a row measured from such a clone is measured from the wrong revision. Fix in the mirror with `git remote set-branches origin '*'` (or `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'`) and re-fetch before a session.

## 🔌 Unwired Capabilities & Technical Debt

Existing modules to be connected or formally retired:

- **Database-Native FTS** — Wire `IFtsAdapter` (`dbAdapter.fts` across SQLite FTS5, Postgres `tsvector`, MariaDB `MATCH...AGAINST`, Mongo `$text`) into the live `?search=` query pipeline with tenant scoping and field-level access controls.
- **Semantic Index Persistence** — Implement incremental updates and disk persistence (`indexItem`, `indexBatch`, `persistSemanticIndex`, `rebuildSemanticIndex`) in `src/services/intelligence/semantic-index.ts`.
- **Content Insights Consumer** — Document and surface `getContentInsights` and cross-tenant pattern recognition in editorial workflows.
- **`TRUSTED_PROXIES`** — Enforce `getTrustedProxies()` from `src/databases/config-state.ts` across IP extraction in rate limiting, auth, and audit logging.
- **Role Bitset Invalidation** — Automate role cache clearing on role permission mutations via `invalidateRoleBitset`.
- **`streamingRawJsonResponse`** — Wire or prune unused streaming helper in `src/routes/api/[...path]/handlers/streaming.ts`.
- **Required-Fields Publish Guard** — Connect `validateRequiredFields()` (`src/widgets/widget-validation.ts`) to status transition mutations to enforce non-empty publish requirements.
- **Legacy Store Bridges** — Migrate `systemState` and `overallState` in `src/stores/system/state.svelte.ts` from legacy `svelte/store` `derived()` exports to modern Svelte 5 runes (`$state()`, `$derived()`).
- **GraphQL Replay & Hint Controls** — `markMutationExecuted` (mutation replay prevention) and `createSuppressHintsRule` in `src/routes/api/graphql/rules.ts` are never wired (`+server.ts` only registers depth-limit and max-alias rules). Wire them into the Yoga validation list or delete them deliberately — as-is the replay guard does not exist at runtime.
- **Background Services Out of the API Process** — `hooks.server.ts` still statically imports the job queue, scheduler, outbox, watchdog, automation, telemetry, and behavioral learner and starts them at READY (an earlier `await import()` left their production exports `undefined` under Rolldown's cyclic-chunk initializers). A dedicated `background-entry.ts` must be started from `index.cjs` **as a separate process** — importing it into the same process evaluates the modules and frees nothing. Prerequisites: child-process DB init, supervision/restart, heartbeat reporting back to the parent's service health, and an explicit decision for SQLite (WAL + `PRAGMA busy_timeout=30000` already tolerate a second writer, but `withWriteLock` is per-process, so the two processes would serialize at the file level — contention, not corruption; a busy API burst could park a background poll for up to the timeout). Projected: 30–80 MB resident, ~5–10% on `create`, 0–3% on cached reads.
- **API-Only Build Profile** — a second build that emits only the read lane, the write lane, and the active adapter (no admin routes, no widget catalog, no session/security admin chrome). This is the step that moves resident memory again; the cached-read rate stays at the PostgreSQL HTTP floor either way. A comparator process (two lists, admin build off) cannot be met by trimming unused widgets or background services.

- **Rust Tooling Evaluation (`fuzdev/tsv`)** — evaluated 2026-09-21; recommendation: **stay with `oxfmt`**, which already ships the needed capability behind a disabled flag. `tsv` 0.4.1 is faster but not _more capable_.
  - `oxfmt` (pinned `^0.68.0`) has a top-level `svelte` key: "Pass `true` or an object to enable `.svelte` file formatting … Default: Disabled", and it loads `svelte/compiler` at runtime — **`svelte@^5.57.1` is already a direct dependency here**. Its `overrides` key supplies per-glob options, so `.svelte` can keep its own style. Measured with a throwaway config (`"svelte": {}` plus a `**/*.svelte` override on tabs / single quotes / no trailing commas): `oxfmt --check src` covers **1470 files in 1.59 s** (1024 → +446 `.svelte`) while `src/**/*.ts` (918 files) stays clean. With the key omitted, oxfmt matches **0 of 489** `.svelte` files. Reproduce: `bun x oxfmt -c <probe.json> --check src`.
  - **`tsv` 0.4.1 is not idempotent** on 2 of 446 `.svelte` files (`src/widgets/custom/seo/input.svelte`, `src/routes/(app)/dashboard/widgets/unified-metrics/index.svelte`): a generic argument list left as `}>(` + object is revised to `}>({` on the second pass, so a single-pass `--check` gate reports those two indefinitely. `oxfmt` reaches a fixed point on the first pass (verified on the same file), which is what a CI gate requires.
  - `tsv`'s advantage is throughput, not coverage: ~0.14 s for 446 `.svelte` files against `oxfmt`'s ~1.6 s for a whole-`src` pass — immaterial at this repo size. Its costs are a second toolchain, a layout that disagrees with `oxfmt`'s in detail (a later switch would mean a second reformat), a hardcoded non-configurable style, and no linter (it does not replace `oxlint`).
  - Whichever tool is chosen, the first run normalizes the backlog: ~427 of 446 `.svelte` files change, because nothing has ever formatted them. The diffs are layout-only — re-wrapping hand-compacted lines past 100 columns, e.g. the one-line `case 'sm': return { … }` arms in `src/components/ui/checkbox.svelte`.
