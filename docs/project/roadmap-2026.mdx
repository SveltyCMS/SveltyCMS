## 🏗️ In Progress

- 🏗️ **Engine-native capability gaps (audited 2026-09-22)** — the remaining places where the DB-agnostic API is a least-common-denominator rather than each engine's potential, ranked: (1) **MariaDB streaming is disabled** (`supportsStreaming: false`) although mysql2 can stream non-buffered, so exports fall back to 500-row pages while PostgreSQL streams; (2) **MongoDB list+count costs two round trips** (`Promise.all` in `mongo-crud-methods.ts`) where a single `$facet` pipeline would do it in one; (3) **`$min`/`$max` on a non-materialized JSON field are refused on PostgreSQL/MariaDB** — their extraction is TEXT, so the answer would be lexicographic (`MIN` of `{10, 2}` is `"10"` on both, and PostgreSQL defines no `min(jsonb)`), and the intended answer is materializing the field; (4) **group keys read from the JSON blob come back as the extraction type** (text on PostgreSQL/MariaDB, typed on SQLite) rather than a native value, so a grouping caller has to normalize; (5) **MariaDB's `JSON_UNQUOTE` comparison coerces** (`"101"` matches `101`) — the one engine that is not type-strict on `$eq`. Already native (no work needed): full-text search (SQLite FTS5 + `bm25()`, PostgreSQL `tsvector`/`tsquery` + GIN, MariaDB `MATCH…AGAINST IN BOOLEAN MODE`, MongoDB `$text` with weights), atomic increments (`jsonb_set` / `JSON_SET` / `json_set` / `$inc`), native upserts, transport-local `RETURNING`, keyset pagination, ordered `bulkWrite`, PostgreSQL `COPY FROM` in the importer, and — shipped 2026-09-22 — cross-engine `aggregate()` (`core/aggregation-translator.ts`: the portable subset plus named `NOT_SUPPORTED` refusals), the per-engine partial-update merge, PostgreSQL containment+GIN dynamic-field filters, the PostgreSQL numeric range guard (`jsonb_typeof`), SQLite dotted-path filters, and the schema fingerprint that ended the legacy repair tails.

- 🏗️ **Media pipeline consolidation** — the remaining work: collapse the two derivative pipelines into one (today: the SIZES ladder plus a deferred `processImageWithPresets` pass, ~17 files per image), background precompilation of operator-defined SIZES, watermark + focal-point aware delivery, and a derivative-GC sweep that actually reclaims disk. Shipped 2026-09-22: dedupe **before** generation and the no-upscaling/no-redundant-write ladder clamp. Plan, status and the benchmark rows that prove each step: [Media Pipeline Plan](./media-pipeline-plan.mdx).

- 🏗️ **Media pipeline #4 — on-demand transform boundary** — media requests still resolve to stored derivatives only; the documented, benchmarked on-demand transform endpoint does not exist yet. Design, the derivative-GC interaction and the fetch path for a non-full-size original are in [Media Pipeline Plan](./media-pipeline-plan.mdx).

- 🏗️ **Plugin Admin Pages (`page` part)** — Finalize declarative sub-navigation, deep-linking, and full-page test suites for `/plugin/<path>` admin tools.
- 🏗️ **Native Commerce Pipeline Add-ons** — Complete the remaining commercial modules:
  - `ConditionPlugin` for complex promotion rules (cart minimums, coupon combinations, category discounts).
  - BOGO and tiered volume pricing calculator.
  - Multi-warehouse inventory allocation.
  - Real-time currency exchange (FX) resolver with caching.
  - Stripe Billing recurring subscription webhooks and portal.
  - Schema.org structured data markup (`Product`, `Offer`, `AggregateRating`) on public `/shop` routes.
- 🏗️ **Reliable per-stage attribution for the write lane** — `readHookTimings()` can report `unavailable` mid-run because the terminal health bypass (`handle-turbo-pipeline.server.ts:381`/`:403`) answers with a minimal payload that carries no `hooks`. A dedicated authenticated diagnostics route (or including counters in the bypass when `verbose`) would make write-lane attribution dependable.
- 🏗️ **A multi-day memory row** — the 1 h row and its controls exist now (2026-09-22: `mixed` 1 h **STABLE (No Leak)**, `read-only` / `idle` controls, two page-cache A/B runs — matrix in [achievements-2026](./achievements-2026.mdx)), and the verbose health probe reports `arrayBuffers` per bucket again. What is still missing: (a) a **24 h+ row** — one hour separates a leak from a _step_ but not from a commitment ratchet that only converges over hours (`heapTotal` tail +0.15–0.30 MB/min at t ≈ 10–21, converging on 342.8–347.9 MB across three runs); (b) a **media-path profile** — the mix never probes a storage path, so the bounded existence cache (`SVELTY_FILE_EXISTS_CACHE_MAX`) cannot show up in any row; (c) a **non-SQLite long row** — the 2026-09-22 matrix is SQLite-only, and `node:sqlite` vs `bun:sqlite` have different native allocators; (d) **native commit vs residency in the verdict** — the mixed 1 h run's RSS tail read +1.35 MB/min (t = 6.5) from a late 45 MB _residency_ excursion with flat `heapTotal` / `external`, i.e. under the 2 MB/min materiality floor and therefore not a leak, but a maintainer reading only RSS would misread it. Sampling `privateBytes` beside RSS (as that investigation did) separates the two; folding it into the harness would make the distinction first-class.
- 🏗️ **`bulkCreate` passes no tenant options** — `CollectionsNamespace.bulkCreate` calls `adapter.batch.bulkInsert(name, entries)` / `crud.insertMany(name, entries)` without an options bag, so under `MULTI_TENANT=true` the fail-closed tenant guard (`crud-tenant-guard.ts`, mode `reject`) has nothing to assert on and the whole bulk path is unreachable (`MULTI_TENANT=false` locally, so no run here exercised it — code-path analysis, not a runtime observation). Fix: thread `{ tenantId }` through `batch.bulkInsert` and pass it to `crud.insertMany` in both branches.
- 🏗️ **Cold point-read row: close the framework/driver gap** — the `findByIdRandom` competitive row is lane-served (`HYPER_TURBO`, full pipeline skipped) with nothing left to remove in the lane's own steps: measured 55 µs SDK `findById` (27 µs of it the `node:sqlite` driver), 69 µs `Headers`+`Response` construction, ~10 % of server CPU in undici web-platform plumbing, against a 28 µs raw-HTTP floor. Levers, all out of scope for a surgical change and each needing its own tradeoff decision: (1) the driver/runtime pair — `node:sqlite` returns one indexed row in 27 µs where the raw `bun:sqlite` ceiling is 3–4 µs, so `RUNTIME=bun` (`index.bun.ts`) is worth a matrix run before any code moves; (2) `LocalCMS.getLocals` builds a 19-namespace facade per request (9 µs) — a shared instance needs a design that keeps namespace state request-scoped; (3) adapter-node's `Response` → socket writer goes through `Readable.fromWeb` for every body (vendored; patched today only for `ORIGIN`); (4) the point lane's 2000-entry FIFO is a size/size tradeoff, not a defect — it serves ~2 % of uniformly random ids at 100 k docs and ~20 % at 10 k, and enlarging it lengthens every collection write's invalidation scan. Method note for whoever picks this up: pin the build fingerprint (`md5sum build/server/chunks/*.js`) around each measured run — a concurrent build changed the artifact mid-run in this session and silently invalidated a pair of runs. **Profiled 2026-09-23** (`SVELTY_CPU_PROFILE` in the spawned server, 2 s snapshots, PostgreSQL, 10 k docs, 8c, 1386 samples): the server is **idle 53.7 % of wall time** on these lanes. Sampled self time is ~9 % our own chunks, 5.6 % Node's web-platform plumbing (header validation/buffer fill), ~5 % socket writes, ~4 % SvelteKit + readable streams, 6.6 % the sampler itself — so **neither lane is CPU-bound and no amount of JS micro-optimisation will close them**; what remains is PG-side statement work (the index reduction above), the response payload/`RETURNING` (the RFC 7240 lever), and framework request→`Response`→socket bridging. A raw `node:http` fast path for the lane would dodge that bridging but must re-implement auth, tenancy and the security header contract — the tradeoff to decide before anyone starts. Caution, measured: sampling costs about half the RPS on read lanes (`findById` 7783 → 5388, `findByIdRandom` 2063 → 1542) and 6.6 % of all samples are the sampler's own `post` — never profile a run whose numbers are published.

- 🏗️ **Beating the two remaining competitive lanes (`findByIdRandom`, `update`)** — 9 of 11 external lanes are won; these two are 1.14× / 1.09× behind KeystoneJS (3142 vs 2753 RPS; 1533 vs 1411 RPS, PostgreSQL, 100 k docs — competitor figures are the harness's own published session, based on publicly available results as of September 2026; the figures below are self-measured). Local attribution on our own replica (`tests/benchmarks/competitive-workload-replica.test.ts`, PostgreSQL, 10 k docs, 8 workers, 5-round medians) says the update lane is **I/O-commit-bound, not statement-CPU-bound**: removing two redundant indexes cut 27 % of the statement's per-row work (31.6 → 13.1 µs, GIN included) and changed nothing measurable on the lane, while read lanes drifted 0.91–1.05× between the same two variants. What does move it is the response — `Prefer: return=minimal` (RFC 7240) measured **1507 → 1572 RPS (+4.3 %)**, 1901 → 70 B, reproducible with `BENCH_PREFER_MINIMAL=1` against the replica. Pending: (a) the external harness applying `Prefer` to **every** row (disclosed in its METHODOLOGY §7/§10) or the benchmark-authored Keystone/Wagtail write routes returning the representation — without either, the row compares 1901 B of native resource against 43 B of harness ack (`docker/keystone/rest.ts`); (b) a CPU profile of the cold read lane (`SVELTY_CPU_PROFILE=<dir>`, see [server-hooks](../reference/architecture/server-hooks.mdx)) to decide whether the residual ~220 µs of in-lane JS justifies a compiled per-collection lane reader instead of the SDK facade.

**Paired A/B, 2026-09-23** (4 alternated pairs × 5 rounds, PostgreSQL replica, 5 000 docs, 8c, with an unaffected lane carried as the control): `cold.findByIdRandom` — which `Prefer` cannot touch — moved **−0.3 %** paired median (spread −9.4 … +0.9 %), which is what makes the design trustworthy on this host; `update` moved **+7.8 % paired median with all four pairs positive (+4.7 … +10.7 %)** for the RFC 7240 minimal ack, and `create` moved **−2.6 % (spread −12.3 … +1.9 %)** with POST support — so the POST half was reverted rather than shipped unproven. The lesson worth keeping: an _unpaired_ median moved ±10 % between arms on the control lane, i.e. a single A/B pair cannot resolve anything at this effect size, and any claim here needs alternated pairs plus a control lane.

**Where the `update` lane actually goes, and what is left (2026-09-24)** — server-side spans (`PROFILE_WRITE=1`, PostgreSQL, 10 k docs, 8c, p50 of 1 637 samples) put **our own work above the adapter at 0.05 ms** (`db:upd:prepare-values` 0.007, `ns:prep:*` 0.004–0.007, `ns:sanitize+validate` 0.014, `ns:beforeSave` 0.024) against **`db:upd:raw` 2.54 ms** and `ns:persist` 2.81 ms — and `db:ins:exec` measures 2.53 ms, i.e. the cost is per-statement/commit, not update-specific. The bridged transport is the _smaller_ half: at one worker the whole request is 3.03 ms against 2.81 ms of server-side persist, leaving **~0.13 ms (4 %) for the entire framework path** — which is why bridging writes is not worth the body-replay complexity, and why the lane's own +125 % on reads does not transfer (reads are transport-bound at 0.05–0.78 ms of work; writes are not). The engine agrees: `scripts/benchmark-matrix/raw-db-ceiling.ts --db=postgresql` measures a bare `postgres.js` single-row UPDATE at **3.5 k RPS / 286 µs at 8c but only 821 RPS / 1.22 ms at 1c**, so our 1 276–1 540 RPS is **~40 % of the driver ceiling** and KeystoneJS's published 1 437 is **41 %** of the same ceiling — two implementations of the same operation landing within noise of each other on a commit-bound path. The correlation to keep: **the WAL flush dominates every lane on this host**, so index hygiene, payload trimming and statement micro-work cannot move it (each already measured as lane-neutral or below the noise floor). The one lever left that changes the physics is **batching concurrent single writes into one durable flush**, which needs per-caller rows back — i.e. a `RETURNING`-capable bulk update on all three SQL engines plus a next-tick coalescer, with `N` callers receiving `N` correct rows. That is a deliberate change with its own correctness gate (per-caller results, tenant clause, JSON-patch merge, timestamp stamps), not a micro-optimisation, so it is specified here rather than shipped unverified: a `perf:` commit has to move its gate before it lands.

**Write coalescing: implemented, gated, measured negative, reverted (2026-09-24)** — the specification above was built out and taken to its gate rather than left as a note, and the gate rejected it. The mechanism: a per-adapter next-tick coalescer (`core/write-coalescer.ts`) queued concurrent single-row updates and executed them as one `UPDATE … CASE … WHERE _id IN (…)` through the adapter's existing `rawBulkUpdate`, with one `findByIds` read-back for the per-caller rows, mandatory per-entry fallback to the unbatched `executeUpdate`, an id-collision split so a twice-queued row cannot lose an update, a `SVELTY_WRITE_COALESCE=0` kill-switch and a `SVELTY_WRITE_COALESCE_WINDOW_MS` batch window.

- **It works, and it is correct.** End-to-end over HTTP (PostgreSQL, 64 docs, 8c, 2 rounds × 3): **128/128 PATCHes returned their OWN document** (id, `count` and title asserted per request) and every value reloaded from the DB with `?refresh=true`; the response key set was identical to the unbatched path. Batching fired hard — at the default zero-latency window (`setImmediate`, no added latency) **120 of 128 writes batched at an average size of 5** (3×8, 5×8, 7×8), and at a 2 ms window average size 7.5.
- **It is slower on PostgreSQL, decisively.** Three alternated pairs on the replica protocol (10 000 docs, 8c, 3 rounds): `update` **1 346 → 950**, **1 315 → 930**, **1 255 → 718 RPS** — median **−29 %**, and the warm p95 latency blew out from ~7.7 ms to 15.7–20.4 ms. The `findByIdRandom` control lane stayed flat across the same six runs (3 645 – 4 084 RPS), so this is not host drift.
- **Why, and why it cannot be fixed by tuning.** The premise was wrong: at 8 workers PostgreSQL already group-commits overlapping transactions, so N concurrent statements cost about one durable flush already — coalescing removed a cost that was not there and paid for it with a second statement plus a bigger plan. The arithmetic follows the earlier probe (`synchronous_commit=off` = +21.7 % is the _no-flush-at-all_ bound, not a coalescing bound), and the only variant that could win is one statement with `RETURNING` instead of the read-back — which needs new per-engine SQL for a ceiling of roughly parity. **Deprioritised: on this evidence the lever is not worth three engines of new SQL.** The code, its unit test and the driver are deleted rather than left off-by-default, per the no-legacy-tails rule; the measurement is the deliverable.

**Raw-transport fast lanes, 2026-09-23** (registry, not a one-off bridge; **default ON since 2026-09-24**, opt-out `SVELTY_FAST_LANE=0`): the single shared server entry `index.server.mjs` — used by `index.cjs` on Node, `bun index.cjs` on Bun, and `start` — hands GET/HEAD requests to a lane registry the app publishes on `globalThis`. A lane calls the very same functions the SvelteKit path calls (`tryCollectionReadLane`), so auth, tenancy, publication filter, cache and security headers stay in one place — nothing is re-implemented — and writes the returned `{ status, headers, body }` straight to the socket, bypassing adapter-node's `IncomingMessage → Request` and `Response → stream` bridging. Adding a lane never touches the entry, and `LANE_BYPASSED_HOOKS` plus the guard test (`tests/unit/hooks/fast-lane-policy.test.ts`) fails when a new `hooks.server.ts` pipeline hook appears unclassified, so a hook cannot silently miss lane traffic. Equivalence is machine-checked inside a single server run by `BENCH_VERIFY_RAW=1` (the `x-fast-lane: off` request header forces the bridged path for that request only, so both transports share one session and one database): point read **200/200 · 1382 B identical**, missing id 200/200 · 28 B, list 200/200 · 11154 B, HEAD 200/200 · 0 B, `If-None-Match` **304/304**. Paired A/B (3 pairs × 5 rounds, PostgreSQL, 5 000 docs, 8c): **`findByIdRandom` +21.7 % (all three pairs +20.4 … +34.1 %), `findById` +82.7 %, `listPlain` +49.1 %**, while the lanes the bridge cannot touch moved ±7 % — the target gains sit outside that band, but the magnitude deserves a re-run now that the hit marker is observable, and the profile's earlier prediction (~10 % of server time in plumbing) underestimated the response-side stream cost. **Still open before this could default to on**: the write lanes are not bridged (they need the request body through the same path), and bypassing the vendored response writer deserves a deliberate security review — the lane still requires a warm admin session, but the bypass point sits before every hook.

**Fast lanes default ON, state-gated, byte hand-off fixed (2026-09-24)** — the two blockers above are now decided and implemented, and the row is re-measured at the regime the replica protocol publishes (10 000 docs):

1. **`system-state` is re-applied, not skipped.** `src/hooks/lane-state-gate.ts` mirrors `handleTurboPipeline`'s own readiness predicate against the same module-level state mirror (`READY`/`WARMED`/`WARMING`/`DEGRADED` serve; `SETUP`/`IDLE`/`INITIALIZING`/`MAINTENANCE`/`RECOVERY`/`FAILED` decline to the pipeline, which produces the maintenance page, the setup redirect or the 503). It is consulted three times on purpose — in `tryCollectionReadLane`, in `tryCollectionWriteLane`, and again in the registry dispatch so a lane added later cannot serve a state an operator took the instance out of. `tests/unit/hooks/fast-lane-policy.test.ts` pins both the state matrix and the dispatch backstop, and `collection-read-lane.test.ts` now establishes an operational state in `beforeEach` (the lane has a precondition; the test satisfies it rather than the lane excusing it).
2. **Default flipped to ON** (`SVELTY_FAST_LANE=0` opts out) so the comparison is config-symmetric instead of a benchmark-only flag: the lane is the same function, reached without adapter-node's bridging, and equivalence stays machine-checked by `BENCH_VERIFY_RAW=1`.
3. **Byte hand-off (regression found and fixed by the measurement).** The lane shim called `Response.text()` and passed the string to `res.end()`, so a 100-row list body was decoded and re-encoded per request: `listLarge` TURBO-HIT measured **2.64 ms bridged → 4.76 ms through the lane**. It now uses `arrayBuffer()` and hands Node the bytes (`content-length` from `byteLength`): **2.85 ms, back at parity with the bridged path**, and the wide-body lanes recovered (`mixed` 2 610 → 2 199 RPS with the regression, 2 128 after the fix at the same dataset — the free-standing `listLarge` row was the clearer signal).

**Re-measured row, paired (PostgreSQL, 10 000 docs, 8c, `tests/benchmarks/competitive-workload-replica.test.ts`, 3–4 rounds per arm):** `findByIdRandom` **3 235 → 3 655 RPS median (+13 %)** with the lane on versus off; `findById` **7 067 → 9 194 RPS**; `listPlain` 7 187 → 10 876; `findMissing` 8 138 → 9 496. Against the published competitor row (3 504 RPS, publicly available results as of September 2026) that is **+4 %**, and individual runs ranged 3 479 – 3 861 — a win, but inside a band that a single run cannot resolve. Independent confirmation of the mechanism: a dedicated 10 000-doc load driver (20 000 random point reads, 8c, server-only CPU profile) measured **3 080 RPS bridged → 4 401 RPS lane-served**, with the profile attributing ~10 % of server samples to undici `Request` construction, 5.7 % to adapter-node's `viaCache` static check and ~12 % to socket writes — i.e. the win is exactly the bridging, and the lane's own work is unchanged (`x-srv-dur` p50 0.74 ms bridged vs 0.71 ms raw).

**Superseded at 100 000 docs (2026-09-24, paired, same protocol, `BENCH_DOCS=100000`)** — the earlier session's reading that this row goes _neutral or negative_ at 100 k **does not reproduce on the default-on build**; it was taken before the lane's byte hand-off fix and with the lane opt-in, and it is corrected here rather than left standing:

| 1    |    2 631 | **3 919** | +49 % | 1 414 → 1 444 (+2 %)                |

Median **2 885 → 3 901 RPS (+35 %)**, i.e. **+11 % over the published 3 504**, with the write lane carried as the control and staying flat (±3 %) — which is what makes the read delta attributable to the transport rather than to host drift. So the claim is not regime-scoped after all: it holds at both dataset sizes, and the 100 k row is the stronger one. `findById` on the same pairs moved 4 850 → 13 617 and 6 681 → 12 648.

**Still open**: the write lanes are not bridged (they need the request body through the same path) — measured as the _smaller_ half of that lane, see the next item.

**Adapter-node now dispatches the lane registry; cold-path trims land (2026-09-24)** — the published row ran the container on `node build/index.js` (adapter-node), whose entry never consulted `globalThis.__SVELTY_FAST_LANES__`: the registry was published at boot, but only `index.server.mjs` dispatched it, so the measured 2 596 RPS on `findByIdRandom` was lane-OFF in all but name. The build now patches the adapter-node entry (`adapterNodeBuildPatchPlugin` in `vite.config.ts`) with the same dispatch plus the per-socket `setNoDelay(true)` that `index.server.mjs` sets. Nothing else changes: the lane functions, the state gate, the `x-fast-lane: off` opt-out and the `BENCH_VERIFY_RAW=1` byte-identity gate are untouched, so every adapter-node deployment — not only the benchmark container — gets the lanes, and a changed adapter-node template leaves the entry unpatched (pattern-guarded, warning logged).

Verification (same host, same `bench-db` Postgres, same entry `node build/index.js`, production mode, `BENCH_DOCS=100000`, 8c, replica protocol):

| entry variant                 |    findByIdRandom |        findById |       listPlain |     findMissing | control (create/update/graphql)                                            |
| :---------------------------- | ----------------: | --------------: | --------------: | --------------: | :------------------------------------------------------------------------- |
| adapter-node, unpatched       |             3 013 |           9 125 |           7 817 |           9 363 | 1 531 / 1 504 / 3 247 (≈ the lane-OFF pair value 2 885)                    |
| adapter-node, patched + trims | **4 470 – 4 553** | 13 576 – 13 640 | 11 822 – 13 544 | 16 138 – 16 937 | 1 563 – 1 588 / 1 463 – 1 544 / 3 252 – 3 331 (inside the ±8 % noise band) |

`BENCH_VERIFY_RAW=1` re-run on the patched entry: point read, list, HEAD and `If-None-Match → 304` byte-identical between the lane and the bridged fallback. Projection for the external row: the measured lane-OFF→ON ratio at 100 k (paired 2 885 → 3 901 in the September session; 3 013 → ~4 500 on the adapter-node entry today) applied to the published 2 596 lands ≈ 3 860 – 3 900, above the published competitor row (3 551, publicly available results as of 2026-09-24) — but this lane's session-to-session spread is ±8 – 30 %, so the claim needs the paired protocol on the next external session, not a single run.

Cold-path trims shipped with it (all inside the lane's own steps, each visible in the attribution table above):

1. **`LocalCMS.getLocals` facade removed from the lane** (9 µs/request in the 2026-09-22 attribution): the lane holds one cached `LocalCMS` instance per process; the `collections` namespace is stateless per adapter and tenancy still comes from `applyAdapterTenantContext`. `tests/unit/hooks/collection-read-lane.test.ts` mocks the constructor shape instead of `getLocals`.
2. **The SDK `findById` L2 `getSync` probe is gated on `!skipCacheService`** — the lane caches the whole HTTP response in `responseCache`, so probing the shared cache (which it never writes) was a guaranteed miss per cold id.
3. **The fast lane builds a minimal URL facade** (`pathname`/`search`/`searchParams`/`protocol`/`hostname` from `req.url` + `origin`) instead of a full `new URL()` parse per request; the lane's access surface is exactly these five properties (`handleApiError` reads only `pathname`), and the byte-identity gate covers the rest.

**Dataset-complexity limits mapped, four cliffs closed or refuted (2026-09-24)** — the full matrix at 1.1M–1.5M docs lives in [scale-limits-1m-postgres](./benchmarks/scale-limits-1m-postgres.mdx), with the raw-driver gap map from `scripts/benchmark-matrix/raw-db-ceiling.ts`. Summary: **reads are at the driver ceiling** (findById 16.0k RPS vs 15.4k driver, findMissing 114 %, listPlain 147 % — nothing left on the read side), **writes are at ~50 %** (create/update 1.5k vs 3.2k/2.9k driver) and the write gap is app work, not indexes — a controlled A/B (`probe-write-index-cost.ts`) measures the 12-index + GIN shape at **0.93–0.97×** of the 4-index shape, refuting W5. The cliffs closed: **W1** dynamic-field sort (3.8 s → 5.1 ms at 1.1M rows via a lazy `((data->>'field'))` expression index, fire-and-forget, bounded registry, `SVELTY_LAZY_SORT_INDEXES=0` opt-out), **W4** adapter-node `BODY_SIZE_LIMIT` 512K → 100M build patch (821 KB bulk verified; the external container's 1.4k-docs/s seed was exactly this), **W3** capacity-gated 2-touch list-tier admission in `response-cache.ts`. **W2** (REST keyset cursor) deferred on purpose: the SDK's field-based keyset merges a single-condition filter, so duplicate sort values repeat/skip pages — the composite `(field < v) OR (field = v AND _id < id)` merge lands first, then the REST surface. No hard limits introduced anywhere: the lazy index is self-tuning, the list admission is capacity-gated, the body limit just stops the kit from rejecting what the app's own 15 MB guard accepts.

- 🏗️ **Write-lane decomposition + multi-core cluster design (2026-09-24)** — the write lane's `x-srv-split` was security/persist/serve; persist was a black box. The collections namespace now accepts an internal `LocalApiOptions.__phaseMarks` map (absent by default, zero cost) and stamps per-request durations for `schema` (peek/schemaOf + hot flags), `prep` (sanitize + validate + gate + beforeSave + widgets), `encrypt`, `dbwrite` (adapter INSERT/UPDATE + outbox scheduling), `postwrite` (decrypt clone + schedulePostWrite), plus `snapshot` on revision-enabled updates; the lane adds `parse` and stamps `x-srv-dur` on writes like the read lane. Collection p50s: `tests/benchmarks/probe-write-split.test.ts`. **Measured at 8c/Postgres (production mode): create srv-dur p50 4.63 ms of which security 0.020 / parse 0.070 / schema 0.020 / prep 0.030 / encrypt 0.000 / dbwrite 4.34 / postwrite 0.030 ms; update p50 3.81 ms with dbwrite 3.59 ms.** The app phases sum to **~0.16–0.17 ms** — the suspected ~0.3 ms app blob does not exist; the write lane is already lean and the gap to the driver ceiling is the WAL commit inside `dbwrite` (consistent with the commit-bound probe). The **multi-core cluster design** is written up in [cluster-multi-core](../reference/architecture/cluster-multi-core.mdx): `node:cluster` shared-socket workers with a full state-partition table (what is per-process vs shared today), the single real gap — the in-process `graphql-yoga` pub/sub that keeps `entryUpdated`/`yjs:*`/SSE from crossing workers, with a Redis-bridge target — and the sizing formula `K = min(cores, DB ceiling ÷ per-process RPS)` grounded in the ceiling map. `scripts/benchmark-matrix/probe-cluster-scaling.ts` measured the RPS(K) curve (load in a forked child — an in-primary undici loop stalls to ~12 req/10s on Windows): **findByIdRandom 5.8k/8.1k/8.5k/9.4k, listPlain 11.2k/13.3k/11.9k/13.6k, create 1.36k/1.75k/2.0k/1.97k for K=1/2/4/8** — per-worker efficiency leaves 1.0 at K=2 and the DB is the crossover: K=2–4 saturates the shared bench-db, more workers buy queueing, not throughput.

- 🏗️ **Measured corrections to the fast-lane work (2026-09-23, later session)** — three findings that supersede earlier claims in this section, recorded so they are not re-derived:
  1. **The raw transport is regime-dependent, not a blanket win.** At 5 000 docs it measured **+21.7 % on `findByIdRandom`**; a full 11-workload A/B at 100 000 docs / 8 workers, with `update` carried as the control (write lanes are not bridged), put the read deltas at **+1.8 % (`findById`), −7.0 % (`findByIdRandom`), +1.4 % (`listPlain`)** against a **±8 % noise floor** — at 100 k the read lanes are DB/cache-bound, so bypassing the framework's request→`Response`→socket bridging buys ≈ nothing there. It remains real for warm hits and lists in transport-bound regimes (small datasets, high cache-hit installations).
  2. **The point-read route is already lane-served.** `isSimpleCollectionRead` accepts both `GET/HEAD /api/collections/:collection` and `/:collection/:entryId`, so all six read workloads are already eligible — extending lane coverage to other deterministic GET routes helps those endpoints, never this row.
  3. **The row's shape is cold-read locality, not transport.** Hot id vs random id at 8c: **6 014 → 3 100 RPS**, i.e. 1.33 ms vs 2.58 ms per request (**+1.25 ms**), while the comparison row is flat (2.28 ms both) — a flat ratio there can also mean uniform slowness rather than the absence of a defect. The split that decides the fix is `SVELTY_SRV_DUR=1`: compare `x-srv-dur` for a hot id against a random id in one run — ≈ 1.2 ms means a DB-class wait (page fetch/queueing, where the only levers are row/page economics with real write-side costs), ≈ 0.2–0.3 ms means miss-path app work (cache-key builds, admission bookkeeping, generic row flattening — all removable). With that floor, **nothing below ~15 % on this row is claimable.**

- 🏗️ **Engine-knob probe: commit-bound writes (2026-09-23, host-labelled, deliberately NOT shipped)** — `synchronous_commit=off` measured the external harness's update lane at **8 workers +21.7 %**, **1 worker +93.1 %**, and seeding **+18.9 %**. Two conclusions: the write path is commit-bound (which also explains why removing 27 % of per-row statement work moved no RPS — the WAL flush dominates, so index hygiene pays in WAL/disk/VACUUM instead), and this is the measured ceiling for a CMS-side coalescing implementation that keeps one durable flush per batch. It is **not shipped**: the setting is cluster-global, so every row on the same Postgres rises identically and the ratio does not move (1 306 → 1 590 vs 1 437 → 1 749). A CMS-side fix is per-row by construction; at 8 workers PostgreSQL already group-commits overlapping transactions, so expect roughly parity to +11 % on that lane — the defensible claim is **concurrent write throughput as a product property**, with parity on the published row accepted.

- 👨‍🔬 **The 1.25 ms is the MISS rebuild — split measured (2026-09-23, harness-side, sequential c=1, 400 requests, same 100k dataset and container boot)**: HOT (`ids[0]`) wall **1.17–1.26 ms** with **server `x-srv-dur` p50 0.070 ms** (TURBO-HIT ×400); COLD (distinct ids) wall **1.42–1.54 ms** with **server p50 0.470–0.480 ms** (MISS ×400). A ~1.1 ms per-request floor is identical hot and cold and lies _outside_ the stamped section (framework/adapter/HTTP/routing) — it caps absolute RPS but does not explain the gap. The ~0.45 ms of MISS-path server work surfaces as ~1.25 ms of added latency and ~20 % of throughput at 8 workers through queueing (`W = L/λ`). **Acceptance gate for read-path work: COLD `x-srv-dur` p50** — it read 0.480 vs 0.470 ms across a full rebuild while RPS moved ±8–20 %, so a change that does not move it is not a read-path win; its target is ≈ 0.30 ms (parity) plus the ~277 B payload trim as the separate bytes-column win. Two corrections to the suspect list: the point-read etag is already the cheap `id-updatedAt` form (`generateContentEtag` is the list path), and the two `dd317ae28` cuts measured < 0.05 ms — below this probe's resolution, exactly as dead-work removal should be, so the earlier +19 % attributed to them is retracted as lane spread.

- 🔧 **Harness-mirror fetch refspec (2026-09-24, operator note)**: a mirror checkout whose `remote.origin.fetch` tracks only `next` leaves `origin/main` silently stale (observed at `7a801f1bf` while `main` had moved) — a row measured from such a clone is measured from the wrong revision. Fix in the mirror with `git remote set-branches origin '*'` (or `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'`) and re-fetch before a session.

- **Rust Tooling Evaluation (`fuzdev/tsv`)** — evaluated 2026-09-21; recommendation: **stay with `oxfmt`**, which already ships the needed capability behind a disabled flag. `tsv` 0.4.1 is faster but not _more capable_.
  - `oxfmt` (pinned `^0.68.0`) has a top-level `svelte` key: "Pass `true` or an object to enable `.svelte` file formatting … Default: Disabled", and it loads `svelte/compiler` at runtime — **`svelte@^5.57.1` is already a direct dependency here**. Its `overrides` key supplies per-glob options, so `.svelte` can keep its own style. Measured with a throwaway config (`"svelte": {}` plus a `**/*.svelte` override on tabs / single quotes / no trailing commas): `oxfmt --check src` covers **1470 files in 1.59 s** (1024 → +446 `.svelte`) while `src/**/*.ts` (918 files) stays clean. With the key omitted, oxfmt matches **0 of 489** `.svelte` files. Reproduce: `bun x oxfmt -c <probe.json> --check src`.
  - **`tsv` 0.4.1 is not idempotent** on 2 of 446 `.svelte` files (`src/widgets/custom/seo/input.svelte`, `src/routes/(app)/dashboard/widgets/unified-metrics/index.svelte`): a generic argument list left as `}>(` + object is revised to `}>({` on the second pass, so a single-pass `--check` gate reports those two indefinitely. `oxfmt` reaches a fixed point on the first pass (verified on the same file), which is what a CI gate requires.
  - `tsv`'s advantage is throughput, not coverage: ~0.14 s for 446 `.svelte` files against `oxfmt`'s ~1.6 s for a whole-`src` pass — immaterial at this repo size. Its costs are a second toolchain, a layout that disagrees with `oxfmt`'s in detail (a later switch would mean a second reformat), a hardcoded non-configurable style, and no linter (it does not replace `oxlint`).
  - Whichever tool is chosen, the first run normalizes the backlog: ~427 of 446 `.svelte` files change, because nothing has ever formatted them. The diffs are layout-only — re-wrapping hand-compacted lines past 100 columns, e.g. the one-line `case 'sm': return { … }` arms in `src/components/ui/checkbox.svelte`.
