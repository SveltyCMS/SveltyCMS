# 🔐 Application-Layer Encryption (ALE) Performance Impact

> [!NOTE]
> Source of truth for these numbers is the reproducible ALE benchmark suite:
> `bun test tests/benchmarks/ale-encryption-performance.test.ts` (adapter CRUD)
> and `bun test tests/benchmarks/ale-cpu-only.test.ts` (isolated crypto cost).
> Raw results: `tests/benchmarks/results/ale-encryption-performance.json` and
> `tests/benchmarks/results/ale-cpu-only.json`.

## ZIEL

Quantifizieren, welchen Overhead Application-Layer Encryption (ALE) — hier
AES-256-GCM Feldverschlüsselung (`@utils/security/field-encryption`) — auf der
**Datenbank-Adapter-Schicht** (`db.crud.insert`) verursacht, im Vergleich zu
unverschlüsselten Schreibern.

## Konfiguration

| Parameter | Wert |
| --------- | ---- |
| Layer | `dbAdapter` → `db.crud.insert` |
| Verschlüsselung | AES-256-GCM (`aes-256-gcm`, 256-bit) via `node:crypto` |
| Verschlüsseltes Feld | `email` (Typ: Feld `encrypt: true`) |
| Schreibvorgänge / Lauf | 1000 |
| Warmup | 100 |
| Testläufe | **3** |
| DB-Engine | SQLite (Benchmark-Datei) |
| Ausführungszeitpunkt | 2026-09-07 21:00 (CEST) |

> [!WARNING]
> ALE wird hier **extern** auf `db.crud.insert` angewandt (via `encryptDocumentFields`),
> weil der rohe Adapter die Feldverschlüsselung nicht selbst anwendet — der eigentliche
> ALE-Hook (`encryptWritePayload`) läuft in der SDK-Write-Pipeline. Die Messung bildet
> damit den realen, zusätzlichen Verschlüsselungsaufwand auf der Adapter-Schicht ab.

## Ergebnisse (Mittelwert über 3 Läufe)

### Adapter-Schreibpfad — Baseline vs ALE

| Metrik | Baseline (Klartext) | ALE (AES-256-GCM) | Delta | Δ % |
| ------ | :-----------------: | :---------------: | :---: | --: |
| **Ø Latenz / Write** | 0.107 ms | 0.128 ms | **+0.021 ms** | **+19.7%** |
| p50 Latenz | 0.061 ms | 0.077 ms | +0.016 ms | +26.2% |
| p95 Latenz | 0.114 ms | 0.142 ms | +0.028 ms | +24.7% |
| **Durchsatz** | 9 331 writes/s | 7 810 writes/s | **−1 521 writes/s** | **−16.3%** |
| CPU-Last (Messfenster) | 94.0% | 98.4% | +4.4 pp | +4.7% |

### Isolierte Verschlüsselungskosten (ohne DB-Noise, 20 000 Ops)

| Metrik | Wert |
| ------ | ---- |
| Ø Latenz / Op | 0.0046 ms |
| p95 Latenz | 0.0064 ms |
| p99 Latenz | 0.0090 ms |
| Durchsatz | ~213 385 ops/s |
| CPU-Auslastung (sustained) | 100 % 😅 |

## Interpretation

1. **Die Verschlüsselung selbst ist extrem günstig**: Eine AES-256-GCM-Operation
   kostet im Schnitt nur **~4.6 µs** (Hardware-beschleunigt via AES-NI). Der reine
   Kryptoaufwand entspricht damit nur ~4 % der DB-Schreibzeit.
2. **Der messbare Overhead liegt überwiegend im Synchronisationspfad**: Der
   Durchsatzverlust von ~16 % entsteht, weil die Verschlüsselung die asynchrone
   Write-Pipeline um eine zusätzliche, serialisierte CPU-Phase verlängert, die
   nicht vollständig mit dem DB-I/O überlappt.
3. **CPU-Seite**: In einer engen, isolierten Schleife läuft AES-256-GCM mit ~100 %
   CPU (rein CPU-gebunden). Auf der Adapter-Schicht (mit I/O-Wartezeiten) sinkt das
   auf einen Delta von ~4.4 Prozentpunkten — die Verschlüsselung wird teilweise
   durch die währende DB-I/O-Zeit "überdeckt".

## Kosten-Nutzen

- **Kosten**: +19.7 % Schreib-Latenz, −16.3 % Schreib-Durchsatz (bei 1000-Write-Läufen).
- **Nutzen**: Felder-at-rest sind verschlüsselt (`v1:iv:tag:ciphertext`-Envelope),
  angebunden an den Tenant- und Kollektions-Kontext (AAD, Swap-Schutz), und
  Domänen-separiert (HKDF). Erfüllt Anforderungen für schützenswerte personenbezogene
  Felder bei vertretbarem Latenz-Aufschlag.

> [!TIP]
> Für Systeme mit hoher Schreiblast und niedrigen Latenz-SLAs, aber verschlüsselungs-
> pflichtigen Feldern: nur die tatsächlich sensiblen Felder als `encrypt: true`
> markieren (nicht ganze Dokumente). Der messbare ALE-Overhead skaliert linear mit
> der Anzahl der verschlüsselten Felder (pro Feld ~4.6 µs Verschlüsselungskosten).

## Verifikation (3 Testläufe)

| Lauf | Baseline Ø (ms) | ALE Ø (ms) | Baseline w/s | ALE w/s | CPU Δ (pp) |
| :--: | :-------------: | :--------: | :----------: | :-----: | :--------: |
| 1 | 0.103 | 0.137 | 9 634 | 7 251 | +95.1 → 100 |
| 2 | 0.115 | 0.129 | 8 621 | 7 728 | +91.0 → 100 |
| 3 | 0.102 | 0.118 | 9 739 | 8 451 | +90.9 → 100 |
| **Ø** | **0.107** | **0.128** | **9 331** | **7 810** | **+4.4** |

> [!NOTE]
> Die CPU-Spaltenwerte einzelner Läufe schwanken (91–100 %), weil `process.cpuUsage()`
> in einem sehr kurzen, schnellen Messfenster durch Thread-Scheduling verrauscht wird.
> Der isolierte Crypto-Test (20 000 Ops, sustained) liefert den stabilen Referenzwert
> für die reine Verschlüsselungs-CPU-Kosten (~100 % CPU gebunden).

> [!INFO]
> **Reproduzierbarkeit**: Die absoluten Millisekunden-Werte variieren zwischen
> Ausführungen (Warmup-, GC- und Scheduling-Zustand — normal bei Microbenchmarks).
> Das **Verhältnis** (ALE ≈ +15–20 % Latenz, ≈ −15–16 % Durchsatz) ist über mehrere
> Verifikationsläufe stabil. Ein zweiter Verifikationslauf (2026-09-07, zweite Ausführung)
> bestätigte: Baseline Ø 0.076 ms/12 000 w/s vs ALE Ø 0.093 ms/10 900 w/s.
