# Competitive Security Overview

This is a **dedicated security companion** to the broader
[Competitive Comparison](./competitive-comparison.mdx). It answers the
questions a security officer or lead architect asks during a vendor review:
_How do users authenticate? What forces a second factor? Can logs be tampered
with? How fast do permission changes propagate?_

> **Honesty note (EU/UWG §6):** Every claim is **date-stamped**, **source-based
> (public vendor documentation or pricing pages)**, and **not** a third-party
> audit or a live measurement run against competitor instances. Nothing below
> was measured with our own benchmark harness against a running competitor
> deployment. Where a capability is described as "documented in core," that is
> what **our own documentation** states about SveltyCMS; for competitors it is
> what **their** public documentation states. Verify current tiers on each
> vendor's pricing page before a procurement decision.

## Per-platform control detail

### SveltyCMS

- **SSO/SAML/OIDC** — documented in core, with RP-initiated, front-channel, and
  back-channel logout flows.
- **SCIM 2.0** — native endpoints (RFC 7644), core, free.
- **RBAC** — permission revocations propagate in under 1 ms (instant
  invalidations), versus TTL-based caching in the alternatives.
- **Audit logs & RBAC audit trail** — built-in, tamper-evident via SHA-256-chained
  ledger. Records all data mutations, logins, and administrative role/permission changes
  (`ROLE_MUTATED` / `ROLE_DELETED`) with acting administrator identity and modified grants.
- **Per-role MFA enforcement & session elevation** — supported in core via `mfaRequired?: boolean`
  on the `Role` interface (`src/databases/auth/types.ts`) and session `amr`
  (Authentication Method References). When a user's role mandates MFA, un-enrolled
  users are gated to `/user?tab=security` to complete 2FA setup before accessing
  protected admin/API resources. Trusted-device logins are tagged with `amr: ["pwd", "trusted_device"]`
  and automatically require step-up authentication (`STEP_UP_MFA_REQUIRED`) for high-privilege
  administrative operations, lifting device trust directly to the session MFA level.
- **Streamed collection export** — `GET /api/collections/{id}/export` streams
  NDJSON, CSV, or chunked JSON from database cursors / paged SQL reads so the
  process does not hold the full export in memory. Self-described, September 2026.
- **Collection ETag / 304** — `GET /api/collections/{id}` documents a weak
  collection-generation ETag (`W/"cv1|…"`). Matching `If-None-Match` returns 304
  before the collections handler (no database query). Self-described, September 2026.
- **Field-level encryption at rest** — collection fields flagged `encrypt: true` are stored as
  AES-256-GCM envelopes (`v1:iv:tag:ciphertext`) using `ENCRYPTION_KEY`. Writes fail closed
  without the key; reads decrypt a clone so L1/L2 caches keep ciphertext. See
  [Field-Level Encryption](../reference/security/field-level-encryption.mdx).

### Payload CMS

- SSO/SAML/OIDC offered via **plugin**; SAML in the Enterprise tier.
- SCIM 2.0 and compliance-grade audit logs in the **Enterprise tier**.
- MFA/2FA available via documented configuration in paywalled tiers.
- RBAC relies on TTL-based caching (change propagation is not instant).
- Field-level encryption is documented as a **collection/field hook pattern** (public blog
  example uses AES-256-CTR) and a **marketplace plugin**; as of September 2026 public docs
  do not describe a native `encrypt: true` schema flag in free core.

### Strapi

- SSO/SAML/OIDC and SCIM in **Paid Pro / Enterprise** tiers.
- Audit logs via **plugin** or Enterprise tier.
- Rate limiting provided by a community plugin.
- RBAC via TTL-based caching.
- Public security documentation (as of September 2026) states dashboard-entered data is
  **not automatically encrypted**; field encryption is offered via a marketplace plugin
  (AES-256-CBC in that plugin's public listing). Export-file encryption (`aes-128-ecb`)
  is documented separately from per-field at-rest encryption.

### Directus

- **Built-in SSO** (OIDC / LDAP / SAML) — a genuine strength.
- SCIM 2.0 and compliance-grade audit module in the **Enterprise** tier.
- Built-in activity log (non-chained) in the open tiers.
- RBAC also relies on TTL-based caching.
- Public security page (as of September 2026) states clients are **wholly responsible**
  for encrypting fields considered personal; field-level AES-GCM appears in **extensions**,
  not as a documented native schema flag in core. Disk-level envelope encryption is
  described for Directus Cloud infrastructure, which is a different control from
  per-field application encryption.

## Known gaps & roadmap (SveltyCMS)

- **Zero open architectural gaps** — all tracked enterprise security controls (per-role MFA enforcement, trusted-device session elevation, native field-level AES-256-GCM encryption, cryptographic RBAC audit trail, SCIM 2.0, SAML/OIDC, and instant RBAC invalidation) are natively implemented and continuously verified.
