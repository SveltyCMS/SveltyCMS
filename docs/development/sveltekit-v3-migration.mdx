# SvelteKit 3.0 Production Architecture & Migration Guide

> [!NOTE]
> **SveltyCMS is built natively on SvelteKit 3 (`@sveltejs/kit: ^3.0.1`) and Svelte 5 (Runes).**
> Rather than relying on legacy frameworks or retrofitting older architectures, SveltyCMS is implemented from the ground up according to official best practices from [sveltekit.com](https://sveltekit.com) and [svelte.dev](https://svelte.dev).
>
> This guide serves a dual purpose:
>
> 1. **Community Migration Guide**: A real-world production reference for developers in the Svelte ecosystem upgrading their applications to SvelteKit 3.
> 2. **Plugin & Widget Developer Contract**: An architectural guide for third-party developers building custom plugins, widgets, and themes for SveltyCMS.

---

## Why SveltyCMS Embraces SvelteKit 3 & Official Best Practices

By adopting SvelteKit 3 and Svelte 5, SveltyCMS leverages the latest advancements in web architecture:

- **Fine-Grained Reactivity (Runes)**: Moving beyond legacy store subscriptions, SveltyCMS uses `$state()`, `$derived()`, and `$props()`. Fine-grained reactivity updates only the exact DOM nodes that change, completely bypassing virtual DOM diffing and ensuring the admin interface responds in sub-millisecond times.
- **Deterministic Hydration with `$props.id()`**: Hydration mismatches are eliminated across SSR and client DOM trees by generating deterministic IDs via `$props.id()` rather than runtime random values.
- **In-Process LocalCMS vs. HTTP Serialization**: Server routes (`+page.server.ts` and hooks) communicate with the CMS core through in-process `LocalCMS` calls (0–2ms), adhering to SvelteKit's server function model rather than making unnecessary internal HTTP requests.
- **Defensive API & Redirect Security**: All external redirects (such as OAuth identity flows) enforce explicit `{ allowExternal: true }` contracts to protect against open-redirect vulnerabilities.

## SvelteKit 3 Upgrade Checklist

For developers upgrading enterprise SvelteKit applications or plugins to SvelteKit 3:

1. **Update Dependencies**:
   ```bash
   bun add -D @sveltejs/kit@^3.0.1 @sveltejs/vite-plugin-svelte@latest
   ```
2. **Synchronize SvelteKit Artifacts**:
   ```bash
   bun x svelte-kit sync
   ```
3. **Audit Environment Variables**: Replace legacy `process.env.ORIGIN` with `event.url.origin` in request handlers, or configure explicit environment variables for background workers.
4. **Audit External Redirects**: Add `{ allowExternal: true }` (or `{ external: true }`) to any OAuth or third-party redirect calls.
5. **Update Error Handlers**: Update `handleError` in `hooks.server.ts` to return explicit `{ message, code, status }` objects.
6. **Embrace Svelte 5 Runes**: Use `$state()`, `$derived()`, and `$props.id()` for deterministic DOM/ARIA IDs across SSR and hydration.

## A) `process.env.ORIGIN` → `event.url.origin` / `kit.paths.origin`

Kit 3.0 removes `process.env.ORIGIN`. In SveltyCMS, origin resolution is handled via `event.url.origin` (where request event is available) or configured environment variable:

| File                                  | Line | Change                                                                                      |
| ------------------------------------- | ---- | ------------------------------------------------------------------------------------------- |
| `src/hooks/handle-system-state.ts`    | 90   | `process.env.ORIGIN` → `event.url.origin`                                                   |
| `src/plugins/sitemap/index.server.ts` | 50   | `process.env.ORIGIN` → `process.env.SVELTYCMS_ORIGIN` (plugin context — no event available) |

## B) External Redirects Require `allowExternal: true`

Kit 3.0 forbids redirects to external URLs by default. OAuth and IdP flows require `{ allowExternal: true }`:

| File                                     | Lines              | Change                                                                       |
| ---------------------------------------- | ------------------ | ---------------------------------------------------------------------------- |
| `src/routes/login/+page.server.ts`       | 490, 500           | `redirect(303, authUrl)` → `redirect(303, authUrl, { allowExternal: true })` |
| `src/routes/login/oauth/+page.server.ts` | 380, 398, 412, 612 | `redirect(302, authUrl)` → `redirect(302, authUrl, { allowExternal: true })` |

## C) `handleError` Returns Status Code

Kit 3.0 allows `handleError` in `hooks.server.ts` to influence the HTTP response status code by returning `{ message, code, status }`:

| File                  | Line | Change                                                                  |
| --------------------- | ---- | ----------------------------------------------------------------------- |
| `src/hooks.server.ts` | 607  | Add `return { message, code, status };` after the `logger.error()` call |

## D) `fail()` Status Code Propagation

Kit 3.0 propagates the status code from `fail(status)` to the HTTP response automatically. SveltyCMS leverages this across server actions:

- `src/routes/login/+page.server.ts` — `fail(401)`, `fail(429)` for auth/rate limiting
- `src/routes/(app)/config/collectionbuilder/collectionbuilder.server.ts` — `fail(400)`, `fail(404)`, `fail(500)`
- All action handlers adhere to explicit error status codes

## Frequently Asked Questions (FAQ)

### How do I fix `process.env.ORIGIN` errors in SvelteKit 3?

In SvelteKit 3, `process.env.ORIGIN` is no longer automatically injected. For server actions, endpoint handlers, and hooks where the request `event` is present, read `event.url.origin`. In isolated background contexts (such as sitemap generators or cron tasks), supply a dedicated environment variable (e.g., `process.env.SVELTYCMS_ORIGIN`).

### Why does `redirect()` throw an error when pointing to an external OAuth URL?

By default, SvelteKit 3 fail-closes against open-redirect vulnerabilities. When redirecting to an external origin (such as GitHub, Google, or enterprise Okta/Entra ID IdPs), pass `{ allowExternal: true }` as the third parameter:

```typescript
redirect(302, authUrl, { allowExternal: true });
```

### How do Svelte 5 runes interact with SvelteKit 3 routing?

SvelteKit 3 fully embraces Svelte 5 runes. Page and layout data are accessed reactively via `$props()` rather than legacy `export let data`. Computed view states use `$derived()`, side effects use `$effect()`, and deterministic client/server HTML element IDs are generated with `$props.id()` rather than runtime random numbers.
